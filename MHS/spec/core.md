This document is the short normative core: what an endpoint, a bridge or driver, and a client MUST do so that a model-driven command reaches a device only through the limits, interlocks, permits and e-stop of the endpoint. It states the rules as the 0.9 reference implementation realises them. The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY and OPTIONAL are interpreted as in RFC 2119 and RFC 8174.

---

## 0. Conventions

**CORE-001:** A rule that cites an existing requirement id (for example `SAFE-040`) is defined in the cited chapter; this document says how the 0.9 reference implementation realises it and never weakens it. A `CORE-nnn` rule is defined here and only here. Where a chapter and this document disagree, this document wins (README §1).

**CORE-002:** "The core" is the endpoint runtime that owns safety enforcement (reference: `mhs.server`). "A bridge" or "a driver" is the translation layer under it (reference: `mhs.bridge`, `mhs.driver`). The core MUST enforce every rule of this document before any bridge I/O, and MUST NOT rely on the bridge, the driver or the model to enforce one.

**CORE-003:** OpenMHS enforces a software envelope. It is not a safety-rated channel and certifies no device, process or experiment: `MHS.SAFETY.NOT_CERTIFIED` is in `hello.features` (SAFE-050), reference files carry `safety.not_certified: true` (CORE-030), and every conformance claim, badge and document keeps the wording of SAFE-052 and SAFE-053. A physical e-stop independent of OpenMHS is the device owner's responsibility (SAFE-005, SAFE-045, SAFE-046).

## 1. Object model

| Object | Identifier | Defined by |
|---|---|---|
| Endpoint | `endpoint_id`, `mhs://host[:port][/prefix]` | [02](02-wire-protocol.md) §1.5 |
| Device | `device_id` (a URI below the endpoint), `instance_id` (ULID) | `device.schema.json` |
| Resource | `resource_id`, a state document with a `state_schema` | `device.schema.json` |
| Capability class | `cap.<class>.v<N>`, or an extension id (`x-cap.<owner>.<name>.v<N>`, or `cap.x.<vendor>.<class>.v<N>` once published, CAP-035) | `capabilities.json`, [03](03-capability-registry.md) |
| Binding | the pair `(capability_id, resource)` with its schemas and limits | [03](03-capability-registry.md) §5 |
| Command | `command_id` (ULID), the idempotency key | CORE-090 |
| Receipt | `receipt_id` (ULID) | `receipt.schema.json`, [02](02-wire-protocol.md) §10 |
| Operation | `operation_id`, `op_` + ULID | [02](02-wire-protocol.md) §7 |
| Session | `session_id`, opaque (`mhs_s_` + ULID + random suffix) | [02](02-wire-protocol.md) §5 |
| Principal | `{id, kind}`, `kind` is `human`, `agent` or `service` | CORE-150 |
| Limit | a closed rule keyed by a limit path | CORE-040 |
| Reference file | `reference.json` and `REFERENCE.md` | CORE-030 |

**CORE-010:** An endpoint serves devices. A device has one `mode` and one `risk_class`, resources, capability bindings, interlocks, and the safety declarations `estop` and `safe_state`. A binding is identified by `(capability_id, resource)`; a pair MUST appear at most once per device, and the endpoint MUST refuse to start otherwise, in every mode. The runtime looks bindings up by that pair and never falls back to another binding's schema or limits. A class that is not in the catalogue is an extension (CAP-035) and carries an inline schema; the declared verb of an extension is not trusted wherever the catalogue verb matters (CORE-021, CORE-046, CORE-075).

**CORE-011:** Ids minted by the endpoint are opaque to clients. Session ids, subscription ids (`sub_` + 128 random bits) and permit ids (`permit_<ULID>_<64 random bits>`) MUST NOT be guessable; `operation_id` is `op_` + a full ULID. Clients MUST NOT derive meaning from their shape.

**CORE-012:** A device's `risk_class` (`R0`-`R3`) is never below the highest class floor of its bindings (SAFE-007) and is shown wherever a capability is listed (SAFE-010). A binding may raise a class risk, never lower it (SAFE-008).

## 2. The three primitives

**CORE-020:** Everything a client can do to a device is one of three primitives: **read**, **write** or **action**. Read is `mhs.resource.read` (and catalogue classes whose verb is `read`); write is `mhs.resource.write`; action is `mhs.command` on any other binding. Writes and actions pass the same evaluation order (CORE-060) and produce receipts; no other method changes device state, and an extension method (PROTO-003) MUST NOT bypass that order.

**CORE-021:** A read returns `{revision, state, state_hash, sampled_at}` for one resource. It never advances the revision (OP-008, PROTO-023), is not refused by the e-stop latch and needs no limit. Only a catalogued class whose catalogue verb is `read` counts as a read for the latch exemption, for `LIMITS_UNSET` (CORE-046) and for the revision rule; the declared verb of an extension id (`x-cap.*`) is not trusted for any of them.

**CORE-022:** `mhs.resource.write` is a command of the resource's `cap.device.configure.v1` binding (PROTO-025, PROTO-025a). The `patch` is that binding's input; its effective input schema is the set of non-`readOnly` properties of the resource's `state_schema`, each keeping its type, `x-mhs-unit` and bounds. A key outside `state_schema` is rejected with `MHS.RESOURCE.FIELD_UNKNOWN`, a `readOnly` key with `MHS.RESOURCE.NOT_WRITABLE` (`details.fields`). Both rules hold at any depth, through `allOf`, `anyOf`, `oneOf`, `then`, `else`, local `$ref`, `patternProperties` and the draft-07 tuple form of `items`; a `readOnly` root or an unresolvable `$ref` is `NOT_WRITABLE`. A resource with no configure binding, or a request naming another `capability_id`, is the JSON-RPC error `MHS.RESOURCE.NOT_WRITABLE` (`details.reason` `configure_unbound` or `write_class_not_configure`): the patch is never passed as another class's input. Every write receipt, refusals included, carries `capability_id` `cap.device.configure.v1`; a completed one has `output` `{applied, revision}`.

**CORE-023:** `mhs.command` names `capability_id`, `input` and `command_id`. When the class is bound to several resources of the device, `resource` is required (omitting it is `MHS.PROTOCOL.INVALID_PARAMS`, `details.reason` `resource_required`, `details.resources`); a resource the class is not bound to, including one the device lacks, is a `rejected` receipt `MHS.CAPABILITY.NOT_BOUND` with `details.bound_resources`. An unknown class is a `rejected` receipt `MHS.CAPABILITY.UNKNOWN` (PROTO-014). `input` is validated against the binding schema intersected with the class schema (PROTO-027).

**CORE-024:** Grants are per binding. `capabilities[]` of `mhs.session.open` takes class ids and patterns (every binding of the class) or objects `{capability_id, resource}` (one binding; an unbound resource is `MHS.CAPABILITY.NOT_BOUND`). `granted[]` has one entry per granted binding, and a grant never widens after open (SESS-001, SESS-011). A permit names one binding: `mhs.safety.permit` without `resource` on a class bound several times is `INVALID_PARAMS` `resource_required`, and a resource the class is not bound to is `MHS.SAFETY.PERMIT_INVALID` (`details.bound_resources`).

**CORE-025:** A stop class bound to several resources is a command like any other: without `resource` it is `resource_required`. The catalogue e-stop `cap.motion.estop.v1` and `mhs.safety.estop` are the exception (CORE-074).

```python
# runnable
from mhs.adapter import load
from mhs.testing import client_for

server = load("MHS/sdk/examples/thermostat", backend="fake")        # strict; a fake backend is served as mode "simulated"
client = client_for(server)
device_id = client.hello()["devices"][0]["device_id"]
session = client.open_session(device_ids=[device_id])["session_id"]

read = client.read("main", device_id=device_id, session_id=session)                        # read
assert read["revision"] == 0 and "temperature" in read["state"]
write = client.invoke("cap.device.configure.v1", {"setpoint": 40}, device_id=device_id,
                      session_id=session)                                                  # write: a configure command
assert write["status"] == "completed" and write["output"]["applied"] == {"setpoint": 40}
action = client.invoke("cap.thermal.setpoint.v1", {"target_temperature": 30}, device_id=device_id,
                       session_id=session)                                                 # action
assert action["status"] == "completed" and action["state_revision_after"] == write["state_revision_after"] + 1
refused = client.invoke("cap.thermal.setpoint.v1", {"target_temperature": 400}, device_id=device_id,
                        session_id=session)                                                # a limit, not a schema error
assert refused["status"] == "rejected" and refused["error"]["mhs_code"] == "MHS.SAFETY.ENVELOPE_VIOLATION"
server.close()
```

## 3. The reference file

**CORE-030:** Every device has a reference file: `reference.json`, validated by the closed schema `reference.schema.json`, and `REFERENCE.md`, its human view. It is generated, never hand-written, and deterministic: the same inputs give the same JCS bytes. Members: `openmhs`, `device`, `measures`, `adjusts`, `actions`, `safety` (`estop`, `safe_state`, `interlocks`, `watchdog_ms`, `operator_required`, `not_certified: true`), `facts`, `tags`, `fidelity`, `overlay`, `provenance`. **Measures** are the non-adjustable state properties and the read bindings that need no input; **adjusts** are the writable state properties of a resource bound to `cap.device.configure.v1`, each with its effective limit or `operator_required`; **actions** are every other binding. A risk in the file is never below the class floor or the device's declared risk.

**CORE-031:** The reference file shows the limits the endpoint enforces, not the limits the author hoped for: it is built from the effective limits of CORE-042. `mhs.devices.get` returns it as `reference`, with each binding's `x-mhs-effective-limits` (`limits`, `cumulative`, `operator_required`, `unlimited`, `narrowed`); when it cannot be rendered (for example an uncatalogued class) `x-mhs-reference-error` says why. The MCP tool descriptions and the CLI `describe` print the same limits and facts (CORE-133, CORE-136).

**CORE-032:** A fact has a `text`, a `source` (`vendor_doc`, `upstream_code`, `operator` or `interview`) and, for the first two, a `ref` of the form `path/in/clone:LINE` at the pinned commit. A statement without both is not a fact. A model-authored driver writes only `vendor_doc` and `upstream_code` facts and limits (DRV-030).

## 4. Limits

One grammar and one engine (reference: `mhs.limits`) serve classes, bindings, device envelopes, operator overlays and driver declarations.

**CORE-040:** A limit rule is a closed object `{min, max, allowed, unit, reason, source, ref, names, per}`; any other member is a load error, so a typo can never remove a bound. `min` and `max` are numbers, or one number per element of a fixed-length array (the bound array's length MUST equal the field's length); a scalar bound applies to every element of a numeric array. `unit` MUST equal the field's `x-mhs-unit`. `source` is `vendor_doc`, `upstream_code`, `class_default` or `operator`, and the first two REQUIRE a `ref`. `names` labels array elements in violations. `per` (`session`, `rolling_1h`, `rolling_24h`, `rolling_7d`) turns `max` into a cumulative budget (CORE-047). The literal `operator_required` in place of a rule defers the bound to the operator overlay. Integer bounds beyond ±(2^53−1) are refused.

**CORE-041:** A limit path is `field`, `a.b`, `a[*]` (every element) or `a[3]` (one element), combined as in `a.b[*].c`: identifier segments joined by dots, each optionally followed by `[*]` or `[N]`, at most 256 characters (`defs.schema.json` `limitPath`). For `cap.device.configure.v1` a path is a state-property path. A path that does not resolve in the effective input schema is a load error (CORE-043). A scalar bound on a numeric array applies to every element.

**CORE-042:** For each binding the effective limits are the intersection of four sources: (1) the class limits (`class_default`), (2) the binding's `limits`, (3) the device envelope `safety.envelope`, (4) the operator overlay. The effective maximum is the smallest maximum, the minimum the largest minimum, `allowed` the intersection, and element names must agree. Envelope keys are capability ids (`cap.<class>.v<N>`, `x-cap.<owner>.<name>.v<N>`) or patterns (`cap.<class>.*`, `cap.*`); every key that matches a binding applies. The overlay is `site-limits.json` (`site-limits.schema.json`, keyed by device id and then by capability id or parameter path). It is **narrow-only**: it MAY fill an `operator_required` bound and MAY tighten any other, and MUST NOT widen anything the regular sources allow. Several narrow-only sources intersect among themselves, so their order never changes the result. There is no other way to relax a limit; an operator bound never lives in a driver (DRV-021).

**CORE-043:** These defects are load errors in every mode; the endpoint does not start (strict mode reports `limits-invalid` in `MHSStrictError`; compatibility mode raises `mhs.limits.LimitConfigError`): a path that does not resolve; an unknown rule member (a misspelt `maxx`, the legacy `limit`); a bound on a non-numeric field or an object; a per-element bound on a scalar or a variable-length array, or of the wrong length; a unit other than the field's `x-mhs-unit`; contradictory sources; an unknown `per` window; a widening overlay; an overlay naming an unbound capability or a non-writable parameter; an envelope key that is no capability id or pattern (`envelope-key-invalid`); an envelope key matching no bound capability (`envelope-unbound`; compatibility mode exempts the reserved `x-cap.mhs-test.` namespace); an envelope path that resolves in none of the bindings it matches. After start-up, a device added or an envelope changed with such a defect answers `MHS.ADAPTER.MANIFEST_INVALID` (`details.reason` `limits_invalid`) on every binding except the stop classes; a late device that strict mode would refuse answers `MANIFEST_INVALID` (`details.reason` `strict_refused`). The stop classes are exempt only from such device-level defects: a stop binding's own broken rule refuses that binding, and `mhs.safety.estop` always works.

**CORE-044:** The core checks every array element and every nested leaf of the input (or patch) against the effective limits. Absent optional fields are skipped and schema defaults of omitted fields are evaluated. A value that cannot be compared with a numeric bound (a string, a boolean, NaN, an infinity) is a `type` violation and never passes. A violation is refused before any native call with a `rejected` receipt `MHS.SAFETY.ENVELOPE_VIOLATION`. `error.details` is the first violation `{path, kind, bound, value, unit, source}` (`path` is concrete, for example `joints[0]`; `kind` is `min`, `max`, `allowed`, `type` or `length`; `source` is `class`, `binding`, `envelope`, `envelope:<pattern>` or `overlay`), with `element_name`, `limit_path`, `reason` and `provenance` when known, `violations[]` (up to 16) and the legacy `field`. Limits are compared in the declared unit after conversion (SAFE-014, SAFE-015).

**CORE-045:** For paths a limit covers, the schema's own numeric bounds are evaluated after the limits (CORE-060 steps 7 to 9). An out-of-range value on a limited field is therefore a safety refusal (`ENVELOPE_VIOLATION`), not `MHS.CAPABILITY.INPUT_INVALID`, also for `mhs.resource.write`.

**CORE-046:** A call that sets a value, or relies on a schema default, at an `operator_required` path no overlay has filled is refused with `MHS.SAFETY.LIMITS_UNSET` (`details.paths`, `details.reason`), in every mode and per call. In strict mode, a hardware or hybrid write or invoke at risk R1 or above that sets a numeric leaf no limit covers is refused the same way (`details.reason` `no_limit`). Stop classes are never refused for a missing bound, and neither is a catalogued read class; the declared verb of an extension id is not trusted.

**CORE-047:** A cumulative budget (`per`) is reserved atomically before the effect and shared across the sessions of the endpoint. The amount drawn is the sum of the magnitudes of the addressed values, so a negative value never refunds a budget. Budgets are pooled per class, the smallest budget wins, and an exceeded budget is `MHS.SAFETY.CUMULATIVE_LIMIT` (`details.used`, `details.limit`, window) (SAFE-016). Stop classes and `safe_state.achieved_by` actions are exempt. With a `state_dir`, draws and releases are journalled and a restart never refills a window (CORE-170).

**CORE-048:** A binding's `clamp` is a limit and uses the same engine: an input outside it is rejected with `MHS.SAFETY.ENVELOPE_VIOLATION` before the native call. Nothing is ever truncated (ADPT-024). A clamp's `unit` is the unit after conversion; a mismatch is a load error.

## 5. Evaluation order

**CORE-060:** The core MUST evaluate a command in this order and refuse at the first failure with no side effect. A refused command never consumes a permit (one already taken is given back), never advances a revision and never becomes the recorded outcome of its `command_id` (SAFE-018, SAFE-019, OP-005). A check that cannot be evaluated refuses. This list replaces the order in SAFE-011.

| Step | Check | Refusal |
|---|---|---|
| 1 | **Principal.** The principal comes from the bearer token; a self-declared `human` or `operator` without a token is an `agent` (CORE-150) | `MHS.AUTH.*` |
| 2 | **Session and grant.** The session is live and owned by the caller; the class is granted, then the resolved binding | `MHS.SESSION.*`, `MHS.SESSION.CAPABILITY_NOT_GRANTED` (JSON-RPC errors) |
| 3 | **Binding.** `(capability_id, resource)` resolves | `MHS.CAPABILITY.UNKNOWN`, `NOT_BOUND`, `resource_required` |
| 4 | **`command_id`.** A replay returns the retained receipt with `replayed: true`; another input digest, or another action in flight, is refused | `MHS.CONFLICT.COMMAND_ID_REUSE` |
| 5 | **Latch.** Effectful commands are refused while the device is latched (CORE-075) | `MHS.SAFETY.ESTOP_ENGAGED` |
| 6 | **Mode, hybrid authority, arming.** A replay device refuses every command; the model may not drive a hardware-authority resource of a hybrid device; hardware actuation needs an armed device | `MHS.MODE.READ_ONLY`, `MHS.SAFETY.ENVELOPE_VIOLATION` (`details.authority`), `MHS.AUTH.HARDWARE_DISABLED` (`details.reason` `not_armed`) |
| 7 | **Structure.** The served schema (binding ∩ class) without the bound keywords of limited fields; configure field rules (CORE-022) | `MHS.CAPABILITY.INPUT_INVALID`, `MHS.RESOURCE.FIELD_UNKNOWN`, `NOT_WRITABLE` |
| 8 | **Limits.** Every element and leaf (CORE-044), then `LIMITS_UNSET` (CORE-046) | `MHS.SAFETY.ENVELOPE_VIOLATION`, `MHS.SAFETY.LIMITS_UNSET` |
| 9 | **Remaining schema bounds** | `MHS.CAPABILITY.INPUT_INVALID` |
| 10 | **Permit**, bound to the exact input digest, then **cumulative budgets** (CORE-047) | `MHS.SAFETY.PERMIT_INVALID`, `APPROVAL_REQUIRED`, `CUMULATIVE_LIMIT` |
| 11 | **Interlocks.** Every gating interlock reads `closed`; `unknown` counts as `open` | `MHS.SAFETY.INTERLOCK_OPEN` |
| 12 | **Device lock, revision, dispatch.** Non-read bindings of hardware and hybrid devices hold the device lock unless the binding declares `constraints.concurrency` `shared`; `expected_revision` is compared with the live revision after the lock and again when the operation is registered; then the bridge call, output validation (strict), the receipt | `MHS.CONFLICT.REVISION`, `MHS.DEVICE.BUSY` |

**CORE-061:** Steps 1 to 11 call the bridge only to read interlock and device state, each read bounded. A command whose `deadline_ms` has passed during the checks is `rejected` with `MHS.OUTCOME.TIMEOUT` (`details.reason` `deadline_exceeded_before_dispatch`, retryable) and nothing is dispatched (OP-012). The effective concurrency of a binding on a hardware or hybrid device is the stricter of its `constraints.concurrency` and the class value (default `exclusive` for non-read bindings; reads are `shared` unless declared `exclusive` or `serialized`; `serialized` holds the device lock); stop classes and `achieved_by` actions never wait for the lock and publish `shared`. Manifests publish the effective value (`exclusive` in device summaries), and the manifest of a simulated device invents none. A request that finds an exclusive device busy is refused `MHS.DEVICE.BUSY` rather than queued, and the device stays busy until the endpoint's own state reads around the command have returned.

## 6. Safety duties of the core and of the bridge

### 6.1 The split

**CORE-070:** The core owns, unconditionally and before any bridge I/O: principals and grants, binding resolution, idempotency, the e-stop latch and its persistence, mode, hybrid authority and arming, structure, limits and budgets, permits, interlock evaluation (fail closed: an unreadable or unrecognised state is `unknown`, which blocks like `open`, SAFE-012), the device lock, revisions, receipts, the evidence chain, cancellation and session expiry. Only the rules CORE-160 lists as strict-only depend on the mode of the endpoint.

| Concern | The core (endpoint runtime) | The bridge or driver |
|---|---|---|
| Limits | Intersects the sources, checks every element and leaf before any native call, refuses with details (CORE-042 to CORE-046) | Declares bounds with a source and a reference; never validates, clamps or relaxes |
| Units | Compares in the declared unit | Converts native units at the boundary |
| E-stop | Latches first, cancels running work, runs the stop path within the budget, persists the latch (CORE-074 to CORE-077) | Provides the native stop; returns promptly; takes no lock a running call holds |
| Cancellation | Requests it on e-stop, session expiry, `operations.cancel` and `max_duration_ms` | Observes it and raises `Cancelled` |
| Interlocks | Reads them, fails closed, refuses (CORE-073) | Reports `closed`, `open` or `unknown` |
| Permits and budgets | Validates, consumes and gives back permits; reserves budgets | Nothing |
| Receipts, revisions, idempotency | Owns them (CORE-090 to CORE-096) | Returns the output or raises a signal |
| Failures | Classifies the signal into a receipt (CORE-071) | Raises `DriverFailed`, `Busy` or `OutcomeUnknown`; never hides a native failure |
| Mode and fidelity | Serves a fake as `simulated`, enforces mode and arming (CORE-111, CORE-153) | Provides an honest fake and a fidelity contract |
| Reference file | Renders it from the effective limits (CORE-030) | Supplies tags and facts, each with a source |

**CORE-071:** A bridge or driver translates and MUST: return the capability output as a JSON-able object, which *is* the receipt output (never an `{"output", "state"}` wrapper); expose state only through `read`; report every outcome that is not a success by raising a signal and never through an output field. The signals are `Cancelled` (the call stopped because cancellation was requested), `DriverFailed(code, message)` (a failure it understands, with a registered code), `Busy` (refused, nothing actuated) and `OutcomeUnknown` (the effect may have happened, for example a native timeout). Any other exception becomes `failed` `MHS.ADAPTER.SHIM_FAILED` with the message `driver raised <Type>`; the native message is never forwarded. A bridge MUST bound every long or awaitable native by the smaller of its `timeout_ms` and the remaining execution budget and observe cancellation; an expired bound is an unknown outcome, never a retryable failure. A bridge MUST NOT clamp, retry an actuation, swallow a native failure, advance a revision, make a receipt, or decide a refusal that belongs to the core. NaN and infinite inputs never reach a native call.

**CORE-072:** A bridge's `estop` MAY be called from another thread while a call runs. It MUST NOT take a lock a running call holds and MUST return promptly. Each `estop` advances the bridge's e-stop epoch before it touches the device; an effectful call that was already waiting for a bridge lock when the e-stop fired is refused `MHS.SAFETY.ESTOP_ENGAGED` once it gets the lock, so no queued actuation follows an e-stop. Calls made after `estop` returned run normally: the latch belongs to the core. `reset`, `interlocks` (`[{id, state, description}]`, state `closed`, `open` or `unknown`; anything else is `unknown`) and `safety_status` are optional hooks that supply facts; the core decides.

**CORE-073:** An interlock has a stable `id`, a description, a `source` (`hardware`, `software`, `operator`, `simulated`) and optionally `required_for`, the capability ids or patterns it gates. When present `required_for` MUST be non-empty: an interlock that gates nothing omits the member and is informative (SAFE-020), and `mhs.safety.status` reports every interlock, gating or not (SAFE-026). A gating interlock that reads `open` or `unknown` refuses the command with `MHS.SAFETY.INTERLOCK_OPEN` and `error.interlocks`. An interlock that opens while an operation runs stops the affected output (SAFE-013). No method sets an interlock (SAFE-027).

### 6.2 E-stop

**CORE-074:** `mhs.safety.estop` and `mhs.command` on a bound `cap.motion.estop.v1` share one path, which latches first (SAFE-040). (1) Under the endpoint lock and before any bridge I/O the core sets the device's latch, persists it when there is a `state_dir`, sets cancellation on every running operation of the device (reason `emergency stop: <reason>`) and revokes the device's permits (SAFE-036). (2) It runs the stop path in a bounded worker: the native stop first (the bridge's `estop`, else a bound `cap.motion.estop.v1`, else none), then every `safe_state.achieved_by` action, which starts no later than the device's e-stop budget `safety.estop.latency_ms` (1000 ms when undeclared) even if the native stop has not answered, then the bridge's own safe-state report. (3) It answers within that budget and never past the caller's `deadline_ms`. The path follows the bindings served at e-stop time; a capability stop path with no binding left is `SAFE_STATE_UNREACHED`. Every `achieved_by` action is called. On the SDK's own ROS call path (the SDK's `RosBridge` itself, or a `RosDriver` whose `call`, `make_bridge`, `inner`, `estop`, `safety_status` and `_run_safe_state` are the SDK's and whose inner bridge is exactly the SDK's `RosBridge`, with none of them shadowed on an instance), a safe-state command whose request (service or action, type, profile, literal request, success predicate, timeout) the native stop or an earlier action of the run already sent and saw confirmed successful is not sent again: it is answered from that request's response and checked against its own output contract, and the receipt lists it in `x-vendor.shared_stop_requests`. After a failed, timed-out or unconfirmed request the command sends its own at once; a request still in flight is awaited until the command's budget is down to its own request's timeout or to half, whichever is less, and the command then sends its own unless that request succeeded. The native stop itself always sends. A background retry (CORE-077) is a new run. Other bridges, packages that override that call path and decorated drivers send every action's request (a native method that the `@estop` method and an action both reach runs twice). A stop of several devices (CORE-076) runs this path once per device, concurrently.

**CORE-075:** While a device is latched, every effectful command and `mhs.restore` is refused with a `rejected` receipt `MHS.SAFETY.ESTOP_ENGAGED`, before schema validation and without a bridge call; the check is repeated atomically when the operation is registered, so a command that passed its pre-checks before the e-stop does not run after it. Exempt are catalogued read classes, the stop classes (`cap.motion.stop.v1`, `cap.motion.estop.v1`) and the `safe_state.achieved_by` actions (SAFE-029), which also skip permits, budgets and the device lock; their schema, limits and interlocks still apply. An extension id is exempt only as an `achieved_by` action, never as a read. Known limitation: an `achieved_by` action that takes input is callable while latched with any input that passes its schema and limits (open item in the 0.9 change notes, `MHS/changes/WP-09.md`).

**CORE-076:** The e-stop needs no session, no prior `mhs.hello`, no valid `deadline_ms`, no ULID `command_id` and no mode. An unknown, expired or missing session gets a transient session; a malformed `command_id` is replaced; a missing or invalid deadline means the device's budget; NaN and infinity in an e-stop request become `null` and the e-stop is still served; an e-stop sent as a JSON-RPC notification still latches. It is never refused by the latch, permits, budgets, rate limits, arming or the generic gates (the `mhs.hello` and `deadline_ms` gates). A request is an e-stop by what it asks for, not by how well its envelope is written: a JSON object whose `method` is exactly `mhs.safety.estop` (or `mhs.command` naming `cap.motion.estop.v1` in object `params`) latches although its `jsonrpc` is not `"2.0"`, its `id` is not a string or an integer, or its `params` are not an object. `params` that cannot be used, and a `device_id` that names no device, are ignored in that case, so the stop covers every device; the defect is recorded in the stop's reason. The answer is still the error of the defect (`MHS.PROTOCOL.INVALID_REQUEST`, or `MHS.PROTOCOL.INVALID_PARAMS` for `params`; `id` null when the id is unusable; no answer to a notification), and its `error.data.details` say whether the stop was served (`estop_served`) and carry its receipt. Text that is not a JSON object with that method (not JSON, an array that does not hold one, a number) cannot be recognised and is refused as before. A well-formed request stops the device it names; else the single device of its session; else the only device of the endpoint; else, on an endpoint that serves several devices, all of them. A stop of several devices engages them concurrently (a stop path that hangs on one never delays the latch of another) and answers with one receipt: the first that is not `completed`, else the first, with `x-vendor.estop` = `{scope: "all_devices", devices: [{device_id, status, receipt_id, safe_state_achieved, error?}]}`. It is `completed` only when every device's stop succeeded (SAFE-002). A `device_id` that is well-formed but unknown is `MHS.DEVICE.UNKNOWN` and stops nothing. Over HTTP with `auth_tokens` configured the e-stop needs the same bearer token as every route (CORE-181): a request without it is refused with 401 before it is decoded, malformed or not.

**CORE-077:** The e-stop receipt is `completed` only when every step succeeded. A timeout, any exception, a failed or unbound safe-state action, the bridge reporting `achieved: false`, or a hardware or hybrid device with no stop path at all gives a `failed` receipt `MHS.SAFETY.SAFE_STATE_UNREACHED` with `details.reason` `timeout`, `native_failed`, `action_failed`, `safe_state_unbound`, `no_stop_path`, `bridge_reports_unsafe` or `command_in_flight` (CORE-086); the latch stays engaged. `mhs.safety.estop` never answers `MHS.OUTCOME.TIMEOUT`. A retryable failure is retried in the background (0.25 s doubling to 5 s) until the stop path succeeds or the device is reset; the success is appended as a `completed` `cap.internal.safety_estop.v1` receipt whose `output.confirms` names the failed one. `estop.confirmed` in `safety.status` means the current attempt of this latch generation succeeded. A sensed-confirmation stop (CORE-088) adds no reason: its unconfirmed outcome is `bridge_reports_unsafe` (or `timeout`, or `native_failed`) with `details.sensed` saying why, and its completed receipts carry `x-vendor.sensed_confirmation`. On a simulated or replay device with no native stop, the software-only latch is `completed` (`output.estop` `software_only`). The receipt carries `latency_ms`, `latch_latency_ms`, `safe_state_achieved` and `cancelled_operations`, and never claims more than the declared safe state (SAFE-044).

**CORE-078:** Cancellation by an e-stop is cooperative: a cancellable operation ends `cancelled`; stop-class and `achieved_by` operations are never cancelled. An effectful operation that ignores cancellation keeps running (logged) and blocks the reset (`operation_running`).

**CORE-079:** A stdio or MCP reader handles the e-stop and `operations.cancel` before it reads the next line, on a priority path that answers while another request is in flight (CORE-132); other requests are served in order, per device lane.

### 6.3 Reset

**CORE-080:** `mhs.safety.reset` is refused with a `rejected` receipt `MHS.SAFETY.RESET_REFUSED`, without calling the bridge and with the latch kept, when: nothing is latched (`details.reason` `not_latched`; "latched" means the endpoint latch, or a latch the device reports through `safety_status()` `latched` or `estop.engaged`, or a boolean `latched` state field); an effectful operation that ignored cancellation is still running (`operation_running`); any declared interlock not marked `reset_exempt` reads `open` or `unknown`, an unreported or unreadable one included (`interlock_open`, with `error.interlocks`); a native e-stop attempt of the device is still in flight (`stop_path_pending`; there is no operator override, and a bridge whose `estop` never returns keeps the device latched until restart) (SAFE-003, SAFE-041, SAFE-043). It is also refused, in the same way, after the endpoint started the stop path of a declared terminal e-stop (`terminal_estop`, CORE-087).

**CORE-081:** The latch is released only when no e-stop was engaged during the reset and no stop attempt is running. A bridge refusal becomes `RESET_REFUSED` (`bridge_refused`, `bridge_code`) and a non-MHS exception a `failed` receipt, both with the latch kept. A refusal after `bridge.reset()` ran is a `failed` `RESET_REFUSED` receipt (`details.latched: true`, `bridge_reset` `completed`) and advances the revision: `estop_during_reset` (the stop path is re-asserted, `details.stop_reasserted`) and `stop_path_pending`. A reset whose caller was answered `TIMEOUT` before the handler reached `bridge.reset()` is not performed: `failed`, `MHS.OUTCOME.TIMEOUT`, `details.reason` `deadline_exceeded`, `bridge_reset` `not_called`. While a reset runs, the background retry of a failed stop does not start a new attempt, at most until that reset's deadline; an e-stop engaged during the reset lifts that hold.

**CORE-082:** A completed reset clears and persists the latch, ends the background retry and never resumes anything (`output.resumed: false`); a new command is required (SAFE-042). On a device that declares a re-enable, that command is the re-enable, and `output.reenable` names it (CORE-086). `mhs.restore` is refused `ESTOP_ENGAGED` while latched, is re-checked after its rollback read, and an e-stop landing during it re-asserts the stop path afterwards.

**CORE-083:** Only an operator releases a hardware latch. On a hardware or hybrid device, `mhs.safety.reset` from a session that is not an authenticated `operator` is refused `MHS.AUTH.FORBIDDEN` (`details.reason` `operator_required`, bridge not called) in strict mode; the CLI `reset` needs the operator token and an interactive terminal, and the MCP projection does not list the tool (CORE-130). On simulated devices an agent may reset.

**CORE-086:** A device whose stop leaves it disabled MAY declare `safety.estop.reenable`: the capability that re-enables it after a completed reset, the new start command of SAFE-042. The named capability MUST be bound to exactly one resource of the device and MUST accept an empty input (the empty object validates against its input schema), and it MUST NOT be a read, a stop class or a `safe_state.achieved_by` action; an endpoint refuses to start a device whose declaration breaks this, in every mode, and refuses a device with such a declaration that was added after start on its first use (`MHS.ADAPTER.MANIFEST_INVALID`, `details.reason` `estop_recovery_invalid`; the e-stop still reaches it). The re-enable is an ordinary effectful command: while the device is latched it is refused `MHS.SAFETY.ESTOP_ENGAGED` (CORE-075), and arming, permits, limits and interlocks apply to it. A reset of such a device only releases the latch: neither `mhs.safety.reset` nor the bridge's reset runs the re-enable or re-arms the device by any other means, any native recovery it needs (fault clearing included) belongs in the re-enable, and a completed reset names it in `output.reenable`. The SDK enforces what it can see, at definition and at start-up: a decorated driver that declares a re-enable MUST NOT define an `@reset` hook, and a family driver's `safety_bindings.reset` MUST NOT call the re-enable's native target (the target members of both entries, compared exactly as declared). A family reset binding that re-arms the device through another target, or through the same one spelled differently, is not detected: avoiding it is the author's obligation, checked by review. On such a device, a command already dispatched when an e-stop lands may land after the native stop and enable the device again (the re-enable itself, or an upstream cancel path that re-arms after its own quick-stop). The stop path therefore runs at once, waits for every effectful command of the device still in flight then (stop, safe-state and read actions excepted, reads as the latch counts them) to settle, and runs again; until that second run succeeds the e-stop is not confirmed (a `failed` receipt `MHS.SAFETY.SAFE_STATE_UNREACHED`, retried in the background as CORE-077 describes; `details.reason` is `command_in_flight`, with `details.awaiting_operations` listing them, while one of those commands has not settled, and `timeout` once they all have and the stop that follows has not answered). The wait for a command ends when it settles or when its worker is gone without settling (it can no longer reach the device). A device that declares none keeps the single run of the stop path and needs no separate re-enable: its next ordinary command is the new start command.

**CORE-087:** A device whose native stop cannot be undone without a new native session MUST declare `safety.estop.terminal`, one sentence that says why, and its reset MUST NOT reopen or reinitialise it (SAFE-048). A new native session is any reconnection, reopening or re-initialisation that may change the device: energise it, enable motion, or start a process that may initialise hardware. Re-establishing communication that changes nothing on the device (reconnecting a socket, re-attaching a client object, reopening a handle) is not one, and a reset MAY do it (SAFE-042). The declaration needs a stop path (a native e-stop or a `safe_state.achieved_by` action) and excludes `reenable`; an endpoint refuses to start a device whose declaration breaks this, in every mode. Once the endpoint starts the stop path of such a device, every later `mhs.safety.reset` of the device on that endpoint is refused with a `rejected` receipt `MHS.SAFETY.RESET_REFUSED` (`details.reason` `terminal_estop`, `details.terminal` the declared sentence, `details.latched` true, and a `remediation`), without calling the bridge, and the latch is kept for the rest of the endpoint's life; a reset during whose bridge reset such a stop path starts never releases the latch either (a `failed` refusal, `estop_during_reset` or `terminal_estop`, CORE-081). `mhs.safety.status` then reports `estop.terminated: true`. The latch, the refusals of CORE-075 and the background retry of CORE-077 are unchanged. Recovery is a new endpoint: a latch that it restores from `state_dir` (CORE-171) is reset as usual, by an operator on a hardware device (CORE-083), until a stop path starts on that endpoint, including the rerun that a replay of the latching e-stop's `command_id` causes (CORE-171); from then on that endpoint refuses the device's resets too.

**CORE-088:** A device of mode `simulated` whose only stop is a request (a land, mode, zero-velocity or motor-cut request whose acknowledgement proves nothing) MAY declare a sensed-confirmation stop, published as `safety.estop.confirmation` (`kind` `sensed`, SAFE-049); a device of any other mode MUST NOT, and an endpoint refuses to start one that does, in every mode (`MHS.ADAPTER.MANIFEST_INVALID`, `details.reason` `sensed_stop_not_simulated`), and refuses a late one on first use (the e-stop still reaches it). What the endpoint serves grants the stop, never a value its constructor was given: a confirmation commits a safe state only on the SDK's own ROS bridge after the endpoint bound it to a device whose served manifest declares mode `simulated` and the confirmation (at start-up, or on first use of a late device), and only on the SDK's route (a RosDriver that overrides none of `call`, `make_bridge`, `inner`, `estop`, `safety_status`, `_run_safe_state`, and whose instance builds no bridge of its own); an unbound bridge still sends the request but never confirms. The bridge's `estop` sends the declared request steps (one to three fixed service calls with their success predicate, or fixed topic publications; each MUST be idempotent: repeating it after the safe state was reached undoes nothing) on its safety lane, where they are not fenced by the latch or the e-stop epoch and count as no native activity; every step is attempted and its outcome (`succeeded`, `refused`, `unknown`, `published`, `not_sent`) recorded, and at least one must have been transmitted. It then opens new subscriptions to one to three sources, discards what each may have received from before it existed (on ROS 1 the bridge has no proven offset between the producer clock and its wall clock, so a producer stamp is not a freshness proof: every ROS 1 stamp sample is discarded and does not refresh counted freshness, including a stamp one second ahead, a ROS simulation clock, a delayed latch, a frame already in a client buffer, and a sample from a transport that cannot report its buffer; an empty queue, a socket poll, a client library buffer, a continuation flag, and a fixed lead are not that proof; on ROS 2 the publisher's declared history, `volatile` or `transient_local` with its depth, cited or operator-supplied and never lower than a cited one, and at least one sample), numbered by arrival before any is dropped. A stamp source then counts samples with strictly increasing producer stamps. A ROS 2 source whose producer does not stamp may instead declare freshness `arrival` with a cited volatile history and `min_interval_ms` (1 to 1000): the first sample is discarded, a later sample closer than `min_interval_ms` restarts the count, and the window's span is arrival time; transient-local history and ROS 1 are refused for that freshness, because a replay spaced at least `min_interval_ms` apart cannot be told from live samples without a stamp. Counted samples are those whose every predicate term holds (`equals`, `range`, `abs_max`, `norm_max`, `span_max` over the window); a repeated stamp, an arrival gap above `max_gap_ms` measured from the newest counted sample, or a failing term restarts the count, and a discarded replay does not advance that arrival, and a missing, malformed, zero or decreasing stamp, or a missing, non-numeric or mistyped field, ends the attempt. When the declaration names an exclusion on a request topic, silence, a subscription error, a sample whose watched fields are not all zero, and a sample the exclusion ring drops each refuse the confirmation. A dropped sample was not inspected, so the tail that remains is not a passive command. Only a passive sample observed on that subscription after it opened, and still fresh at the commit, is evidence the competing command is absent. The safe state is committed, and `estop` returns `safe_state_achieved: true`, only when that exclusion rule holds and every source holds `consecutive` (at least 2) counted samples spanning `min_span_ms` of producer time (arrival time when freshness is `arrival`) whose newest arrived within `max_gap_ms`, before `confirm_within_ms` after the first transmission and the caller's deadline, with no native activity, new e-stop epoch, disconnect or close in between; otherwise it returns unachieved with `confirmation.reason` `request_not_sent`, `sensed_missing`, `sensed_stale`, `sensed_invalid`, `not_confirmed`, `superseded` (a closed bridge or a lost connection included) or `not_simulated` (the bridge is not bound), and never raises for an unconfirmed outcome. `safety_status` reports the committed confirmation of the current attempt only (`safe_state.confirmation`), withdrawn by any later native activity, epoch, disconnect or close. The core is unchanged (CORE-074, CORE-077): the latch is set first; a failed e-stop carries `details.sensed`, and a completed e-stop or background confirmation `x-vendor.sensed_confirmation`, both copied only from the SDK's own ROS route (CORE-074); the background retry sends the request again. A reset of such a device first re-confirms read-only (new subscriptions, no request, no re-enable) and is refused (`bridge_refused`, latch kept) when the sensed state no longer holds; it never resumes anything (SAFE-042). Thresholds are cited or operator-supplied (the operator's are narrow-only against a cited value), and so is each ROS 2 source's history (the operator's may only raise a cited replay); `consecutive`, `min_span_ms`, `max_gap_ms`, `confirm_within_ms`, `throttle_ms` and the request timeouts are client execution bounds that can only withhold a confirmation; `safety.estop.latency_ms` covers the request timeouts plus `confirm_within_ms`. A stop that only a new native session undoes also declares `safety.estop.terminal` (CORE-087).

### 6.4 Permits, sessions and expiry

**CORE-084:** A permit is single-use, bound to the exact input digest, binding, session and principal, and expires (SAFE-030 to SAFE-036). In strict mode a permit on a hardware (or hybrid, hardware-authority) device at R2 or above needs the endpoint's `approval_verifier`; without one it fails closed with `MHS.SAFETY.APPROVAL_REQUIRED`. A permit consumed by a command that is then refused before dispatch (a revision conflict, an expired deadline) is given back, unless an e-stop revoked it. A model must not be able to approve its own permit: the MCP projection hides the permit and reset tools unless an operator enables them (CORE-130), and a host collects approvals through an operator route (HOST-040 to HOST-047).

**CORE-085:** On session expiry or close the core cancels the session's running operations (stop and `achieved_by` operations excepted), releases its permits and subscriptions, and runs the `safe_state.achieved_by` actions of every device that was running one of its effectful operations (SESS-004, SESS-006, SESS-010). Expiry relies on cooperative cancellation plus `safe_state.achieved_by`: a device without `achieved_by` whose bridge ignores cancellation keeps running (this is logged). The session record stays, so later use, a heartbeat included, gets `MHS.SESSION.EXPIRED`.

## 7. Receipts, idempotency, revisions and long-running work

**CORE-090:** Every mutation carries a client-chosen `command_id` (a ULID). The idempotency scope is `(endpoint_id, device_id, command_id)` and the digest is `input_digest = sha256(JCS({capability_id, resource, input}))` (PROTO-036, OP-006). A retry with the same digest returns the retained receipt with `replayed: true` and does not run again (OP-003); another digest is a `rejected` receipt `MHS.CONFLICT.COMMAND_ID_REUSE` that leaves the retained receipt untouched (OP-004). A rejected attempt is never the command's recorded outcome (OP-005); only the command's own non-rejected receipt with the same digest settles it. A replay of a command that is still running returns the live state of the operation.

**CORE-091:** A receipt's `status` is `accepted`, `running`, `completed`, `failed`, `rejected`, `cancelled` or `unknown`. At most one execution ever runs for a `command_id`, and it has exactly one **final** receipt, `completed`, `failed` or `cancelled`: the retained outcome that replays return. A `rejected` receipt records a refusal before any effect; it is chained as evidence but is not the outcome, does not reserve the `command_id` (a corrected retry with the same id may run) and leaves the revision unchanged. `accepted` and `running` are not evidence. `unknown` is the answer when the outcome cannot be observed in time or the response is lost: the execution's final receipt reconciles it later (`x-vendor.reconciles` `{receipt_id, status, mhs_code}`), and where nothing can (an endpoint restart, CORE-172) the `unknown` receipt stays the outcome. A client MUST read state before acting on an `unknown` outcome and MUST NOT retry it blindly (OP-013, OP-014, SAFE-055). An endpoint MUST NOT report `completed` for an effect it did not observe.

**CORE-092:** Every final receipt, `rejected` ones included, is appended to the evidence chain before it is returned (PROTO-029, EVID-010, EVID-012). Receipts follow the signal rules of CORE-071; a failure in the endpoint's own post-call code is `failed` `MHS.INTERNAL.ERROR` with the exception type only. A `mhs.command` input with no canonical JSON form (an integer beyond 2^53−1) is `MHS.CAPABILITY.INPUT_INVALID` (`details.reason` `not_canonical_json`) and is never dispatched (the e-stop excepted: it latches with a placeholder digest). NaN and infinity in an output become `null` and are listed in `x-vendor.non_finite_output`.

**CORE-093:** The `result` of `mhs.command`, `mhs.resource.write`, `mhs.restore`, `mhs.operations.get`, `mhs.operations.cancel`, `mhs.safety.estop` and `mhs.safety.reset` is the receipt object itself, validated by `receipt.schema.json`, with no `{"receipt": ...}` wrapper. Method-specific data lives in `output`: the e-stop's `output` has `estop`, `latched`, `latency_ms`, `latch_latency_ms`, `safe_state_achieved`, `safe_state` and `cancelled_operations` (CORE-077), and the reset's has `reset`, `estop`, `latched`, `cleared_interlocks` and `resumed` (CORE-082), and `reenable` when the device declares one (CORE-086). Internal methods use the receipt `capability_id` values `cap.device.configure.v1`, `cap.internal.restore.v1`, `cap.internal.safety_estop.v1`, `cap.internal.safety_reset.v1` and `cap.internal.operation_cancel.v1` (PROTO-038).

**CORE-095:** The device revision advances only when the device's state hash changed. Reads, every `rejected` receipt, `safety.status`, evidence, `operations.get` and session calls never advance it. A catalogued read class never advances it. For any other outcome (`completed`, `failed`, `cancelled`, `unknown`) the revision advances by one when the state hash differs before and after the call, or when it cannot be computed (an unreadable or unanswered state read counts as a change: fail closed). Stop classes and `achieved_by` actions, e-stops, restores and completed resets advance it whenever they run; a `failed` `RESET_REFUSED` after `bridge.reset()` ran advances it too (CORE-081). This restates OP-007 to OP-009: one advance per command, never for a read.

**CORE-096:** `expected_revision` is an integer (a boolean is not a revision). It is compared with the live revision after the device lock is taken and once more when the operation is registered; a mismatch is a `rejected` receipt `MHS.CONFLICT.REVISION` with `current_revision` recomputed at refusal time, and a permit it had consumed is given back. Every `rejected` receipt reports the true current revision.

**CORE-100:** `deadline_ms` bounds only the wait for the response, counted from the request's ingress; it never cancels or shortens an execution. Execution is bounded by `max_duration_ms`, taken from the binding's `constraints` and else from its class, counted from dispatch; that bound, not the response deadline, is the bridge's budget. A `long_running` binding (`constraints.long_running` or the class flag) whose deadline passes answers the current non-terminal receipt: `status` `running`, `operation_id`, `x-vendor {long_running, deadline_ms, max_duration_ms}`; the command keeps running, bounded by `max_duration_ms` (600000 ms when neither binding nor class declares one, and strict mode refuses a `long_running` binding with no bound). Any other command whose deadline passes answers `unknown` with `MHS.OUTCOME.TIMEOUT`, `retryable: false`, `details.reason` `deadline_exceeded` or `max_duration_exceeded`, and keeps running. This is the single rule behind PROTO-011 and OP-010, and a refusal before dispatch is OP-012 (CORE-061).

**CORE-101:** When `max_duration_ms` ends the wait before the deadline does, a cancellable command is asked to stop (`cancellation.reason` `max_duration_ms exceeded`): if it stops within a 0.25 s grace the caller receives `cancelled`, otherwise `unknown` with `max_duration_exceeded`. After the caller has been answered, a timer does the same at the bound and records `unknown` for a long-running command whose caller holds only a `running` receipt (SAFE-017).

**CORE-102:** The `unknown` receipt is recorded under a claim before the worker's final receipt, which then carries `x-vendor.reconciles` and replaces the stored receipt, so `operations.get` and a replay return it. Until then `operations.get`, `operations.list` and a replay report the operation's live `running` receipt (`x-vendor.unknown_receipt_id`). A late `Busy` instead frees the `command_id`.

**CORE-103:** A blocking method needs an integer `deadline_ms` of at least 1 (PROTO-010) and the endpoint caps it at `hello.limits.max_command_deadline_ms` (600000). A read that exceeds its budget fails with a structured timeout; `restore` and `safety.reset` answer a truthful timeout or `unknown` carrying the pre-assigned `command_id`, and never report a late success. The e-stop is exempt (CORE-076).

## 8. Modes and the rule against silent simulation

**CORE-110:** A device serves exactly one `mode` (`hardware`, `simulated`, `hybrid`, `replay`) and never changes it at runtime (MODE-002, MODE-003). A session requests the device's own mode; a mismatch is `MHS.SESSION.MODE_MISMATCH` and is never resolved by falling back (SESS-002). The mode is reported by the manifest, `hello`, `safety.status`, the session and every receipt (MODE-004), and by the reference file and every surface that lists a device.

**CORE-111:** Nothing that is not the real device may present itself as the real device. A fake or simulator backend of a hardware driver is served as `mode` `simulated` under the id `<hardware id>/<backend>` with a fidelity contract (F0 for a fake) and honest `gaps` (FID-001, FID-041, FID-045); it never answers under the hardware id. The backend names are `hardware`, `fake` and `sim`, and only `hardware` drives the device. A bridge MUST NOT substitute a simulation when hardware is unavailable; the endpoint fails instead (FID-049). Evidence from a fake or simulator is `contract_checked` and never a device-level conformance claim (CORE-191).

**CORE-112:** A hybrid device declares per resource which side is truth (`fidelity.authority`, MODE-006). The model may not drive a hardware-authority resource of a hybrid device: the command is refused with `MHS.SAFETY.ENVELOPE_VIOLATION` (`details.authority` `hardware`) and only a catalogued read class may touch it. Hybrid safety follows the stricter side (FID-034).

**CORE-113:** A replay device is read-only: every command is a pre-effect `rejected` receipt `MHS.MODE.READ_ONLY` and replay endpoints advertise `replay.seek` (MODE-005, FID-022, FID-024). The twin rule and the fidelity contract are the Sim/Fidelity/Replay profile ([profiles.md](profiles.md) §3).

## 9. Discovery

**CORE-120:** An HTTP endpoint serves its descriptor at `GET /.well-known/mhs.json` (`endpoint-descriptor.schema.json`) without authentication; the descriptor advertises `auth` (`["bearer"]` when tokens are configured, else `["none"]`) and the endpoint's honest `transports` and `features` (TPT-002). A stdio endpoint is found through its launch command.

**CORE-121:** A client finds endpoints from two configured sources: the environment variable `MHS_ENDPOINTS` (comma-separated: `http://host:port`, `mhs://host:port`, whose port defaults to 7400, and `stdio:<command>`, whose words are separated by spaces and which is listed but never launched by discovery) and the endpoints file `~/.mhs/endpoints.json` (or `$MHS_ENDPOINTS_FILE`), validated against `endpoints.schema.json`. `mhs discover` probes every HTTP entry.

**CORE-122:** Discovered does not mean trusted. Discovery authenticates nothing: every entry is reported `trusted: false`, an invalid endpoints file is a usage error, and a discovered endpoint receives only the `token_file` of its own entry, never a token given for another endpoint. Two discovered endpoints that list one device id make that name ambiguous (`MHS.HOST.DEVICE_AMBIGUOUS`). `mhs.registry.search` is not an endpoint method; a registry result is never a controllable device before authentication (PROTO-039).

## 10. The control surfaces

The MCP projection, the `mhs` command line and code files are generated from the same reference file and are thin clients: each holds only the authority of the session it opens, and the endpoint enforces every limit, interlock, permit and e-stop rule whatever surface called.

### 10.1 MCP projection (reference: `mhs.mcp`)

**CORE-130:** The projection exposes one tool per binding, `mhs__<device_slug>__<capability_slug>` (TPT-030), and the fixed tools `mhs__devices`, `mhs__inspect`, `mhs__read`, `mhs__safety`, `mhs__operations`, `mhs__evidence` and `mhs__estop`. The tools `mhs__reset` and `mhs__permit` are listed and callable only when the operator enables `operator_tools`, in every mode; otherwise they refuse `MHS.AUTH.FORBIDDEN` (`policy` `operator_tools=false`). The host policy has four flags, `enabled`, `allow_hardware`, `operator_tools` and `allow_external_sessions`; without a policy document the projection is enabled and every other flag is false, and with one a flag is true only when it is the JSON value `true`. `enabled` false refuses every call with `MHS.AUTH.FORBIDDEN`; `allow_hardware` false refuses capability tools, `mhs__read` and `mhs__operations` on hardware devices with `MHS.AUTH.HARDWARE_DISABLED`, while discovery, `mhs__safety`, `mhs__estop` and `mhs__evidence` stay available.

**CORE-131:** `tools/call` is exactly one `mhs.command`. A receipt of any status is a successful call (`isError` false, `structuredContent.receipt`, the full receipt also in the first text block); `isError` is true only when no receipt exists: a policy refusal, a lapsed session, a transport failure, or an `arguments` object that does not match the input schema (`MHS.CAPABILITY.INPUT_INVALID`, nothing sent) (TPT-038, TPT-039). A value outside an enforced limit is sent and answered by a `rejected` receipt `ENVELOPE_VIOLATION`, kept in the evidence; the projection describes limits but the endpoint enforces them. The optional control fields are `session_id`, `command_id`, `expected_revision`, `permit_id` and `deadline_ms` (TPT-033).

**CORE-132:** The projection never trusts the model's `session_id`: it refuses one it did not open with `MHS.SESSION.UNKNOWN` unless `allow_external_sessions` is set. It opens its own sessions with the principal `{kind: agent, id: agent:mcp/<clientInfo.name>}`, sends a heartbeat before a call when less than a third of the TTL is left, and opens a new session after `EXPIRED`, `UNKNOWN` or `CLOSED`; reads are retried once on the new session, commands never. A `_meta.retryToken`, or a `command_id` that is not a ULID, maps deterministically to the ULID formed from the first 16 bytes of `sha256(tool_name + "\n" + token)`, so a retry replays instead of acting twice (the mapping is scoped by tool name only, a known limitation; open item in the 0.9 change notes, `MHS/changes/WP-09.md`). `mhs__estop`, `ping` and `notifications/cancelled` are served on a priority path while a `tools/call` is in flight. Frames are at most 4 MiB, and the projection answers the requested MCP protocol version when it is one of `2024-11-05`, `2025-03-26`, `2025-06-18` and `2025-11-25`, otherwise `2025-11-25`.

**CORE-133:** A tool description is at most 2048 bytes and is generated from `mhs.devices.get`: mode, risk class, the enforced limits, the interlocks the call needs, the permit requirement, long-running behaviour and the facts of the reference file. Tools carry the annotations `readOnlyHint` (read verbs), `destructiveHint` (non-read calls on R2/R3 or hardware and hybrid devices), `idempotentHint` and `openWorldHint` (hardware and hybrid), and `x-mhs` with the capability metadata. Tool names are stable across restarts; a slug collision fails closed (TPT-032).

### 10.2 Command line (reference: `mhs.cli`)

**CORE-136:** The `mhs` command (`python3 -m mhs`, `mhs`, `openmhs`) provides: `serve <dir|adapter.json|reference fixture>` (`--stdio`, `--port`, `--mcp`, `--backend fake|sim|hardware`, `--allow-hardware`, `--arm`, `--state-dir`, `--site-limits`, `--token-file`, `--operator-token-file`), `driver check|reference|new|export|catalog`, `validate`, `devices`, `describe` (alias `inspect`), `hello`, `read`, `write`, `call`, `session`, `estop`, `status`, `reset`, `evidence`, `run`, `discover`, `conform`, `registry` and `version`. `serve` always loads in strict mode and defaults to the fake backend; only `--backend hardware` drives a device, and it needs `--allow-hardware` and `--state-dir` (CORE-154). `--json` is the machine contract; human output may change. `estop` needs no session and no mode and stops every device unless `--device` is given; `reset` needs the operator token file and an interactive terminal and sends nothing otherwise; `describe` prints mode, risk, trust, e-stop, safe state, interlocks, verbs, effective limits, fidelity gaps and facts.

**CORE-137:** Exit codes are one table for every command: `0` success (a `completed` receipt, or `accepted`/`running` work); `1` the command ran but was refused or failed (a `rejected`, `failed`, `cancelled` or `unknown` receipt, any other endpoint error such as `MHS.DEVICE.UNKNOWN`, an invalid document); `2` usage error; `3` transport error (the endpoint cannot be reached, or the response was lost: `MHS.OUTCOME.TIMEOUT`, `MHS.OUTCOME.UNKNOWN`); `4` authentication or authorisation (`MHS.AUTH.*`, a `reset` without an interactive operator, a hardware backend without `--allow-hardware`); `5` `conform` did not reach the required level; `130` interrupted. A receipt maps to 0 or 1 by its status whatever its error code, except a refusal whose code is `MHS.AUTH.*`, which is 4. A multi-device `estop` exits 0 only when every device has a `completed` receipt and otherwise with the code all failures share (3 or 4), else 1. TPT-052 states the same table.

### 10.3 Code files (reference: `mhs.run`)

**CORE-140:** A code file is a plain Python script run by `mhs run`. `mhs.run.lab(*targets, check=True, ledger=True, mode=None, ttl_s=600, token=None, principal=None)` connects to each endpoint once and gives every device its own handle and session, opened in the device's own mode. With `check=True`, the default, any receipt other than `completed` (or work still `running`) raises `MHSRejected`; this is the one exception to TPT-055, and `check=False` returns the receipts. A code file has no more authority than the same calls made one by one, never retries a physical command, and never resets a latch: `bench.estop(reason)` stops every device, tries all of them even if one fails, and raises with `data["errors"]` and `data["receipts"]`. `token` is sent only to the endpoints named in the call.

**CORE-141:** Every run writes a ledger, `.mhs-run/<run id>.json` (`ledger_version` 1, a ULID `run_id`, `script_sha256`, `endpoints[]`, `receipts[]`, `lost[]`, `outcome`, `error`, `exit_code`, `sdk`). The ledger is checked against the endpoint's own evidence (`mhs evidence --ledger`, `mhs.run.verify_ledger`): the hash chain must verify and every ledger receipt of that endpoint must be in it with the same command id, device, capability and status; the check fails (`valid: false`) with `chain_invalid`, `missing_receipts`, `mismatched_receipts`, `endpoint_not_in_ledger` or `no_receipts_for_endpoint`.

## 11. Principals, authentication and arming

**CORE-150:** The principal of a request is the principal of its bearer token: `auth_tokens` maps a token to `{id, kind}` with `kind` `human`, `agent`, `service` or `operator`, compared in constant time against every token; on the wire an operator is `kind: "human"` with `x-meta.role: "operator"`. `session.open` with a token records the token's principal (`x-meta.authenticated: true`, a different `params.principal` kept as `x-meta.claimed_principal`) and the session is usable only by requests with that principal; any other caller sees `MHS.SESSION.UNKNOWN` (the SSE stream: 403). The members `x-meta.authenticated`, `role` and `claimed_principal` belong to the endpoint: a caller's are dropped, and a principal without `authenticated` is unauthenticated. Without a token a strict endpoint records a self-declared `human` or `operator` as an `agent` with `x-meta.claimed_principal`; a compatibility endpoint keeps it and warns once per principal (SESS-007, SAFE-061).

**CORE-151:** An operation belongs to its principal `(id, kind, authenticated)`. In strict mode `operations.get`, `list` and `cancel` hide another principal's operations as `MHS.OPERATION.UNKNOWN` (PROTO-031).

**CORE-152:** HTTP serves only loopback without tokens. A non-loopback bind (anything but `localhost`, `127.0.0.0/8` and `::1`; wildcards included) without `auth_tokens` is refused with `MHS.AUTH.TRANSPORT_INSECURE` unless `insecure_dev=True`, which warns. Over stdio the process that holds the pipe is the principal (SAFE-060, TPT-013).

**CORE-153:** Hardware actuation, a non-read and non-stop command on a `hardware` device, needs the device to be armed; otherwise it is a `rejected` receipt `MHS.AUTH.HARDWARE_DISABLED` (`details.reason` `not_armed`) with no bridge call. Arming exempts reads and stop classes only; a `safe_state.achieved_by` action is exempt from the latch (CORE-075) but not from arming, and the e-stop path runs those actions itself whatever the arming. `armed` unset arms nothing in strict mode and every device (warned) in compatibility mode; an explicit `False` or a list of device ids holds in both. Arming is an operator decision (`mhs serve --arm`, `MHSServer(armed=...)`).

**CORE-154:** A hardware backend starts only on an explicit operator decision: `allow_hardware`, a `state_dir` (so the latch and the journal survive a restart), and, for a model-authored driver at R2 or above, a human `reviewed_by` (DRV-040). The loader refuses otherwise (`LoadError.reason` `hardware_not_allowed`, `state_dir_required`, `review_required`).

## 12. Strict and compatibility mode

**CORE-160:** `MHSServer(strict=...)` takes `None` or `False` (compatibility mode, the 0.9 default of the bare constructor; the default flips after the pilot) or `True` (strict). `mhs.adapter.load`, `mhs.driver.build_server` and `mhs serve <dir>` are always strict, and passing `strict` to `load` is a `TypeError`. A device is strict when the server or the device says so. The following hold in both modes: the e-stop and reset rules (CORE-074 to CORE-083, CORE-086, CORE-087 and CORE-088), element-wise limits and their intersection, every load-time limit error (CORE-043), `LIMITS_UNSET` for `operator_required` paths, full ULIDs, the HTTP rules (CORE-180 to CORE-185), `schema.get` of shipped schemas only, SSE ownership, session expiry, persistence, strict JSON decoding, refusal of a duplicate `(capability_id, resource)` pair, and the non-finite output rule. Strict-only: catalogue resolution of every binding (unknown ids, drift, `KIND_MISMATCH`, the risk floor, the class verb, the class `requires_permit` flag), binding ∩ class schemas, output validation, the no-limit form of `LIMITS_UNSET`, SAFE-045, the approval verifier for hardware permits at R2 and above, operator-only hardware reset, default-off arming, the downgrade of unauthenticated self-declared principals, and the hiding of other principals' operations.

**CORE-161:** Each static finding (`unknown-capability`, `schema-drift`, `verb-differs`, `kind-mismatch`, `risk-floor`, `achieved-by-unbound`, `required-for-empty`, `required-for-unbound`, `interlock-invalid`, `limits-invalid`, `envelope-unbound`, `SAFE-045`, the `fidelity-*` findings, `constraints-invalid`, ...) is a refusal in strict mode: construction raises `MHSStrictError` with every refusing finding (`.findings`, `.codes`, `.rules`). In compatibility mode each is an `MHSStrictWarning` listed in `MHSServer.strict_findings`, a risk class below the class floor is raised to the floor, a call to a drifting binding whose input the class schema refuses warns once per capability, and the 0.9 behaviour is otherwise kept. SAFE-045 covers hybrid devices as well as hardware devices. Endpoint-configuration findings (`hardware-armed-implicitly`, `approval-verifier-missing`, `operator-token-missing`) are never refusals.

## 13. Persistence

**CORE-170:** With `MHSServer(state_dir=...)` the endpoint keeps, in that directory, `evidence.jsonl` (the chain), `latch.json` (`openmhs.state.latch/1`), `journal.jsonl` (`openmhs.state.journal/1`: the idempotency index, write-ahead `begin`/`end` records, cumulative `draw`/`release` records and a header with the revisions reached) and a POSIX `lock`: one endpoint process uses a directory at a time. A directory that is in use, belongs to another endpoint, or whose evidence or journal cannot be trusted refuses the start (`StateDirError`). `hello.limits.receipt_store` is `state_dir`, or `memory` without one, and then the latch, the idempotency store and the revisions are lost on restart.

**CORE-171:** `latch.json` is replaced atomically and fsynced under the endpoint lock, before any bridge I/O, by every e-stop and every completed reset (SAFE-065). A failed write never stops the latch; it is reported in the e-stop's `output.latch_persisted` and in `safety.status` `estop.persisted`. On start a latched device stays latched, including one the endpoint does not serve now, and `safety.status` shows `estop.restored: true` and `estop.confirmed: false` until the next e-stop, or a replay of the latching e-stop's `command_id`, runs the stop path again. The latch after a restart is `latch.json` or the evidence (the last engaging e-stop receipt with no later completed reset); a missing latch file next to receipts, and a latch file that cannot be read, fail latched. In the unreadable case every served device and every device in the evidence starts latched, the bytes are kept as `latch.json.unreadable-<ULID>` and each device is released only through `mhs.safety.reset`.

**CORE-172:** A completed command id replays its receipt byte for byte after a restart, with zero bridge calls. A command that was in flight when the process died gets an `unknown` receipt (`MHS.OUTCOME.UNKNOWN`, `retryable: false`, `details.reason` `endpoint_restarted`, with `lost_receipt_id` when the journal kept a receipt the evidence lost) and is not run again (OP-006). An effectful command whose write-ahead record cannot be written is refused before any bridge I/O with `MHS.INTERNAL.ERROR` (`details.reason` `journal_write_failed`); reads, stop classes and safe-state actions are not.

**CORE-173:** Revisions continue above the highest any previous run reached, so no pre-restart revision is current again and a stale `expected_revision` is `MHS.CONFLICT.REVISION`. A final line of the evidence log that a crash cut short is moved aside (`<path>.torn-<ULID>`, warned); damage anywhere else fails verification and refuses the start.

## 14. Transport rules that hold in every mode

**CORE-180:** Every HTTP route checks the `Host` header: it must name `localhost`, `127.0.0.1`, `[::1]`, the bound address or an `allowed_hosts` entry (case-insensitive, port ignored, a missing header refused), else 403 `MHS.AUTH.FORBIDDEN`. An `Origin` header, when present, must be the endpoint's own loopback origin (same port) or an `allowed_origins` entry (`null` is refused), else 403.

**CORE-181:** With `auth_tokens` configured, every route except `/.well-known/mhs.json` needs `Authorization: Bearer <token>`, otherwise 401 `MHS.AUTH.UNAUTHENTICATED` with `WWW-Authenticate: Bearer`. The e-stop is not exempt, so every client is given a token; a token is never echoed (TPT-014).

**CORE-182:** `POST /mhs/v1/rpc` requires `Content-Type: application/json` (parameters allowed), otherwise 415 `MHS.PROTOCOL.INVALID_REQUEST`; `GET` on that path is 405 and never executes a method (TPT-011). Every early refusal closes the connection so an unread body is never parsed as the next request; every connection has a socket timeout (default 30 s); a request over 1 MiB is `MHS.LIMIT.PAYLOAD_TOO_LARGE`; a batch over 64 requests is `MHS.PROTOCOL.BATCH_TOO_LARGE`.

**CORE-183:** Transports decode JSON strictly (RFC 8259): a `NaN` or `Infinity` literal is `MHS.PROTOCOL.PARSE_ERROR` (HTTP 400), and so are non-finite values in in-process params and a number that overflows to infinity (`1e999`; over HTTP that case answers status 200 with the JSON-RPC error, a known inconsistency; open item in the 0.9 change notes, `MHS/changes/WP-09.md`), except in an e-stop request (CORE-076). A request for an effectful method (`mhs.command`, `mhs.resource.write`, `mhs.restore`, `mhs.safety.reset`, `mhs.safety.permit`, `mhs.composition.run`) sent as a notification is dropped and logged and never executed, because its outcome could not be receipted (PROTO-005); an e-stop notification still latches.

**CORE-184:** `GET /mhs/v1/events?session_id=<id>` requires a live session (missing id 400, unknown or expired 403, a token-bound session of another principal 403) and drains only that session's subscriptions; an optional `subscription_id` must belong to it (else 404). A principal may hold at most 4 streams (429 `MHS.LIMIT.CONNECTION_LIMIT`). Frames are `id: <subscription>:<seq>` and `event: mhs.event` after an initial `retry: 3000` (TPT-016); `mhs.unsubscribe` works only for the owning session. Safety events (e-stop engaged or confirmed, reset) travel on the `control` stream with `type` `safety`.

**CORE-185:** `mhs.schema.get` serves only the classes the device binds and the schemas shipped with the package, resolved by bare file name or known `$id`; a path, `..`, `~`, a drive or a URL is refused (`INVALID_PARAMS`, HTTP 404), and a document a local caller loaded is never served (PROTO-022).

**CORE-186:** `mhs.hello` returns `server`, `implementation {name, version}`, `spec_version`, `mhs_version`, `protocol_versions`, `endpoint_id`, `time`, `started_at`, `features`, `limits`, `conformance`, `devices` and `safety {certified: false, notice}`. `limits` has `max_request_bytes` (1048576), `max_batch` (64), `max_subscriptions` (64), `max_rate_per_s` (50), `session_max_ttl_s` (86400), `receipt_retention_days` and `max_receipt_retention_s` (the same retention in two units, default 30 days, EVID-018), `receipt_store` and `max_command_deadline_ms` (600000). `conformance` lists only the devices' own claims and is `[]` when none is made. The endpoint implements 24 methods: the 26 of [02](02-wire-protocol.md) §3 less `mhs.composition.run` (reserved) and `mhs.registry.search` (not an endpoint method; `MHS.PROTOCOL.METHOD_NOT_FOUND`).

## 15. Claims and honesty

**CORE-190:** `mhs.conformance.report` returns the last report stored with `record_conformance_report` (its digest must recompute and its `subject.id` must be the endpoint or one of its devices) or, when none was stored, a schema-valid report in which every suite test is `skip` with detail `not_run`, `level_achieved` `CL0`, and the disclaimers `not_certified` and `self_issued`. An endpoint MUST NOT report a level it has not run.

**CORE-191:** A pass on a fake or simulator backend produces the evidence state `contract_checked` and never an MHS-Device level. A hardware evidence level comes only from an operator-run check on the real device. Reports, badges and registry records keep the wording of SAFE-052.
