# Playbook: from a task card to a merged driver package

For whoever runs a model (DeepSeek or another) over the corpus, and whoever reviews what it writes. The model's own
instructions are in [PROMPT.md](PROMPT.md). The Driver API and the gate are in
[`MHS/sdk/docs/driver-authoring.md`](../sdk/docs/driver-authoring.md).

All commands run from the repository root with `export PYTHONDONTWRITEBYTECODE=1`.

## 1. The unit of work and which cards are given out

One task card becomes one driver package becomes one pull request. A card is `MHS/registry/tasks/<track>/<owner>__<repo>.json`
(2,967 of them). They are generated by `python3 MHS/registry/build_registry.py --jobs 8` and never edited by hand: a wrong
decision is corrected by an entry in `MHS/registry/overrides/` (a maintainer's job), then the registry is rebuilt.

`python3 MHS/handoff/tools/dispatch.py --stats` classifies every card. The counts below are those of the registry build
in this repository; run the command for the current ones.

| State | Cards | What happens |
|---|---:|---|
| `dispatch` | 0 | remaining driver tasks: none; the 150 ROS cards ran in [ROS wave C](../changes/ROS-WAVE-C.md), the 33 cards of the helper integration in [helper wave 1](../changes/HELPER-WAVE-1.md) and the 15 routed waiting cards in [helper wave 2](../changes/HELPER-WAVE-2.md) |
| `recon` | 0 | the last 3 entry or repository-role decisions were routed on 2026-11-05 ([WAVES.md](WAVES.md)) |
| `waiting-helper` | 0 | the 22 cards that waited for a helper were routed on 2026-11-05 ([WAVES.md](WAVES.md)) |
| `skip`, `reference`, `bridge-runtime` | 1530, 319, 272 | no repository author task |
| `done` | 842 | 746 pass (the exemplars included), 85 blocked ([why each is blocked](BLOCKED.md)), 11 skip-proposed; see [ROS wave C](../changes/ROS-WAVE-C.md), [helper integration](../changes/HELPER-INTEGRATION.md), [helper wave 1](../changes/HELPER-WAVE-1.md), [helper wave 2](../changes/HELPER-WAVE-2.md) and the SDK and repair records of 2026-11-05 and 2026-11-06 in `MHS/changes/` |

Snapshot: 2026-11-06, after the helper integration (five helper families, the AS7265x repair, reviewed card corrections), ROS wave C (150 cards, each reviewed by Claude), helper wave 1 (33 cards, each reviewed by Claude), helper wave 2 (15 cards) and the SDK and repair phases of 2026-11-05 and 2026-11-06 (companion sources and lock companions, sensed-confirmation stops, the simulator host and other records in `MHS/changes/`; the last phase authored by Grok and reviewed by Codex), with the registry regenerated and every package's task.json synchronized. Passing package status is fake contract evidence. The historical MCM3000 binary citation still fails strict collection and has not been accepted by a model. No hardware or publication approval follows from these counts.

A card is **dispatchable** when `decision` is `direct-driver` or `family-config`, `helper_status` is `available`,
`blocked_on` is empty, `quarantine` is false and `package_status` is `none` or `in_progress`. A passing package is
maintained, not given out again; a `blocked` or `skip-proposed` package waits for a human (section 6).

## 2. The loop

```sh
python3 MHS/handoff/tools/dispatch.py --publishable --limit 20        # pick cards, wave then rank (lower is first)
python3 MHS/handoff/tools/prepare.py gh.owner/repo                    # creates the driver dir with task.json (--dry-run to look)
python3 MHS/handoff/tools/render_prompt.py gh.owner/repo --model-id <MODEL_ID> --run-id <RUN_ID> > prompt.txt
#   run the model on prompt.txt inside the sandbox (SANDBOX.md); it writes only that driver directory
python3 MHS/handoff/tools/collect.py MHS/drivers/<track>/<owner>__<repo>   # YOU re-run the gate; never trust RESULT.json
#   human review (REVIEW.md)  ->  one pull request for this directory  ->  CI re-runs the gate  ->  merge
python3 MHS/registry/build_registry.py --jobs 8                       # AFTER the merges: package_status becomes pass / blocked / skip-proposed
python3 MHS/handoff/tools/prepare.py --sync                           # and every package's task.json follows its rebuilt card
```

A pull request changes nothing outside its own `MHS/drivers/<track>/<owner>__<repo>/`, so the card and the record of a new
package still say `package_status: none` and `static_scan` when it is merged. CI therefore runs `validate.py --allow-stale-cards`
(the two lagging comparisons are warnings). The maintainer's step after a batch of merges is the last two commands above, then
`python3 MHS/registry/validate.py --no-corpus` **without** the flag, which must pass: until the registry is rebuilt it reports
`card package_status 'none' != overlay 'pass'`, and until `--sync` has run the gate reports `G1.CARD_EDITED` for the packages
whose card moved (`task.json` must be a byte copy of the registry card).

`tools/collect.py` exits 1 when a package fails the gate. It prints `warning:` lines (and fails with `--strict`, which CI uses)
for `RESULT_UNTRUSTED` (RESULT.json disagrees with the gate), `RESULT_DIGEST_STALE` (RESULT.json is a pass whose `gate.digest` is
not the digest of this gate run: the package was edited after the author's last gate run), `EXEMPLAR_RESIDUE` (any text file of
the package still names another exemplar's repository, class or model: `mhs.driver new --like` copies the exemplar's files and a
model sometimes keeps them), `UNSOURCED_LIMIT_GATE_WARNING` (G4 warned that a cited line does not show the number) and
`UNVERIFIABLE_CITATION` (a citation points into a PDF, whose page G4 cannot read). The last two are the reviewer's reading list:
once `driver.lock.json` carries `reviewed_by`, they are printed as `accepted by <reviewer>` and no longer fail `--strict`.
`note:` lines never fail anything: the gate's other warning codes, and `DECISION_DEVIATION` (a `family-config` card was written as
a direct driver; a maintainer decides on an override for the card).

Budget per package: the model gets at most 6 gate runs and the time box of the card. The gate runs in order, a G3 failure leaves
G5, G6, G8 and G9 unrun, and a run takes a few seconds (up to the 180 s of G9).

`tools/run_wave.py` does the first four steps of this loop for many cards, one after the other (see its docstring): you give it
the command that starts your agent (`--agent-cmd '<agent> {PROMPT_FILE}'`), it prepares each card, renders the prompt, runs your
command with the card's time box as the limit, re-runs the gate with `collect.py` and appends one line per card to
`work/handoff-runs/<batch>/summary.jsonl`. It starts no model by itself and has no sandbox of its own: run it where
[SANDBOX.md](SANDBOX.md) says. `--dry-run` shows what it would do. A card may take up to its `timebox_min` (30 to 90 minutes; the
pilot's took about 10), so run several at a time: `--jobs 10` keeps ten cards running, each in its own agent process, and lists
afterwards any file that changed outside the cards' directories (`outside-writes.txt`), including the settings in a clone's `.git`
(`config`, `info/`, `hooks/`) that change what git reports about the checkout.

Without a script, [MASTER-PROMPT.md](MASTER-PROMPT.md) is the prompt to type into an interactive harness; [HARNESS.md](HARNESS.md) says what a harness
has to do for either way.

`tools/show_refs.py <dir>` prints every citation of a package beside the cited upstream lines, for the reviewer.
`prepare.py --sandbox` additionally creates `work/sandbox/<owner>__<repo>/{src,venv}` for the rare card that needs upstream
code to run; the gate itself never does ([SANDBOX.md](SANDBOX.md)).

## 3. Reading a card

| Field | Meaning |
|---|---|
| `decision`, `role`, `reason_code` | what the repository is and why triage decided so. `direct-driver`: a `Driver` subclass with decorated methods. `family-config`: a config-only subclass of the family `helper` (`ScpiDriver`, `SerialDriver`, `PythonObjectDriver`, `GymnasiumDriver`, `MujocoDriver`) |
| `family`, `helper`, `helper_status`, `blocked_on` | the helper that exists (`available`) or the `helper:<name>` the card waits for |
| `entry_symbols` | `module.path:Class`, with `file`, `line` and `confidence`: `ast` (found by parsing the clone), `override` (a recon proposal a maintainer accepted), `recon` or `guess`. The first `override` or `ast` symbol is the usual `native` |
| `models` | MuJoCo scene or robot models, main model first; a `MujocoDriver` loads `models[0]` |
| `hints` | candidate reads, writes, actions and catalogue classes, found by a static scan of the clone. Suggestions only; verify every one in the code |
| `safety.expected_mode`, `safety.risk_floor`, `safety.limit_hints` | the device mode the driver must be (`hardware` needs a hardware backend and a fake; `simulated` is served as it is), the lowest `risk` allowed (taken from the catalogue only) and `path:LINE` places to look for bounds |
| `mock_strategy` | `preferred`: `upstream-sim` (the repo has a simulator), `fake` (write a recording fake) or `transcript` (replay recorded exchanges); `hints` are places to start |
| `install` | what the upstream needs. The gate needs none of it; it matters only for running upstream code in a sandbox |
| `needs_recon` | what the scan could not derive: `decision`, `entry_symbol`, `model`, `install`, `capabilities`, `limit_sources` (no bound found yet: expect `Limit.operator_required`), `license`, `artifacts` (README downloads assets: usually `NEEDS_ARTIFACTS`), `motion`, `mode` |
| `exemplar` | the package to copy structurally |
| `timebox_min` | minutes before the run is cut off |
| `publish_review` | `required`: the licence is copyleft-network, source-available, proprietary or unknown. A driver may still be written; the owner decides before it is published |
| `wave`, `rank` | order of work ([WAVES.md](WAVES.md)) |
| `package_status` | `none`, `in_progress` (directory without RESULT.json), `pass`, `blocked`, `skip-proposed` |

A card's `decision` and `helper` are a triage guess made by a static scan. A `family-config` card for `SerialDriver` is wrong when the
upstream builds its bytes from parts (a letter plus a number such as `V5R`) or frames them (address, sequence, checksum): the
model then writes a direct `Driver` with a `native.py` factory, says so in the notes, and `collect.py` shows
`DECISION_DEVIATION`. The maintainer adds an override for the card (`MHS/registry/overrides/README.md`) so the registry says
`direct-driver` and the next model run starts from the right shape. For a driver pack (one repository, many devices) keep the
card's family in the override: the family picks the entry symbols and the floor, and another family can pick other devices
than the package drives (`G7.NOT_AN_ENTRY_SYMBOL`, `G3.RISK_FLOOR`). About 46 cards name `SerialDriver`, 49 `ScpiDriver`; expect
this for the serial ones with compact commands. The `hints` of a card are name matches: a listed method can be broken upstream
(`XCaliburD.haltExec` names an undefined variable) and a listed catalogue class may not bind the device kind (`cap.fluid.dispense.v1`
needs a labware and a well; `cap.motion.stop.v1` does not bind `fluid.pump`); the gate reports the latter as `G3.STRICT`.

## 4. What the model produces

All inside `driver_dir` (`MHS/drivers/<track>/<owner>__<repo>/`):

| File | |
|---|---|
| `task.json` | the card; input, never edited |
| `driver.py` | exactly one `Driver` subclass |
| `fake.py` or `fixtures/` | the fake backend (recording fake, upstream simulator hook, or transcript) |
| `facts.md` | tags and facts, each with `path:LINE` |
| `test_driver.py` | calls `check_driver`; may gain cases, never loses that call |
| `driver.lock.json` | pin, install, backends, `authored_by` (`kind: "model"`), `reviewed_by: null` |
| `reference.json`, `REFERENCE.md` | generated by `python3 -m mhs.driver reference <dir>` |
| `RESULT.json` | below |
| `native.py` | the hardware factory (`connect(**options)` opening the upstream transport); required for a hardware driver that is not a family helper. The gate never imports it; a reviewer reads it line by line |
| `site-limits.example.json`, `fixtures/conformance.json` | optional |

`RESULT.json`:

```json
{"status": "pass", "gate": {"digest": "sha256:...", "failed": []}, "notes": "what the package does not cover",
 "catalogue_requests": [{"capability_id": "x-cap.owner.name.v1", "reason": "no catalogue class fits", "verb": "invoke"}]}
{"status": "blocked", "blocked_on": ["NEEDS_ARTIFACTS"], "notes": "last gate output, trimmed"}
{"status": "skip-proposed", "blocked_on": ["NOT_A_DEVICE"], "notes": "why, with file:line evidence"}
```

The digest is the one the gate prints (`gate digest (RESULT.json gate.digest): sha256:...`), the digest of the report without its
clock; the report's own `report_digest` changes with every run and is not the one. It identifies a gate result, not the package's
content (`collect.py` re-runs the gate anyway), and it is only right for the last gate run, so
`RESULT.json` is written last and the gate is run again after any later edit (`collect.py` reports `RESULT_DIGEST_STALE`).
`catalogue_requests` is optional. `check-report.json` is regenerated by every gate run and is not committed.

## 5. Blocked codes

| Code | Use it when | A human then |
|---|---|---|
| `ENTRY_UNVERIFIED` | none of the card's entry symbols can be confirmed in the clone | fixes the card by an override, or marks the repo `skip` |
| `INSTALL_FAILED` | an optional sandbox install failed and the card needs the upstream simulator | inspects, may change `mock_strategy` |
| `NO_HARDWARE_FREE_PATH` | no honest fake is possible (the device cannot be modelled without hardware) | decides between a transcript from a real run and a skip |
| `HELPER_MISSING` | the card's helper cannot express the device and a direct `Driver` over the upstream class cannot either | schedules SDK work |
| `LICENSE_BLOCKED` | the licence forbids the work | decides with `publish_review` |
| `NOT_A_DEVICE` | with `skip-proposed`: a library, tool or benchmark | adds a `skip` override |
| `QUARANTINE` | the card is quarantined | nothing; it is never run |
| `PLATFORM_UNSUPPORTED` | a backend that can never run on the target platforms (Python 2 source is no reason any more: G7 reads it leniently, `G7.LEGACY_SOURCE`, and `native.py` ports it) | decides |
| `NEEDS_ARTIFACTS` | the device's essential output is an image, waveform or large array and the standard has no artifact transport yet | waits for the artifact store |
| `CATALOGUE_GAP` | the capability is essential and no class or extension fits | decides on a catalogue class |
| `SDK_BUG` | the SDK or the gate misbehaves; the notes carry a minimal repro | fixes the SDK, then reopens the card |
| `GATE_TIMEOUT` | the package hangs the gate (900 s bound) and cannot be fixed | inspects |

## 6. Triage of results (a human, after `collect.py`)

- **pass**: review ([REVIEW.md](REVIEW.md)), then pull request. A hardware driver at R2 or above stays unable to start its
  hardware backend until a human signs `reviewed_by` in `driver.lock.json`.
- **blocked** or **skip-proposed**: read the notes and act as the table says. Keep the directory (it records the attempt)
  or delete it before the merge; the registry reads `RESULT.json` and shows the card as blocked.
- The model never changes the SDK. Several packages blocked on the same `SDK_BUG` are one SDK task.

## 7. Recon tasks (cards in the `recon` state)

For `untriaged` cards (946: `weak_entry`, `no_entry_class`, `non_python`) and cards blocked on `recon:*` the model does **not** write a
driver. It decides what the repository is and writes one proposal file, `MHS/handoff/recon/<owner>__<repo>.json` (named after the card's
driver directory, which differs for 14 clones such as a name with a trailing dash), with the prompt [RECON-PROMPT.md](RECON-PROMPT.md):

```json
{"package_id": "gh.owner/repo", "proposed": {"strategy": "direct-driver", "role": "device-driver", "family": "python-object"},
 "entry_symbols": [{"symbol": "pkg.mod:Class", "file": "pkg/mod.py", "line": 12}],
 "evidence": ["pkg/mod.py:12 class Class drives the device over a serial port", "README.md:30 ..."],
 "notes": "One sentence that stands alone (it becomes the override's justification), then what a driver author needs to know."}
```

`strategy`, `role` and `family` are the enumerations of `MHS/registry/schema/overrides.schema.json`. The loop is the driver loop with
other tools: `render_prompt.py <id> --recon ...` (or `run_wave.py --recon`, which also checks each proposal), the same sandbox
([SANDBOX.md](SANDBOX.md)), then

```sh
python3 MHS/handoff/tools/check_recon.py --all                          # shape, card, every cited path:LINE, entry symbols
python3 MHS/handoff/tools/check_recon.py --all --show                   # prints the cited lines for the maintainer who reads them
python3 MHS/handoff/tools/check_recon.py --all --emit-overrides draft.json   # the valid proposals as override entries
```

The checker cannot tell whether the evidence *means* what the model says. A maintainer reads at least the entry symbol and the
evidence lines of every proposal that makes a repository a driver task, moves the entries that hold into a file of
`MHS/registry/overrides/` (format: `MHS/registry/overrides/README.md`: each repository once across all files, sorted by package
id), runs `python3 MHS/registry/build_registry.py --jobs 8` and `prepare.py --sync`; the card is then a normal driver task, a
reference or a skip. A proposal of `skip` or `untriaged` is a result too. Nothing writes into `overrides/` by itself.

A driver proposal's emitted entry carries its `entry_symbols`, and the rebuilt card names them (confidence `override`) instead of the
scan's guesses; that is what turns a card without a parsable class (Python 2, a script) into a driver task. The driver prompt then
points the model at the proposal, whose notes say what to port and what to fake. Recon wave A (batch `rA`, 680 cards of wave 4, October
2026) is the first run at scale: `MHS/changes/RECON-A.md` has what the review accepted and why; recon wave B (batch `rB`, the
285 cards of wave 6) is in `MHS/changes/RECON-B.md`.

## 8. Things that do not fit yet (say so instead of faking it)

- **Frameworks with many devices** (the card lists several entry symbols): implement one device class, the first
  confirmed, and name the others in `facts.md` and `notes`. One package per repository is the rule.
- **Images, spectra, waveforms, large arrays**: the standard has no artifact transport yet. Expose scalar and small-array
  state only. An instrument with useful scalar functions passes with them and names the array in its notes ("NOT COVERED:
  the spectrum array"; `gh.ap/python-seabreeze` and `gh.python-ivi/python-ivi` are such cases); a device whose only
  output is the array (a camera with nothing else to read or set) stops with `NEEDS_ARTIFACTS`. A robot or simulator whose control works without the data (actions, state, reward) may still pass: its fake
  returns a smaller array of the declared type and rank (a 480 x 640 x 3 image costs 3.4 MB and seconds per step through the
  bridge, more than the gate can afford), and the real size is named in the notes and the fidelity `gaps`. The reviewer then
  decides between publishing and `NEEDS_ARTIFACTS`. `gh.huggingface/gym-aloha` is such a case.
- **Numbers in a fake** (start positions, canned replies) are test data, not facts. They are marked `# placeholder` and never
  enter a `Fact`, a `Limit` or the reference. The exception is a Gymnasium fake's action space: the reference shows the bounds
  derived from it without a source, marked as the fake's, unless `action_space_ref` cites the upstream line the fake copies
  (`docs/driver-authoring.md` section 5).
- **Vendor manuals that are PDFs**: cited `docs/manual.pdf:PAGE`; G4 cannot read them, so each such citation is a reviewer's
  `UNVERIFIABLE_CITATION`.
- **SDKs that report failure as a return code** (most robot arms): the gate injects exceptions only, so the package needs its
  own case in `test_driver.py` that forces a non-zero code and expects a `failed` receipt. The xArm exemplar shows how.
- **MuJoCo cards** point at the Gymnasium exemplar: the shape is the same, but no exemplar loads a
  MuJoCo model file. A `MujocoDriver` loads `models[0]` of the card; `docs/bridges.md` has the grammar. Expect to need the SDK
  maintainers' help on the first few.
- **Expected warnings.** A Gymnasium or MuJoCo driver shows `G8.NO_UNIT` warnings for the integer inputs the bridge derives
  (`ticks`, `action.index`, `seed`), and `G6.NO_NATIVE_CALL` for the seed class. They do not fail the gate; `collect.py` prints
  them as a note. A bound that sits in a constructor default or on another line than the cited check (a valve port count) leaves a
  `G4.REF_VALUE` warning for the reviewer. Any other warning is something to fix or to explain in the notes.
- **Recovery after an e-stop.** A reset only re-establishes communication that changes nothing on the device. When the
  stop leaves the device disabled, the upstream's own enable, power-on or start call (with any fault clearing) is one
  `@action(reenable=True)` and the driver has no `@reset`; when only a new native session undoes the stop, set
  `estop_terminal` (SAFE-042, CORE-086, CORE-087). The xArm exemplar shows the re-enable.
- **Long actions** use `@action(long_running=True, max_duration_ms=..., cancellable=True)` and check `self.cancelled()`.
- **Continuous control** (velocity streams) needs the device's own watchdog, cited as a Fact, before `watchdog_ms` may be
  declared; the runtime implements no watchdog.
- **Publication**: `PUB` cards (`publish_review: required`) can be implemented, but the owner decides before the package
  is published. Drivers import upstream code in the hardware backend and never copy it.
