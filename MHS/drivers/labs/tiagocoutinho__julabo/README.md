# Exemplar: gh.tiagocoutinho/julabo (an async direct Driver)

A JULABO circulating bath (`julabo.device:JulaboCF`) as an R2 hardware driver. The package is model-authored
(`driver.lock.json` `authored_by` kind `model`) and unreviewed (`reviewed_by` null), so it runs on the **fake backend
only**: the loader refuses the hardware backend of a model-authored R2 driver until a human signs `reviewed_by`.
Its evidence is `contract_checked` and never an MHS-Device level.

## Run the gate

```sh
PYTHONPATH=MHS/sdk/src python3 -m mhs.driver check MHS/drivers/labs/tiagocoutinho__julabo --backend fake
```

## What it demonstrates

| Pattern | Where |
|---|---|
| An async upstream API: every method is `async def` and awaits `self.native` | `driver.py`, `fake.py` |
| `@read` parameters in `Cel`, an integer, a boolean and a string | `driver.py` |
| A `@read` and a `@write` of the same parameter (`setpoint`) | `driver.py` |
| A bound no text file states: `Limit.operator_required(reason)`, filled by the site overlay | `driver.py`, `site-limits.example.json` |
| An `x-cap.<owner>.<name>.v1` action with an inline output schema | `start_circulation` |
| The native stop as `@estop` and as the safe-state action (`safe_state=True`), which SAFE-045 asks of R2 hardware without a cited hardware e-stop | `stop`, `stop_circulation` |
| A fake that mirrors the upstream method signatures (`set_point_1(value=None)` reads or writes) and starts from the upstream simulator's defaults | `fake.py` |
| An async hardware factory and a `teardown` hook | `native.py`, `driver.py` |
| Facts that cite ranges of lines (`path:FIRST-LAST`) | `driver.py` |

## Files

| File | Role |
|---|---|
| `task.json` | the registry task card (input; a copy of `MHS/registry/tasks/labs/tiagocoutinho__julabo.json`) |
| `driver.py` | the `Julabo` Driver class |
| `fake.py` | `FakeJulaboCF`, the fake backend: only attributes `julabo.device:JulaboCF` has (gate G7) |
| `native.py` | the hardware factory; the gate never imports it and nothing here ran it |
| `facts.md` | the facts and limits with their sources |
| `site-limits.example.json` | an operator overlay: it supplies the range of the set point |
| `test_driver.py` | the gate harness call plus cases for this driver |
| `driver.lock.json` | pinned upstream, install, backends, `authored_by`, `reviewed_by` |
| `reference.json`, `REFERENCE.md` | generated: `python3 -m mhs.driver reference <dir>` |
| `RESULT.json` | `pass` with the gate digest the check printed |

## Honest limits of this package

- The hardware path (`native.py`, the real connection URL, the pacing of the protocol) was never run. The fake is an
  in-memory object, not a recording of the device.
- The set point range is unknown to the driver: it refuses every set point write (`MHS.SAFETY.LIMITS_UNSET`) until the
  operator's `site-limits.json` supplies one. `site-limits.example.json` is an example, not a statement about any unit.
- The driver writes set point 1 only. The active set point channel (1 to 3) names the working set point in use; the driver
  reads it and never changes it, so a write to set point 1 matters for regulation while the channel is 1. The clone names
  the channel but does not describe what the controller does with it.
- `check-report.json` is generated by every gate run (new timestamps each time) and is not part of the package.
  `RESULT.json` records the digest the check printed (`gate digest (RESULT.json gate.digest)`), which stays the same
  while the gate result stays the same.
