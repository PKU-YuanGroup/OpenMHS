# Exemplar: gh.thinksrs/srsinst.sr860 (a ScpiDriver command map with a transcript-backed fake)

The SR860 lock-in amplifier (`srsinst.sr860.instruments.sr860:SR860`, also the SR865 and SR865A) as an R1 hardware
driver. The package is model-authored (`driver.lock.json` `authored_by` kind `model`) and unreviewed (`reviewed_by`
null). It is checked on the **fake backend only**; its evidence is `contract_checked` and never an MHS-Device level.

## Run the gate

```sh
PYTHONPATH=MHS/sdk/src python3 -m mhs.driver check MHS/drivers/labs/thinksrs__srsinst.sr860 --backend fake
```

## What it demonstrates

| Pattern | Where |
|---|---|
| A family driver is configuration only: `parameters`, `reads`, `writes`, `safety_bindings` | `driver.py` |
| Limits the upstream code states, each citing its line; a range reference (`path:FIRST-LAST`) when the two bounds sit on different lines | `driver.py` |
| An allowed set of numbers and an `enum_map` from the value to the instrument's index (`OFLT 6` for 1 ms), both built from the same expression the upstream code uses | `driver.py` |
| An identity check on connect (`idn`) | `driver.py` |
| An e-stop that writes the lowest value of the one output the driver sets | `driver.py` |
| A transcript-backed fake: a recorded session in the `mhs.testing.Transcript` format answers by lookup, and writes change the answer of their own query | `fixtures/session.json`, `fake.py` |
| An operator overlay that narrows every limit (a range, a maximum, a subset of the allowed set) | `site-limits.example.json` |
| Cases that check the wire commands the command map produces | `test_driver.py` |

Why the fake is not a strict replay: `transcript = "fixtures/session.json"` on the driver replays one fixed request
sequence and raises on any other. The gate and the conformance suite send many different sequences, each on a fresh
transport, so `fake.py` looks every recorded query up instead.

| File | Role |

| `driver.py` | the `Sr860` ScpiDriver class |
| `fake.py`, `fixtures/session.json` | the fake transport and the recorded session it answers from |

## Honest limits of this package

- The session is not a recording of an instrument run by this driver. The identity, the frequency, R and Theta are the
  values the upstream README prints (`README.md:63`, `186-190`); X and Y are derived from R and Theta; the amplitude
  starts at 0 V. Each exchange of `fixtures/session.json` says so in its `note`.
- The wire syntax (`FREQ?`, `FREQ value`, `OUTP? 0`) follows the forms the clone shows for other commands
  (`components.py:234`, `583`) and the command names of its command tables. The command classes that build these lines
  live in `srsgui`, which is not part of the clone, so the exact lines were not checked against an instrument.
- Numbers are written with up to ten significant digits in Python's `g` format (`1e-09` for a nanovolt); whether an
  instrument takes that exponent form was not tried.
- The time constant is write-only here: `OFLT?` answers the index, and a read map cannot turn it back into seconds.
- X, Y and R are in the unit of the selected signal input (volts or amperes); the driver neither reads nor sets the
  input mode.
- The upstream class reads out an initial string after connecting over TCP (`sr860.py:80-86`), and the generic SCPI
  bridge has no such step before its `*IDN?` check. Prefer a VISA resource (`visa_resource`) for the hardware backend;
  nothing here ran any hardware backend.
- `check-report.json` is generated by every gate run (new timestamps each time) and is not part of the package.
  `RESULT.json` records the digest the check printed (`gate digest (RESULT.json gate.digest)`), which stays the same
  while the gate result stays the same.
