## Scope and safety

The pinned clone is a ROS 1 Noetic Gazebo warehouse world. The README names Ubuntu 64-bit 20.04 (`README.md:28`), ROS Noetic (`README.md:30`) and an apt line that installs `ros-noetic-navigation` (`README.md:34`). The shipped launch includes `gazebo_ros` `empty_world.launch` with `worlds/warehouse.world`, `paused=false` and `gui=true` (`launch/warehouse_simulation.launch:8-12`). `warehouse.world` sets the physics type to `ode` (`worlds/warehouse.world:67`). The launch spawns the pioneer3dx model from `urdf/pioneer3dx.xacro` and starts `robot_state_publisher` under `/pioneer3dx` (`launch/warehouse_simulation.launch:19-23`). The Pioneer 3DX differential-drive plugin sets `commandTopic` `cmd_vel`, `odometryTopic` `odom`, `robotNamespace` `/`, `wheelSeparation` 0.32, `wheelDiameter` 0.18, `wheelAcceleration` 0 and `updateRate` 100.0 (`urdf/pioneer3dx_body.xacro:320-341`).

The only in-package command endpoint is the teleop's relative `cmd_vel` publication of `geometry_msgs::Twist` (`src/key_control.cpp:178`). That node block is inside an XML comment (`launch/warehouse_simulation.launch:25-27`), and the package builds exactly one executable, `key_control` (`CMakeLists.txt:30-31`). The shipped launch also starts `slam_gmapping`, `move_base`, `rviz` and `hector_trajectory_server` (`launch/warehouse_simulation.launch:8-67`). `move_base` starts at the root namespace with `respawn` true and no remap (`launch/warehouse_simulation.launch:45-60`).

The package exposes that one velocity publication. The device resource reads no topic. Odometry, the laser, the IMU and `/clock` come from world updates. Ordinary `World::Step` updates are suspended while `pause` is true, except when `stepInc` is greater than 0 or a reset is due (`World.cc:835-837`). The read-back observes only `IsPaused()` and does not prove those exceptions did not run. The `cmd_vel` receipt reports `sent_linear_velocity` and `sent_angular_velocity`, the two values handed to rosbridge. It does not expose `/scan`, `/odom`, `/imu`, `/tf`, `/map`, the `move_base` action, `/clock`, or the Gazebo reset and spawn services.

The stop is the Gazebo world pause of companion gazebo_ros 2.9.3. The `gzserver` wrapper adds `libgazebo_ros_api_plugin` unless the arguments already name it, and the shipped launch starts that server through `empty_world.launch`:

- e-stop: `/gazebo/pause_physics` (`std_srvs/Empty`). `pausePhysics` calls `world_->SetPaused(true)` and returns true (`gazebo_ros_api_plugin.cpp:1725-1729`);
- read-back (`safety_bindings.safe_state`): `/gazebo/get_physics_properties`. The e-stop is confirmed only when `pause` is true. `getPhysicsProperties` sets `res.pause` to `world_->IsPaused()` (`gazebo_ros_api_plugin.cpp:1489`). A pause that is not answered, a read-back that fails (a physics engine other than ODE, `gazebo_ros_api_plugin.cpp:1496-1528`) or `pause` false is `MHS.SAFETY.SAFE_STATE_UNREACHED` with the latch held and a background retry.

`World::Step` of Gazebo 11 advances simulation time and calls `Update` only when the world is not paused, a step increment is pending or a reset is due; otherwise it adds the step to the pause time (`World.cc:835-854`). `GazeboRosDiffDrive` connects `UpdateChild` to the world-update begin event (`gazebo_ros_diff_drive.cpp:177-179`). When `seconds_since_last_update` is greater than `update_period_`, `UpdateChild` calls `getWheelVelocities` and, when `wheel_accel` is 0 or a wheel is within 0.01 of its target speed, sets both wheel joint velocities (`gazebo_ros_diff_drive.cpp:269-289`). `getWheelVelocities` derives both wheel speeds from the stored `x_` and `rot_` (`gazebo_ros_diff_drive.cpp:324-333`). `cmdVelCallback` stores `linear.x` in `x_` and `angular.z` in `rot_` with no timeout (`gazebo_ros_diff_drive.cpp:335-340`). `QueueThread` serves that queue with a 0.01 s wall-clock wait while the plugin is alive (`gazebo_ros_diff_drive.cpp:342-349`), so a command received while the world is paused is stored and applied on the next world update. The stop is that paused flag, not a measured standstill.

No unpause is offered, neither as a re-enable nor as an ordinary command (the orchestrator's SAFE-042 condition and `MHS/handoff/REVIEW.md` item 13). Stopping the `cmd_vel` publishers does not clear the plugin's stored `x_` and `rot_` (`gazebo_ros_diff_drive.cpp:335-340`). `UpdateChild` applies those stored values again when updates resume (`gazebo_ros_diff_drive.cpp:269-289`, speeds from `:324-333`). A zero Twist can replace `x_` and `rot_`, but that publication is unacknowledged and is not proof the stored command is clear. The shipped launch also starts `move_base` at the root namespace with `respawn` true and no remap (`launch/warehouse_simulation.launch:45-60`). This package does not command `move_base`: the clone declares no `move_base` cancel, and `move_base`'s velocity topic is set outside the clone, so it is not cited as a fact. A controller this package does not command cannot be cleared first. `unpausePhysics` (`gazebo_ros_api_plugin.cpp:1731-1735`) is cited only as a fact about that function; it is not bound. After `mhs.safety.reset` the latch is released and the world stays paused. Before any manual unpause the operator prevents publisher respawn, including `move_base`, and clears or reinitializes the retained `x_` and `rot_` outside MHS.

A pending step, a Gazebo reset (`World.cc:835-837`), a GUI step or a WorldControl `multi_step` (`World.cc:1630-1640`) still calls `Update` while `pause` is true, and any ROS client can unpause the world. MHS does not read the flag again after the e-stop. The read-back succeeds only for the ODE engine (`warehouse.world` sets `ode`); another engine makes `get_physics_properties` return false and the latch stays held. The deployment's gazebo_ros and Gazebo must be the pinned 2.9.3 (Noetic) and 11 releases the companion citations name; rosbridge cannot read their versions. On a graph without gazebo_ros neither service exists and the e-stop fails with the latch held.

The declared risk is R2 (mobile-base transit, `MHS/spec/04-safety.md` section 2.1, `MHS/handoff/REVIEW.md` item 12). In the simulated deployment the effect is confined to Gazebo, but `/cmd_vel` is the generic root topic that a real mobile base behind the same rosbridge would also consume, and a simulated label does not lower that risk. The pause service is a world service; the R2 is the velocity binding. This is not a physical emergency stop, no physical device is present, and the package makes no hardware-safety claim. `driver.lock.json` keeps `reviewed_by` null.

## Limits

The clone states no numeric range or physical unit for `Twist.linear.x` or `Twist.angular.z`. The teleop reads `scale_linear` and `scale_angular` with constructor defaults 2.0 (`src/key_control.cpp:170-176`). `keyLoop` sets `linear_` and `angular_` to the per-key literals 0.7, 0.3, 0.0, -0.3 or -0.0, then multiplies by those scales (`src/key_control.cpp:232-264`). The scales are not device bounds. Both action inputs use `Limit.operator_required` with unit `1`. Every publication is refused with `MHS.SAFETY.LIMITS_UNSET` until the operator supplies `site-limits.json`. `site-limits.example.json` is example operator data only, not a fact.

## Fidelity contract

`driver.py` describes the deployed fake: engine `canned:ROS fake (no physics)`, level F0, determinism `none`, `timestep_ms` 0 (event-driven replies with no physics step), `realtime_factor` 0 (not paced), reset `none`, and no snapshot/restore. The fake is not a recording of captured traffic. It keeps a paused flag that `/gazebo/pause_physics` sets and `/gazebo/get_physics_properties` reports. There is no unpause, so `mhs.safety.reset` leaves the flag set. While it is set, a Twist is stored as `last_cmd_vel` and does not become `driving_cmd_vel`. Its GetPhysicsProperties numbers are placeholders. The `cmd_vel` receipt reports the values handed to rosbridge, not a measurement. The gaps disclose the absent Gazebo, physics and navigation stack, that ordinary updates are suspended while `pause` is true except a pending or manual step or a Gazebo reset, that another client can unpause and MHS does not read the flag again, that stopping publishers does not clear stored `x_` and `rot_` and that publishing zero is unacknowledged, the ODE requirement, the pinned 2.9.3 and 11 versions, that `move_base`'s velocity topic is outside the clone, and that the receipt is transmission evidence.
