### `resume_simulation`

`x-cap.mortezaaliyari.resume.v1` on `main`: invoke, risk R2, extension.

The declared re-enable after a safety reset: publish a zero Twist on /tb3_0/cmd_vel and /tb3_1/cmd_vel, then unpause the Gazebo world with /gazebo/unpause_physics. Each differential-drive plugin keeps the last cmd_vel it stored and applies it as soon as the world runs; the zeros replace them, but they are unacknowledged publications, so a stored command can still act for a few world steps, and a running move_base publishes new ones.

Inputs:

None.

Outputs:

| Field | Type | Unit | Description |
|---|---|---|---|
| `acknowledged` | boolean |  | True once /gazebo/unpause_physics answered |
| `zero_commands_published` | boolean |  | True when both zero Twists were handed to rosbridge before the unpause; transmissions, not confirmations |

## Safety

- E-stop: software, latching, native stop `/gazebo/pause_physics`.
- Re-enable after a reset: `x-cap.mortezaaliyari.resume.v1` (the reset never runs it; it is refused while the e-stop is latched).
- Safe state: The Gazebo world is paused and get_physics_properties read pause true back: no world update runs, so neither robot's drive plugin sets wheel velocities and odom and scan are silent; it is the paused flag, not a measured standstill, it holds until the resume command, the Gazebo GUI or another client unpauses the world (a GUI step advances it), and each plugin keeps its stored cmd_vel, which the resume zeroes first without an acknowledgement. (achieved by nothing declared).
- Operator-required limits not yet set: `publish_tb30_cmd_vel.angular_velocity`, `publish_tb30_cmd_vel.linear_velocity`, `publish_tb31_cmd_vel.angular_velocity`, `publish_tb31_cmd_vel.linear_velocity`. Hardware use is refused (MHS.SAFETY.LIMITS_UNSET) until site-limits.json supplies them.
- OpenMHS is not a safety certification and not a safety-rated channel; the physical e-stop stays authoritative.
