### `activate_trajectory_controller`

`x-cap.blackcoffeerobotics.activate_controller.v1` on `main`: invoke, risk R2, extension.

The declared re-enable after a safety reset: switch joint_trajectory_controller on again through /controller_manager/switch_controller (STRICT), so the trajectory the e-stop dropped is not resumed. On activation the controller holds the state it starts from: the last command-interface values when set_last_command_interface_value_as_state_on_activation (true by default) applies and every state interface has a command interface, else the measured joints. With this deployment's position-only command interface (position and velocity states) that is the measured position; a configuration that also commanded velocity would hold the last position command, which can differ from the measured position

## Safety

- E-stop: software, latching, native stop `/controller_manager/switch_controller`.
- Re-enable after a reset: `x-cap.blackcoffeerobotics.activate_controller.v1` (the reset never runs it; it is refused while the e-stop is latched).
- Safe state: joint_trajectory_controller is inactive, as list_controllers read back: its goal was aborted and its trajectory dropped, and each joint's position command keeps its last value, which the Gazebo system holds; the world keeps running, it is the controller's state, not a measured standstill, and any client can re-activate it. (achieved by nothing declared).
- Operator-required limits not yet set: `follow_arm_trajectory.points[*].time_from_start.nanosec`, `follow_arm_trajectory.points[*].time_from_start.sec`. Hardware use is refused (MHS.SAFETY.LIMITS_UNSET) until site-limits.json supplies them.
- OpenMHS is not a safety certification and not a safety-rated channel; the physical e-stop stays authoritative.
