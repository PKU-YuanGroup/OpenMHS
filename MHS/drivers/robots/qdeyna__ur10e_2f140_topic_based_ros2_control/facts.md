## Tags

`ros`, `ros2`, `fake-hardware`, `robot-arm`, `trajectory`, `joint-state`, `ur10e`.

## Scope

This package serves only the fake-hardware path of `ur_robotiq_control.launch.py` (`use_fake_hardware` true): `controller_manager`'s `ros2_control_node` and `scaled_joint_trajectory_controller`. The Isaac launch defaults `initial_joint_controller` to `joint_trajectory_controller` and is not served. The real `ur_ros2_control_node` starts unless `use_fake_hardware` is set and uses the same endpoint names, so a rosbridge pointed at it can command a real arm. The mode stays simulated and the risk is R2. `tf_prefix` defaults to empty; this package binds the unprefixed joint names only.

The MoveIt launch says the scaled controller does not work on fake hardware and, when `use_fake_hardware` is true, sets `joint_trajectory_controller` as the MoveIt default. This package does not serve MoveIt. Confirmation is only that `scaled_joint_trajectory_controller` is inactive.

## Limits

The ur10e `joint_limits.yaml` writes `min_position` and `max_position` with the `!degrees` tag (shoulder joints and wrists 360, elbow 180). Those literals are degrees. Copying them as radians would invent a number the line does not state, so the six joint positions are `operator_required`. The clone states no maximum trajectory duration and no nanosecond range for a Duration, so `time_from_start.sec` and `time_from_start.nanosec` are `operator_required` too. A call that sets them is refused with `MHS.SAFETY.LIMITS_UNSET` until the operator supplies the site envelope in `site-limits.json`. `site-limits.example.json` is example test data, not a device bound and not a conversion of the degree tags.

## Safety

The device is a robot arm and is declared R2. The e-stop is `/controller_manager/switch_controller` deactivating `scaled_joint_trajectory_controller` with strictness STRICT and a 0.4 s switch wait. The controller manager node of `ros2_control_node` is named `controller_manager`, and the launch's spawners address it as `/controller_manager`. The scaled controller does not override `on_deactivate`, so joint_trajectory_controller 2.54.1 aborts the goal, keeps each position command at its last value, releases its interfaces and drops the stored trajectory. The stop is confirmed only by `/controller_manager/list_controllers` with a list-element predicate (E4): exactly one element named `scaled_joint_trajectory_controller` must report the state `inactive`. A switch that answers ok false, or a missing, duplicated or still active element, is `MHS.SAFETY.SAFE_STATE_UNREACHED` with the latch held. The gripper, `joint_trajectory_controller` and the forward controllers are not shown inactive. `forward_position_controller` is loaded inactive and claims the same six arm joints, so another client can activate it after this controller releases its interfaces. Any client of the switch service can re-activate `scaled_joint_trajectory_controller` after the e-stop.

The declared re-enable `x-cap.qdeyna.activate_controller.v1` (CORE-086) switches that controller on again. On activation the controller holds the measured position for this position-only command with position and velocity state, because the command-interface read fails on velocity. The trajectory the stop dropped is not resumed (SAFE-042: cleared by the stop itself). Reset releases the latch only and does not activate the controller. There is no world pause and no unpause.

The scaled controller requests `speed_scaling_interface_name` from the controller manager (`scaled_joint_trajectory_controller.cpp:63-70`). The manager claims every individual state interface before it calls activate, and it skips the controller when that claim throws (`controller_manager.cpp:1653-1681`). `claim_state_interface` throws when the key does not exist (`resource_manager.cpp:743-747`). The `on_activate` search (`scaled_joint_trajectory_controller.cpp:84-95`) looks only at interfaces already assigned to the controller. It is not the path the manager takes when the interface was never exported. `scaling_factor_` defaults to 1.0 in the header (`hpp:78`); that initializer is not a deployment fallback for a missing interface.

On the fake-hardware path this package serves, `ur_macro.xacro:113-114` includes `ur.ros2_control.xacro` when `use_fake_hardware` is true. That description selects `mock_components/GenericSystem` (`ur.ros2_control.xacro:44-48`). Inside the block omitted for `sim_gazebo` and `sim_ignition`, it declares gpio `speed_scaling` with state interface `speed_scaling_factor` and parameter `initial_speed_scaling_factor` 1 (`:160-166`; the comment at `:160` says the following are joints used only for testing with fake hardware). GenericSystem records and exports that gpio state (`generic_system.cpp:244-251`, inside `on_init` at `:34`, and `:301-305`) and, when the interface has no `initial_value`, initializes it from the component parameter `initial_<interface name>` (`:714-726`). With an empty `tf_prefix`, the controller yaml's `speed_scaling/speed_scaling_factor` is that interface. A description that omits the gpio does not reach `on_activate`.
