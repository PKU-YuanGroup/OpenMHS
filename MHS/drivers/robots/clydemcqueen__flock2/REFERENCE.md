## Actions

### `publish_cmd_vel`

`x-cap.clydemcqueen.cmd_vel.v1` on `main`: invoke, risk R2, extension.

Publish one geometry_msgs/Twist to the drone controller's cmd_vel topic. The four values are the controller's normalized rate components; the clone states no physical unit. The receipt is a publication acknowledgement only.

Inputs:

| Field | Type | Unit | Required | Limit | Description |
|---|---|---|---|---|---|
| `linear_x` | number | 1 | yes | operator required (not set) | Twist linear.x, a normalized body-frame rate component |
| `linear_y` | number | 1 | yes | operator required (not set) | Twist linear.y, a normalized body-frame rate component |
| `linear_z` | number | 1 | yes | operator required (not set) | Twist linear.z, a normalized vertical rate component |
| `angular_z` | number | 1 | yes | operator required (not set) | Twist angular.z, a normalized yaw-rate component |

Outputs:

| `confirmed` | boolean |  | Always false: a rosbridge publication carries no execution confirmation |

## Safety

- E-stop: software, latching, no native stop (software latch only).
- Safe state: No acknowledged safe stop exists in the pinned clone: /stop_mission is a ROS 2 publication whose callback clears the mission flag, publishes a zero Twist and may forward an asynchronous land request to the external tello_action service; the publication and the service acceptance do not prove that the drone stopped, hovered or landed. (achieved by nothing declared).
- Operator-required limits not yet set: `publish_cmd_vel.angular_z`, `publish_cmd_vel.linear_x`, `publish_cmd_vel.linear_y`, `publish_cmd_vel.linear_z`. Hardware use is refused (MHS.SAFETY.LIMITS_UNSET) until site-limits.json supplies them.
- OpenMHS is not a safety certification and not a safety-rated channel; the physical e-stop stays authoritative.

- DroneBase::start_action drops the requested action when the action manager is busy; otherwise it calls action_mgr_->send(action, g_actions[action]). (upstream_code: src/drone_base.cpp:381-396)
- The action manager sends a TelloAction service request with request->cmd set to the action string and then waits for the service future. (upstream_code: src/action_mgr.cpp:8-21)
- The service response's rc is compared with OK, ERROR_BUSY and ERROR_NOT_CONNECTED; an OK response only marks the action as accepted and leaves state waiting_for_response. (upstream_code: src/action_mgr.cpp:23-48)
- The action manager completes an action only when a later tello_response topic message reports success, failure or timeout. (upstream_code: src/action_mgr.cpp:50-70)
- The action manager comment states that tello_driver uses a ROS service plus a ROS topic to simulate an action, and that only one action can be active at a time. (upstream_code: include/action_mgr.hpp:11-20)
- TrajectoryVelocityFlyer.stop sends a zero four-component command when launching or running and explicitly does not try to land the flying drone. (upstream_code: src/flock_simple_path.py:202-215)
- FlockSimplePath publishes the relative cmd_vel Twist topic and subscribes to absolute /start_mission, /stop_mission and /tf; it creates no service or action server. (upstream_code: src/flock_simple_path.py:347-367)
- FlockSimplePath::flyer_cmd_callback passes the flyer's four velocity components through to a geometry_msgs::msg::Twist and publishes it. (upstream_code: src/flock_simple_path.py:430-440)
