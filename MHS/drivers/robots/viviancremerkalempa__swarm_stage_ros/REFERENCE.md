## Actions

### `publish_target_pose`

`x-cap.viviancremerkalempa.target_pose.v1` on `main`: invoke, risk R2, extension.

Publish one turtlesim/Pose x/y target for robot_0 on /robot_0. The pinned follower ignores the message theta and computes its heading from the target direction. The receipt confirms only that rosbridge accepted the publication; the follower sends no arrival, motion or stop acknowledgement.

Inputs:

| Field | Type | Unit | Required | Limit | Description |
|---|---|---|---|---|---|
| `x` | number | m | yes | operator required (not set) | Target x coordinate in the map frame |
| `y` | number | m | yes | operator required (not set) | Target y coordinate in the map frame |

Outputs:

| Field | Type | Unit | Description |
|---|---|---|---|
| `submitted` | boolean |  | True when rosbridge accepted the turtlesim/Pose message for publication |
| `confirmed` | boolean |  | Always false: the pinned controller sends no queue, motion or stop acknowledgement |

## Safety

- E-stop: software, latching, no native stop (software latch only).
- Safe state: No acknowledged ROS stop is declared: the clone registers no stop, pause or reset service or action, so the e-stop fails with the latch held, which only refuses this driver's publications; Stage keeps running and each posctrl follower keeps publishing Twist commands until it is within 0.3 of its last target. A zero-Twist publication and killall stageros (respawned by the launch) are not safe-state evidence. (achieved by nothing declared).
- Operator-required limits not yet set: `publish_target_pose.x`, `publish_target_pose.y`. Hardware use is refused (MHS.SAFETY.LIMITS_UNSET) until site-limits.json supplies them.
- OpenMHS is not a safety certification and not a safety-rated channel; the physical e-stop stays authoritative.
