# Package composition: several typed resources in one driver package

One driver package can now serve capabilities whose catalogue classes accept different resource kinds, such as a stable image (`sensor.camera`) and a stable point cloud (`sensor.depth`), as one device with several typed resources. A driver declares `extra_resources` and binds an action to one with `Action(resource=...)` or `@action(..., resource=...)`; each binding resolves against its own resource's kind on the core's existing multi-resource device, and the device keeps one backend object, one bridge and transport, one e-stop latch and one lifecycle. No catalogue compatibility rule was loosened. The RealSense ROS package is repaired on this basis and passes its gate on the fake backend; nothing ran on hardware.

## Why

The read-only RealSense preflight (`work/handoff-runs/mhs-build-20261102/completion-audit/realsense-primary-workflow-preflight-v1`) found that the one-class package path resolves every binding against one `device_kind`, while the stable image class accepts only `sensor.camera` and the stable point-cloud class only `sensor.depth`. The blocked-package triage reproduced it: one image binding with color `rgb8` and depth `16UC1` sources passes, and adding `cap.sensing.point_cloud.v1` fails `G3.DEFINITION` under either kind. The core already keys bindings by `(capability_id, resource)`, resolves each against its own resource's kind in strict mode, grants sessions per binding, reads every resource for receipts and exposes per-resource MCP routes; only the driver model, the manifest builder, the decorated and ROS runtimes and gate G6 assumed one resource.

## Design (bounded)

- Declaration: `extra_resources = {"pointcloud": {"kind": "sensor.depth", "title": "..."}}` on a decorated `Driver` or a `RosDriver`; an action names its resource with `resource=` (default: the main resource). Every other family refuses `extra_resources` (`the <family> family serves one resource`), because its bridge cannot route a second resource.
- Definition rules, all `DriverDefinitionError` before any backend object exists (gate `G3.DEFINITION`, load refusal): at most 7 extra resources; ids like `resource_id` and distinct from it; catalogue kinds; titles without control characters; every extra resource bound by at least one action; an action's resource must be declared; each binding resolves against its own resource's kind (messages for the main resource are byte-identical to before); a capability id is still bound once; in `RosDriver` a command map's own `resource` key is not authority and must equal the declared binding resource, like `safe_state`.
- Runtime: the manifest lists the main resource and then each extra resource (empty read-only state); an extra resource reads as `{}` without native I/O and refuses writes (`MHS.RESOURCE.NOT_WRITABLE`); a direct call naming another resource is `MHS.CAPABILITY.NOT_BOUND` in the decorated runtime and in `RosBridge`; the ROS bridge configuration lists every resource, routes each command by the declared contract and refuses (with a `resources` list) any command, read or write naming an undeclared resource.
- Gate: G6 sends each command (and its test permit) to its binding's resource and reads every extra resource against its schema; no other gate changed. The conformance suite already handled several resources.
- Reference and registry: a reference file of a device with more than one resource carries `device.resources` (`[{id, kind, title?}]`, optional in `reference.schema.json`, mirrored into `mhs/_data`) and a `REFERENCE.md` line; `MHS/registry/validate.py` checks each action against its own resource's kind, and that the list describes the device (the first entry has `device.kind`, ids are unique, and every action, measure and adjust names a listed resource). A single-resource reference is byte-identical, so no existing `reference.json`, `REFERENCE.md` or gate digest changes.
- Not in scope: several drivers or devices in one package (the loader's one-class rule stays), parameters on extra resources, the same capability on two resources, other families, atomic RGB-D packets and latched (transient-local) QoS.

## RealSense (`gh.realsenseai/realsense-ros`)

The blocked metadata-only package (DeepSeek author, source pin `7a87097c499e3b0b69518d54a8e7a9ac1924e87c`, version 4.59.1) was repaired by the model review. Resource `camera` (`sensor.camera`): `cap.sensing.image.v1` with the finite selector `color` (`/camera/camera/color/image_raw`, `rgb8`) or `depth` (`/camera/camera/depth/image_rect_raw`, `16UC1`), every pixel and the exact ROS 2 header per artifact; the complete color and depth CameraInfo and Metadata messages; the original three capabilities and resource state unchanged. Resource `pointcloud` (`sensor.depth`): the complete opt-in `/camera/camera/depth/color/points` PointCloud2 (the node publishes it only after `pointcloud.enable`, default false). The author, lock, card, pin, null signature and every original test are kept; 18 facts were added with exact citations.

Not covered, and stated in the package: infrared, aligned depth, the `rgbd` message (an atomic pair needs separate support), IMU and `imu_info`, latched extrinsics and `/tf_static` (late-subscriber delivery through rosbridge is unqualified), diagnostics, D5xx outputs, other image formats, parameter controls, `hw_reset`, the calibration services and action, the safety services and every stop path; rosbridge QoS, the deployed namespace, model, firmware and native behaviour. Independent captures are never a synchronized RGB-D pair.

## Found, not fixed

- The server reads every resource for each receipt, refused ones included; for a ROS package with topic-backed parameters each receipt costs one subscription or service call per parameter (six for RealSense). Composition adds no I/O (an extra resource reads `{}`), but the existing per-receipt cost stays.
- Package test files may not import `mhs.mcp` (gate `G3.FORBIDDEN`), so a package's MCP check lives outside the package (as for the Klintan camera); the RealSense one is `work/handoff-runs/claude-20261104/development/b3-composition/scripts/realsense_mcp_host_test.py`.
- The review tool `work/handoff-runs/review-tools/fact_overlap.py` hard-codes the workspace root, so it checks the actual tree, not a private copy.
- The rosbridge transport budget assumes base64 `uint8[]` data; a deployment that sends JSON integer arrays is refused whole at the message bound.
- A subscription whose transport send fails is reported `MHS.OUTCOME.UNKNOWN` ("a partial transmission cannot be ruled out") although a subscription has no effect, and the failed connection then answers later operations `MHS.DEVICE.NOT_READY`; both fail closed, but an observation could be classed `failed`.
- `tests/bridges/test_mcp_stdio.py` (`test_hung_init_and_close_during_startup_keep_no_cancel_for_init`) gives a freshly spawned child process 2 s to start. At a machine load average near 20 (other agents' suites) it failed in one full run and in one of three module runs; it passed 5 of 5 alone on this tree and on the unmodified snapshot. Neither the test nor `bridge/mcp_stdio.py` is touched here.
- The decorated runtime's own `safe_state()` hook forwards its caller's context; for a composed decorated driver with a safe-state action on an extra resource, a caller naming the main resource would be refused. The server's safe-state path is unaffected: it calls each action with its own binding's resource.
