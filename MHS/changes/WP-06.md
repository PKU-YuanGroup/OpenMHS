# WP-06 — Driver API, adapter loader, acceptance gate and reference fixtures

## Step 06a — driver package and loader (items 1 and 2 of WP-06)

Findings addressed: DRV-01 / DRV-04 / REGQ-02 / SIM-02 (no per-repo driver
contract and no loader: `mhs.adapter.load` now serves a driver directory or an
`mhs-adapter.json`; the CLI `serve` wiring is WP-08), SC-04 / DRV-09 / FIT-02
(read/write primitives: `@read` parameters are `readOnly` state served by
`mhs.resource.read`, `@write` parameters bind `cap.device.configure.v1`),
DRV-10 / AF-02 (reference file built from the class: facts, tags, method
names, `safety.estop.native`, `operator_required` reasons), DRV-06 /
FIT-ROS-08 (scalar returns wrapped into the class's single output field,
`sampled_at` stamped, return codes raised as `DriverFailed`), FIT-09 / LAB-02
(async methods on the WP-05 `AsyncRunner`, Status/Future returns), DRV-02 /
FIT-ROS-01 (per-element, scalar-on-array and nested limits are declarable
and land on the binding the server enforces), DRV-03 (the e-stop reaches the
native through `@estop` / family `safety_bindings`; a driver without one
reports a software-only latch, never "engaged"), SIM-03 / FIT-04 (Gymnasium,
MuJoCo, SCPI, serial and python-object families as config-only subclasses),
DRV-11 / DRV-12 (one declaration shape; limits declared once, on the field).
MISSED items covered: "mode truthfulness for fake or test backends is
undefined", "provenance for model-authored drivers", "no runtime executes the
per-repo adapter artifact", "no generic adapter host", "no way to map e-stop,
reset or interlocks to native calls".

### What changed (all new files, inside WP-06 ownership)

### Behaviour (what a driver author gets)

- Mapping (plan 3.8): one resource; `@read` -> `readOnly` property with
  `x-mhs-unit`; `@write` -> writable property + the `cap.device.configure.v1`
  binding with the limits keyed by parameter path; a parameter with both a
  getter and a setter is read back from the native, one with only a setter
  reports the last value written; `@action(cap=...)` -> the class binding
  narrowed to the method's parameters (closed, class-required members kept
  required) with `x-mhs-name` = method name; `@action(name="x-cap...")` ->
  inline schema + `x-mhs-schema-digest` (`catalog.extension_digest`);
  `long_running=True` writes `constraints.long_running` and an explicit
  `max_duration_ms` (the class's when not given); risk = max(declared,
  per-action/per-write risk, class floors).
- Fake truthfulness: a hardware driver on its `fake` or `sim` backend (the
  only other backend names; see the fix round below) is served as
  `mode: simulated`, `device_id <hardware id>/<backend>`,
  `models: [<hardware id>]`, `fidelity = FAKE_FIDELITY` (`engine fake`, `F0`,
  determinism `{kind: seeded, seed_control: none}`, `timestep_ms 0`,
  `realtime_factor 0`, `reset full`, `snapshot_restore false`, gaps
  `["transport replaced by fake backend"]`). An overlay entry for the
  hardware id is moved to the served id, so `site-limits.json` narrows the
  fake as it narrows the hardware.
- Loader rules: `backend="hardware"` needs `allow_hardware=True` and
  `state_dir`; a hardware driver at R2+ needs a valid `driver.lock.json`, and a
  model-authored one a non-null `reviewed_by` (refused before the backend is
  created); a simulated driver has no hardware backend; an
  `mhs-adapter.json` with a hardware device has no fake.
- E-stop: only a class with an `@estop` method (the most derived definition
  of each name wins; see fix round 2) overrides `Bridge.estop`, so a
  driver without one is reported `software_only` by the runtime (SAFE-045
  then needs `estop_physical_ref` or a `safe_state=True` action at R2+).
- Families keep the bridges' own rules (canonical binding `concurrency`,
  strict error codes, whole-reply interlock parses, e-stop wire ordering).

### Step 06a fix round — fail-closed backends (verification of 06a)

The 06a verifier found two fail-open paths (major) and five minors. All are
fixed inside WP-06 ownership.

What changed:

- Backend vocabulary (major). `mhs.driver.model.BACKENDS = ("hardware",
  "fake", "sim")` (the WP-08 `--backend` set). `check_class_attributes`
  makes any other backend name a definition error, and refuses a `fake`/`sim`
  entry that equals `backends["hardware"]` or uses the relative `.native`
  module (the hardware module of the templates), and a `hardware` entry on a
  simulated driver. `Driver(backend=...)` raises `ValueError` for a name
  outside the set; `build.is_fake_view` / `served_mode` / `served_device_id`
  (and so `build_manifest`) raise `ValueError` too (new `build.check_backend`).
  `mhs.adapter.load` / `load_driver` raise `LoadError(reason="backend_unknown")`
  before anything is imported or opened. Before: a hardware driver with
  `backends = {"hardware": ".native:connect", "sim": ".native:connect"}`
  loaded with `backend="sim"` was served as `mode: simulated` with no
  allow_hardware, state_dir or review gate, and its native `connect()` ran.
- Serial/SCPI fake fallback (major). `SerialDriver` / `ScpiDriver.make_bridge`
  refuse a `None` backend object on any view but the hardware one
  (`MHS.DEVICE.NOT_READY`, "the 'fake' backend produced no transport"), and
  build the bridge config of a non-hardware view without `port` / `host` /
  `visa_resource` / `visa_backend` (class attributes and options alike).
  `open_native` returns `None` for `backend="hardware"` only when the
  instance `is_hardware`. `PythonObjectDriver` refuses a `None` backend object
  the same way. Before: a fake factory returning `None` made the bridges open
  pyserial on the configured port or a TCP socket to `host:port` under a
  simulated label.
- Strict check before the backend opens (minor). `load_driver` resolves the
  device contract with `build.strict_findings(cls, backend=...)` before the
  driver is constructed and opened (decorated and declarative families), so
  a refused driver (for example SAFE-045) never calls the factory or
  `setup()`. Simulator families derive their contract from the opened
  backend and are still checked after opening; `site_limits` are checked when
  the server starts.
- `mhs-adapter.json` (minor): `backend="hardware"` on a document whose devices
  are all simulated raises `LoadError(reason="no_hardware_backend")`, as the
  driver-directory path does.
- `watchdog_ms` (minor): the runtime implements no watchdog, so a class that
  declares `watchdog_ms` must cite the device-side watchdog with a `Fact`
  whose text mentions it (`vendor_doc`/`upstream_code` with `ref`, or
  `operator`); otherwise it is a definition error. Documented on `Driver`.
- Docs: the `mhs.driver` module docstring example (plan 3.8 Bath) now sets
  `estop_physical_ref` with a SAFE-045 comment, so strict mode serves its
  hardware backend too; the `Driver`, `build`, `adapter` and family
  docstrings state the backend rules.
- Tests: `support.Bath` gets a separate hardware entry (`connect_bath`), and
  the `transcript` backend test now expects `LoadError(backend_unknown)` (an
  undeclared known name, `sim`, still gives `MHS.DEVICE.NOT_READY`). New:
  `test_build.BackendVocabularyTests` / `WatchdogTests`,
  `test_adapter.FailClosedLoadTests` (a `sim` entry reusing `.native:connect`
  is refused and the native is never called; an unknown name in the package
  is a definition error; SAFE-045 is refused before the factory and
  `setup()`), `AdapterManifestTests.test_simulated_manifest_has_no_hardware_backend`,
  and `test_families.FakeViewTransportTests` (a socket listener sees no
  connection from a fake SCPI view; serial/SCPI configs carry no port or host
  on a fake view).

Behavioural changes: backend names other than `hardware`, `fake` and `sim`
are refused everywhere (definition error, `ValueError` or
`LoadError(backend_unknown)`); a fake/sim backend can no longer be the
hardware entry point; family fake views never open a configured port or host;
`load()` refuses strict-mode failures before connecting.

Compatibility notes: no released code used other backend names (`mhs.driver`
is new in 0.9). Driver packages that share one factory between `fake` and
`hardware` must split them (as `support.Bath` now does). The WP-11 exemplars
and the templates already use `.native:connect` for hardware and `.fake:X`
for fakes.

### Step 06a fix round 2 — mhs-adapter.json transports, e-stop resolution

The second 06a verification found one blocker, one major and three minors.
All are fixed inside WP-06 ownership (`adapter.py`, `driver/base.py`,
`driver/spec.py`, `driver/model.py`, `driver/loader.py`, `tests/driver/`).

What changed:

- `mhs-adapter.json` transports (blocker; same class as round-1 major 2,
  DRV-03/MISSED "mode truthfulness"). A `serial`, `scpi` or `scpi-visa` bridge
  opens the port, host or VISA resource named in its config, and an
  `mhs-adapter.json` has no fake transport. Its device must therefore be
  declared `hardware` or `hybrid`, which puts it under the hardware rules. A
  simulated device with such a bridge raises `LoadError(reason="no_fake_backend")`
  on every backend, also next to a hardware device, before anything is
  imported or opened. Before: `load(<dir>/mhs-adapter.json)` with the default
  backend served a simulated SCPI device and sent `*IDN?`, `FREQ?` and
  `FREQ 10` to the configured host.
- E-stop resolution (major, DRV-03). `Driver.__init_subclass__` resolves the
  `@estop` role the way `driver_model()` resolves members: the most derived
  definition of each name wins. `Driver.__init__` also installs the
  `Bridge.estop` default on the instance whenever the served model has no
  `@estop`, and the unreachable `_estop_impl` branch now raises
  (`MHS.ADAPTER.SHIM_FAILED`) instead of returning `{}`. Before: a subclass
  that overrode the decorated `stop()` without `@estop` (or set `stop = None`)
  published `safety.estop.native: null`, but `mhs.safety.estop` reported
  `engaged` with no native call.
- Strict before bridges (minor). `_load_adapter` resolves every served
  manifest in strict mode with `device_from_manifest(served, None)` before any
  bridge is built. A refused device (for example `risk-floor`, SAFE-045)
  never constructs its python-object target or opens a transport.
- Driver bridge path (minor). A `kind: "driver"` bridge whose `config.path`
  is not a directory containing `driver.py` raises
  `LoadError(reason="adapter_invalid")`. Before: a path pointing back to the
  `mhs-adapter.json` recursed until `RecursionError`.
- `Action(risk=...)` (minor). The risk must be `R0`..`R3` or `None`, or
  `DriverDefinitionError` is raised. `binding_from_action` reports a risk
  assigned after construction too. Before: `"r2"`, `"R9"` or `2` silently
  left the device at its declared risk.
- Loader (cheap, from the verifier notes). The private package name now
  hashes every `*.py` file of the driver directory, subpackages included
  (skipping `__pycache__` and dot directories). A change inside a subpackage
  is now imported again.

Tests (`tests/driver` 112 -> 118):

- `test_runtime.EstopResolutionTests`: an undecorated override and
  `stop = None` give `software_only`, `native: null`, the latch held and no
  native stop called. A re-decorated override is the native stop.
- `test_adapter.AdapterManifestTests`: a simulated `scpi`, `scpi-visa` or
  `serial` device is refused on fake, sim and hardware, and next to a
  hardware device, while a socket listener sees no connection; a strict
  `risk-floor` refusal leaves the python-object factory uncalled (the marker
  file is absent); a driver bridge must name a driver directory.
- `test_spec.ActionTests`: risk validation.
- `LoaderTests.test_a_changed_file_is_imported_again` also covers a
  subpackage file.
- Mutation check (scratch `wp06-06a-fix2/mutants.py`): undoing the strict
  pre-check or the transport rule makes the new adapter tests fail.

Behavioural changes:

- An `mhs-adapter.json` can no longer serve a simulated serial or SCPI
  device. Serve a driver directory with a `fake` backend (a transport
  object) instead, or declare the device hardware.
- A Driver subclass that overrides its base's `@estop` method must decorate
  the override again to keep a native stop.
- Invalid `Action` risks are definition errors.

Compatibility notes: there are no in-tree `mhs-adapter.json` files with
simulated serial or SCPI devices. Python-object bridges on simulated devices
are unchanged: the loader cannot tell a Python simulator object from an SDK
object, so the manifest author's `mode` is trusted there, as before.

## Step 06b — the acceptance gate, the CLI, mhs.testing and the tutorial (items 3, 4, 5 and the tests of 8)

### What changed

New modules in `MHS/sdk/src/mhs/driver/`:

- `check.py` — `run_check(dir, backend="fake", *, root, clone,
  write_report, gates, inner, timeout_s)` with gates G1–G9 (plan 3.9,
  HANDOFF §5), `format_report`, `CheckUsageError`. The report follows
  `check-report.schema.json` (validated before it is returned; written to
  `<dir>/check-report.json` unless `write_report=False`); `report_digest` is
  the JCS digest of the report without it. Exit codes (CLI): 0 pass, 1 fail
  (failing gate ids printed), 2 usage (missing directory, `--backend
  hardware`, unknown gate). Only `fake` and `sim` backends are gated.
- `behaviour.py` — gate G6 (`BehaviourRun`, `Session`, `Endpoint`).
- `upstream.py` — `UpstreamTree` (reads the clone at the pinned commit from
  the git object store with `git --no-optional-locks cat-file/grep/ls-tree`,
  never a checkout or a write; a non-git clone or the synthetic `vendor/` is
  read as a working tree), `class_surface` (AST of the native class, its
  methods, properties, class and instance attributes, `__slots__`, constant
  `setattr`, bases followed inside the clone through imports; external bases,
  `__getattr__` and dynamic `setattr` leave the surface "open"), `parse_ref`,
  `safe_relpath`. Upstream code is parsed, never imported.
- `package.py` — `reference_documents` / `write_reference` /

### Step 06b fix round — the gate fails closed (verification of 06b)

The 06b verification failed on three fail-open paths. All three are fixed,
and so are the minor issues it listed.

**Blocker: package code could make the gate exit 0.** A `driver.py` with
`raise SystemExit(0)` or `os._exit(0)`, or a `fake.py` ending in `sys.exit()`,
used to end the gate with status 0, no output and no report.

- `python3 -m mhs.driver check` (now `check.run_check_isolated`) never
  imports package code. It runs the gates in a child process,
  `python -m mhs.driver._gate`, whose network and device files are disabled
  (`_repotests.guard_process`). It exits 0 only when that child wrote a report
  that validates against `check-report.schema.json`, whose `report_digest`
  checks out, and whose process exited 0. If the child ends without such a
  report (`os._exit`, a signal, a crash), the gate fails with
  `<gate>.ABORTED`, blaming the gate that was running (from the child's
  progress file; the import of `driver.py` counts as G3). A hang past
  `GATE_TIMEOUT_S` (900 s) fails with `<gate>.TIMEOUT`. Gates that had already
  finished keep their results. In every case `check-report.json` is written
  and the failing gate ids are printed.
- In the child and in-process (`run_check`, `mhs.testing.check_driver`), a
  `SystemExit` raised by package code becomes a finding of the gate that was
  running, never an exit. This covers the driver import (`G3.IMPORT`), the
  backend import (`G3.BACKEND_IMPORT`), every gate runner (`<gate>.CRASH`),
  G5, G6, G8 and the driver close. Only `KeyboardInterrupt` propagates.
- G9 now requires the result file of the test runner. `_repotests --result`
  writes it after the cases have run and then ends with `os._exit`.
  `SystemExit` at import or in a fixture gives `G9.FAILED`. A
  `test_driver.py` that exits early (for example `os._exit(0)` in a test)
  gives `G9.NO_RESULT`.

**Major: package code could switch the gate off.** Previously, a `driver.py`
that monkeypatched `mhs.driver.check._g3/_g6/_g8` passed an R2 driver that
had no e-stop.

- The runner table, G9, the clone re-check, the progress emitter and the
  report builder are bound before any package import. The gate modules
  (`_GATE_MODULES`) are imported first.
- Before the import, every loaded `mhs` module is fingerprinted: identity and
  `__code__`/defaults of functions, the function and descriptor members of
  classes, constants, and the module-level containers of the gate's own
  modules. The fingerprint is compared again after the import and after every
  gate. Any change fails G3 with `G3.GATE_TAMPERED`, and G9 is then not run.
  The child also reports tamper events in its progress file, and the parent
  enforces them. The parent fails every gate that has an error finding,
  whatever status the child wrote.
- A static scan (`check.static_findings`, using `ast` only, so nothing is
  imported) runs in G3 and again in the parent. It reports `G3.FORBIDDEN`
  for package code that:
  - imports the gate, the conformance harness or runtime internals
    (`mhs.driver.check/behaviour/_repotests/_gate/upstream`,
    `mhs.testing.recorder`, `mhs.conformance*`, `mhs.server`, `mhs._server*`,
    `mhs.mcp`) or interpreter internals (`builtins`, `gc`, `ctypes`, `cffi`);
  - patches `mhs` (an assignment into an object imported from `mhs`,
    `setattr`/`delattr` on one, or `mock.patch` of `mhs.*`);
  - exits the interpreter (`sys.exit`, `os._exit`, `os.abort`, `os.kill`,
    `exit()`, `quit()`, `SystemExit`);
  - reaches into the interpreter (`sys.modules`, `sys._getframe`, `settrace`,
    frame attributes, `__builtins__`, assigning `__code__`/`__dict__`/...).

  The scan skips the `if __name__ == "__main__":` block and the synthetic
  tutorial's stand-in clone. A package file that cannot be parsed is
  `G3.SYNTAX`.

**Major: a fake backend could be the upstream hardware class.** For a
hardware driver, G3 now refuses:

- `backends["fake"|"sim"]` equal to `native` (`G3.FAKE_IS_NATIVE`);
- a package fake that is, or derives from, the `native` class (MRO check after
  the package import; `G3.FAKE_IS_NATIVE`);
- a fake outside the package or the SDK (`G3.FAKE_OUTSIDE_PACKAGE`), unless
  the card's `mock_strategy.preferred` is `"upstream-sim"`. Even then, the
  simulator must not be `native` or derive from it. The gate checks this in
  the clone's AST and does not import the simulator; `upstream.Surface.classes`
  lists the classes visited.

G5, G6 and G8 do not run after a G3 failure, so the hardware class is never
instantiated. As a second line of defence, the gate's child process refuses
opens of device files under `/dev` (the standard streams, `/dev/null`,
`/dev/urandom`, `/dev/tty` and `/dev/fd/*` stay allowed) and non-loopback
sockets. G9's child does the same.

**Minors.**

- Recorder phases are now attributed by code identity. A contract-method name
