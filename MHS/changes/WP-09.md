# WP-09 — Specification realignment: one trustworthy spec for the SDK as it is

MHS/spec now describes the 0.9 SDK as it behaves: a short normative `core.md` (87 `CORE-nnn` rules), a `driver-profile.md` and a `profiles.md`, a README that fixes the precedence (schemas, core, driver profile, chapters 01 to 10, appendices, informative `00-architecture.md`), the earlier followups written into their chapters, a `spec_doctest.py` that runs the examples and lints the ids, and no legacy names outside appendix D.

The rule of the work package: the code and its tests are reality. Where the old text and the code disagreed, the text was changed; where the code itself looked wrong or unsafe, the text records the behaviour and the item is listed under "Followups" with evidence, and no SDK source, schema, catalogue or site file was touched.

## 5. The tool: `spec_doctest.py`

```
python3 MHS/sdk/tools/spec_doctest.py MHS/spec                 # run, validate, lint (exit 0 / 1 / 2)
python3 MHS/sdk/tools/spec_doctest.py MHS/spec --no-run         # lint only
python3 MHS/sdk/tools/spec_doctest.py MHS/spec --check-catalogue
python3 MHS/sdk/tools/spec_doctest.py MHS/spec --write-catalogue
```

It checks, over every `*.md` file of the directory:

- **Runnable blocks.** A Python fence whose first line is `# runnable` (the info string `python runnable` is also read) runs in this process, in a fresh namespace, with the repository root as working directory and `MHS/sdk/src` on `sys.path`, under a timeout. A block that raises, exits or hangs fails with its file and line.
- **Validated JSON.** A `json` block is validated against a shipped schema when the sentence of the paragraph directly above it says "valid against [`x.schema.json`](...)" (the form the specification uses), or when the fence info string says `validate=x.schema.json`, or when the line above is `<!-- validate=x.schema.json -->` (the two forms for other documents). Other `json` blocks that neither parse nor look abridged give a warning.
- **Fences.** The info string of every fence is one word (`[A-Za-z0-9_.+-]*`). One word is read as a fence by every renderer; the first scratch build of the site did not read anything else (with `json validate=...` it took the closing fence for an opening one and swallowed the headings that followed, section 8 deviation 10), and the site owner has since fixed that renderer.
- **Identifiers.** Definitions are paragraphs starting `**AREA-NNN.**` (chapters) or `**CORE-NNN:**` / `**DRV-NNN:**`; an id defined twice, or referenced and defined nowhere, is an error; summary lines such as `**GOV-001** text` are references.
- **Keywords and names.** The informative documents (`00`, appendix C, appendix D) contain no capitalised RFC 2119 word; `MHS Editors`, `MHS-1.0` and `Draft 1.0` appear nowhere and the legacy domain only in appendix D.
- **Codes and links.** Every `MHS.AREA.CODE` named in `core.md`, `driver-profile.md`, `profiles.md`, the README and appendix C is registered in `errors.json`; relative links and anchors resolve.
- **Generated section.** Section 7 of chapter 03 equals the rendering of `capabilities.json` (`--check-catalogue`, `--write-catalogue`).

## 8. Deviations from the brief

1. **Final ids of the replaced rules.** The earlier note named `CORE-020` (for `SAFE-011`), `CORE-044` (for `PROTO-011` / `OP-010`) and `CORE-081` (for `TPT-050` / `TPT-052`). `core.md` is organised by topic, so the rules live at `CORE-060`, `CORE-100` and `CORE-136` / `CORE-137`; the "replaced by" marks use those.
2. **Colon format for Core and Driver ids.** `**CORE-nnn:**` and `**DRV-nnn:**`, not `**CORE-nnn.**`, because `build_applicability.py` fails on an unknown area (it cannot assign profiles). Consequence: F9.
3. **`gen_appendices.py` prose.** Four lines of prose in `MHS/sdk/tools/gen_appendices.py` were edited because the appendices may be changed only through the generator and the non-conforming id and the legacy reference live in its text. No logic changed.
4. **Test edits.** Three existing tests were edited (list in 2.4), all forward-compatible; no test was weakened.
5. **`HOST-089a` left the normative text.** B52 asked for it. It is an id removed from the chapters (no id was renumbered, no id was added to a chapter).
6. **Two `MUST`s were reversed, not only clarified.** `ADPT-008` (a bridge "MUST refuse" an incompatible licence) and `ADPT-024` (clamping inside a wider envelope was allowed) now say what the SDK does. They are the two places where the text of an existing requirement changed meaning; the maintainers should read them.
7. **Appendix C was rewritten**, not patched (1076 to 599 lines), so that every example is either run or schema-validated.
8. **A last read of the text against the code corrected one error of mine.** `SAFE-045` had said that an e-stop of `kind` `hardware` needs no `physical_ref`; the static check (`mhs/_server/strict.py:354`) and its test refuse that, so the text now requires the `physical_ref` for `hardware` as well as for `both`.
9. **`applicability.json` counts moved** from 580 ids / 267 `not_verified` to 581 / 268 as the tool computes them; I did not trace the one-id difference beyond `CAP-046` replacing the non-conforming `MHS-A-001` and `HOST-089a` leaving the text.

10. **Four fences were changed after a site build.** They read `json validate=<schema>`; the first scratch build of the site read only one-word info strings as fences and swallowed the headings after them (six errors in the site check: broken fragments in `00`, `01`, `02` and a page over budget). They are plain `json` fences now, the schema is named in the sentence above, `spec_doctest.py` learnt that form and lints for the old one, and a test pins both. The site owner has since taught the renderer the long form too; the one-word form stays because every renderer reads it. The README (section 6) and the docstring of `spec_doctest.py` still give the old renderer as the reason for the rule; both were left as they are after the freeze of `MHS/spec` and `MHS/sdk`.
11. **`00-architecture.md` was shortened** (1260 to 1129 lines) because its page was 106 KiB against the 100 KiB budget: the 26-row method table (a second copy of `02` section 3) became a grouped list, section 1.4 and the embedded example were tightened, and four bold phrases that crossed a line break (the renderer cannot read them) were re-wrapped in `00`, `04` and `10`. The site owner has since split the page; the shorter text is kept because the table was a copy that could drift.

## 9. Maintaining it

- After any edit of `MHS/spec/*.md`: `python3 MHS/sdk/tools/build_applicability.py` (line numbers), `python3 MHS/sdk/tools/gen_appendices.py --check`, `python3 MHS/sdk/tools/spec_doctest.py MHS/spec`, then `python3 tools/build_changelog.py` when a fragment was added.
- A new Core rule gets the next free `CORE-nnn` and is defined once, in `core.md`; a chapter rule that the core restates is cited, never copied.
- Chapter 03 section 7 is never edited by hand: `spec_doctest.py --write-catalogue`.
- RFC 2119 words belong to `core.md`, `driver-profile.md`, `profiles.md` and chapters 01 to 10 only.
- Fences have a one-word info string, a validated JSON example names its schema in the sentence above it, and a bold or italic phrase stays on one line: the portable forms, which the site renderer reads without exception. Before a release build the site into a scratch directory (`build.py --out DIR`, then `check.py --site DIR`); the spec must not grow past the page budget (`core.html` is at 95.5 KiB of 100).
