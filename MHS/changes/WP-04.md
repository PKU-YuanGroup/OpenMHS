# WP-04 — Server safety core and runtime semantics

Sub-steps are serialized; each section below is one merged step.

## 4a1 — E-stop, reset and safe-state semantics (unconditional; no strict flag)

Findings addressed: SDK-01, SDK-02 (in-process part), DRV-03, SPEC-03 (endpoint
part), SDK-11 (reset part), SURF-01 (endpoint part: reset never resumes), the
MISSED items on safe-state/stop exemptions (`vstop`), `cap.motion.estop.v1`
routing, `_achieve_safe_state` any-success semantics and the fit-robots-ros
`estop_probe` (no preemption). Plan 3.6 "rules that apply unconditionally" (e-stop, reset).

### What changed (`MHS/sdk/src/mhs/server.py`)

- **E-stop latches first.** `mhs.safety.estop` (now self-bounded, no longer run
  through `_dispatch_bounded`) and `mhs.command` on a bound
  `cap.motion.estop.v1` both go through `_engage_estop`:
  1. under `self._lock`, before any bridge I/O: set the latch, call the
     persistence hook `_persist_latch` (no-op until 4f writes it to
     `state_dir`), set `cancel_event` (reason `emergency stop: <reason>`) on
     every running operation of the device, revoke the device's permits
     (SAFE-036);
  2. run the stop path in a daemon worker (`mhs-estop-<device>`): the native
     e-stop (`Bridge.estop(reason)` when the bridge implements it, otherwise a
     bound `cap.motion.estop.v1` binding, otherwise none), then every
     `safe_state.achieved_by` action, then the bridge's own
     `safety_status().safe_state.achieved`;
  3. wait at most `safety.estop.latency_ms` (1000 ms when undeclared) and never
     past the caller's `deadline_ms`.
  The receipt is `completed` only when every step succeeded. A timeout, ANY
  exception (not only `MHSError`), a failed or unbound safe-state action, the
  bridge reporting `achieved: false`, or a hardware/hybrid device with no stop
  path at all give a `failed` receipt with `MHS.SAFETY.SAFE_STATE_UNREACHED`
  (`error.details.reason` = `timeout | native_failed | action_failed |
  safe_state_unbound | no_stop_path | bridge_reports_unsafe`). The latch stays
  engaged. Retryable failures are retried in the background
  (`mhs-estop-retry-<device>`, back-off 0.25 s doubling to 5 s) until the stop
  path succeeds or the device is reset; the success is appended as a
  `completed` `cap.internal.safety_estop.v1` receipt whose output carries
  `confirms: <command_id of the failed receipt>`, and `safety.status`
  reports `estop.confirmed`. An e-stop receipt never waits on a hung device:
  its state hash is read with a 100 ms bound when the stop path is still
  running.
- **No session needed.** A live session supplies the principal; an expired
  session keeps its principal and id for attribution; an unknown or missing
  session gets a transient `mhs_s_<ULID>` and the principal from
  `_estop_principal` (`{"id": "anonymous", "kind": "agent"}` until 4b binds
  principals to tokens). Any device of the endpoint can be stopped, whether or
  not the session covers it. A malformed `command_id` no longer refuses the
  e-stop (a fresh ULID is used); a replay of a retained e-stop `command_id`
  while still latched returns the retained receipt.
- **Default `Bridge.estop`.** A bridge that does not override the base no-op
  reports `output.estop: "software_only"` (`"engaged"` when a native stop
  returned, `"failed"` when it raised, `"timeout"` when it had not answered).
  On a simulated/replay device a software-only latch is a `completed` e-stop;
  on hardware/hybrid with no native stop and no `achieved_by` it is
  `SAFE_STATE_UNREACHED` (`no_stop_path`).
- **`safe_state.achieved_by`.** Validated at construction: an id that is not a
  bound capability raises `ValueError` on hardware/hybrid devices; on
  simulated/replay devices it emits a `RuntimeWarning` and every e-stop of that
  device reports it as a failed action (`safe_state_unbound`, not retried).
  `_achieve_safe_state` (also used after a cooperative cancellation) now has
  all-must-succeed semantics.
- **Exemptions.** Stop classes (`cap.motion.stop.v1`, `cap.motion.estop.v1`)
  and every `achieved_by` action are exempt from the latch, permits
  (`_permit_required`), cumulative budgets (`_check_limits`) and the exclusive
  device lease (SAFE-029). Interlocks, schema and min/max limits still apply.
- **Latch scope.** The latch check moved out of `_check_interlocks` to plan 3.6
  step 5 (after command-id replay, before schema validation) and is re-read
  atomically with operation registration in `_start_operation(latch_check=...)`,
  so a command that passed its (slow) pre-checks before the e-stop is refused
  instead of executing after it (repro e7 b). Effectful commands get
  `MHS.SAFETY.ESTOP_ENGAGED`; read-verb capabilities stay callable;
  `mhs.restore` is refused while latched.
- **Cancellation receipts.** The operation worker treats
  `mhs.signals.Cancelled` and the legacy `{"cancelled": true}` output (only
  once cancellation was requested) as `cancelled`, so an e-stop or
  `operations.cancel` of a cooperative operation (reference conveyor delay)
  receipts `cancelled` instead of `completed`.
- **Reset (SAFE-041/042/043).** `mhs.safety.reset` returns a `rejected`
  `MHS.SAFETY.RESET_REFUSED` receipt, without calling `bridge.reset()`, when:
  nothing is latched (`not_latched`; "latched" = the endpoint latch or a latch
  the device reports itself via `safety_status()` `latched`/`estop.engaged` or a
  declared boolean `latched` state field); an effectful operation that ignored
  its cancellation is still running (`operation_running`); any declared
  interlock not marked `reset_exempt` reads `open` or `unknown` — unreported or
  unreadable counts as unknown (`interlock_open`, with `error.interlocks`). A
  bridge refusal becomes `RESET_REFUSED` (`bridge_refused`, `bridge_code`); a
  non-MHS exception is a `failed` receipt and the latch stays. A completed
  reset clears the latch, stops the background retry and never resumes
  anything (`output.resumed: false`); a new command is required.

## 4a1 (fix round) — verifier findings on e-stop/reset semantics

Fixes the independent verification of 4a1 (two blockers, one major, the cheap
minors).  Same findings as 4a1 (SDK-01, SDK-02, SDK-11, SPEC-03, DRV-03, SURF-01
endpoint part) plus the verifier probes `p_race_reset`, `p_verb`, `p_hung_read`,
`p_params`, `p_hello` (`scratch/verify-WP-04/4a1/probes/`).  Where this section
and the 4a1 section above disagree, this section wins.

### What changed (`MHS/sdk/src/mhs/server.py`)

- **Reset race (blocker).** Every engaged e-stop bumps a per-device sequence
  number (`_estop_state[did]["seq"]`) under `self._lock`, next to the latch.
  `mhs.safety.reset` reads it under the lock before its checks and releases
  the latch only when it is unchanged after `bridge.reset()` returned.
  Otherwise the reset is `rejected` `MHS.SAFETY.RESET_REFUSED` with
  `details.reason: "estop_during_reset"` (`bridge_reset: "completed"`,
  `latched: true`), the latch stays, and the stop path is run again after the
  bridge reset (`_reassert_estop`, bounded by the e-stop budget and the
  reset's remaining deadline; `details.stop_reasserted`; an unconfirmed
  re-assertion is retried in the background).  This covers a reset whose
  caller was already answered `MHS.OUTCOME.TIMEOUT` by `_dispatch_bounded`:
  an e-stop after the timeout survives the late reset.  In addition, a reset
  whose caller was answered `TIMEOUT` before the handler reached
  `bridge.reset()` (slow interlock read) is not performed: a `failed` receipt
  with `MHS.OUTCOME.TIMEOUT`, `details.reason: "deadline_exceeded"`,
  `bridge_reset: "not_called"` (the dispatcher now flags abandoned handlers
  through `self._dispatch_local.abandoned`).  A reset already inside
  `bridge.reset()` when the caller timed out still finishes and is receipted
  as before (RE-PROTO-004 `test_reset_deadline_is_truthful_and_reconcilable`).
- **Declared-verb latch bypass (blocker, regression of 4a1).** New
  `_is_read_capability`: a `cap.*` binding counts as a read only when its
  declared verb *and* its catalogue verb (`mhs.catalog.get(id)["verb"]`, cached
  per server) are `read`; an extension id (`x-cap.*`, `cap.x.*`) keeps its
  declared verb; an uncatalogued `cap.*` id or an unloadable catalogue is not a
  read.  Used for the latch exemption in `_run_command` (and the atomic
  re-check in `_start_operation`) and for the reset's `operation_running`
  check.  `cap.motion.move.v1` bound with `verb="read"` is again refused with
  `ESTOP_ENGAGED` while latched, with no bridge call.
- **Bounded e-stop receipt (major).** The receipt's state-hash read is always
  bounded: `max(2 ms, min(100 ms, remaining caller deadline))`, whether or not
  the stop path finished.  `p_hung_read`: 3002 ms -> 106 ms.  No other bridge
  I/O is on the e-stop response path (`safety_status()` runs in the attempt
  worker).
- **Generic gates (minor).** `mhs.safety.estop`, and `mhs.command` naming
  `cap.motion.estop.v1`, skip the `mhs.hello` and `deadline_ms` gates
  (`_is_estop_request`; gate logic moved to `_dispatch_gate_error`).  The
  handler sanitises its own budget (`_estop_deadline_ms`: a valid integer is
  clamped to 600000 ms; missing, non-integer, bool, 0 or negative means the
  device's e-stop budget).  Unchanged: an unknown `device_id`, or no
  `device_id` on a multi-device endpoint without a single-device session, is
  still an error (see followups).
- **`cap.motion.estop.v1` via `mhs.command` (minor).** Routed in `_m_command`
  before the session, mode, ULID and input checks (`_command_estop`): an
  unknown, expired or missing session, a malformed `command_id`, a non-object
  `input` or a missing deadline all latch.  When the target device does not
  bind the class the ordinary path (and the skipped gates) apply.  The
  routing in `_run_command` stays as a guard for other callers.
- **Operation worker (minor).** The worker checks `cancel_event` before
  `bridge.call`; an operation cancelled after registration but before dispatch
  is receipted `cancelled` and never reaches the bridge.  The e-stop no longer
  sets `cancel_event` on running stop-class / `achieved_by` operations.
- **Confirmation ordering.** `_confirm_estop` records the confirmation
  receipt before `safety.status` reports `estop.confirmed: true` (and leaves
  the state alone if a reset intervened).  This fixes an intermittent failure
  of `test_failed_native_estop_is_retried_in_the_background` under load
  (seen in the pre-fix full SDK run).
- Not changed: the capability-less synchronous branch of `_run_command` is
  unreachable (`mhs.command` and `mhs.resource.write` always resolve a
  capability, so every effect runs as a registered operation).

## 4a1 (fix round 2) — verifier findings r1 on the background retry and reset

Fixes the second independent verification of 4a1 (one major, four minors).
Probes: `scratch/verify-WP-04/4a1/r1/probes/q_supervisor_race.py`,
`q_supervisor_race_gap2.py`, `q_reset_unconfirmed.py`, `q_restore_race.py`.
Same findings lineage as 4a1 (SDK-01, SDK-11, SPEC-03, DRV-03).  Where this
section and the sections above disagree, this section wins.

### What changed (`MHS/sdk/src/mhs/server.py`)

- **Background retry per latch generation (major).** A retry supervisor
  serves exactly one latch generation (a reset bumps it) and ends on its own
  within one 50 ms poll after it changed.  `_ensure_estop_supervisor` records
  `_estop_state[did]["supervisor_generation"]` and starts a new supervisor when
  the live one serves an older generation (before, a live old-generation
  supervisor made a failed e-stop right after a reset report
  `retrying: true` with no retry ever run).  It starts nothing when the
  generation it is asked for was already reset.  `_supervise_estop` reads the
  current attempt atomically with its generation check.
- **Reset never runs alongside the stop path (minor; also the precondition of
  the major).** `mhs.safety.reset` is refused with `RESET_REFUSED`
  `details.reason: "stop_path_pending"` (bridge not called, latch kept) while
  the current e-stop attempt has not finished (the native e-stop has not
  answered).  Checked with the other refusals and re-checked atomically when
  entering `bridge.reset()`.  While a reset is inside `bridge.reset()` the
  background retry does not start a new attempt (`resetting` counter), at most
  until that reset's deadline (`reset_hold_until`), so a hung
  `bridge.reset()` cannot hold the retry back for ever.  A reset whose
  `bridge.reset()` returns while such a retry is in flight keeps the latch
  (`stop_path_pending`, `bridge_reset: "completed"`).  Invariant: the latch is
  released only when no e-stop was engaged during the reset and no stop
  attempt is running.
- **Restore re-checks the latch (minor).** `mhs.restore` re-reads the latch
  under `self._lock` after the (possibly slow) rollback `bridge.snapshot()`
  read, right before `bridge.restore(state)`, and refuses with
  `ESTOP_ENGAGED` (in-flight entry finished).  An e-stop that lands while
  `bridge.restore()` runs (seq changed) re-asserts the stop path afterwards
  (`_reassert_estop`, not awaited; retried in the background until confirmed),
  because the restore may have rewritten the state the stop had reached.  The
  tail of `_m_restore` moved unchanged into `_restore_and_receipt`.
- **Safe-state actions do not wait for a hung native stop (minor).**
  `_run_estop_attempt` runs the native e-stop (`Bridge.estop` or a bound
  `cap.motion.estop.v1`) in its own daemon thread
  (`mhs-estop-native-<device>`); the `safe_state.achieved_by` actions start as
  soon as it answered or once the device's e-stop budget
  (`safety.estop.latency_ms`, default 1000 ms) is spent, whichever is first.
  The attempt finishes only when both are done, so the receipt and
  `estop.confirmed` stay truthful.  With a native stop that answers, the order
  is unchanged (native first, then the actions).
- **Extension ids are latched (minor, fail closed).** `_is_read_capability`
  no longer trusts the declared `verb="read"` of an extension id (`x-cap.*`,
  `cap.x.*`), whose verb the catalogue cannot confirm: while latched such a
  command is refused with `ESTOP_ENGAGED` (as every command was before 4a1),
  and a running one blocks the reset (`operation_running`).  Catalogued read
  classes declared `read` stay callable.
- `_fresh_estop_state()` builds the per-device bookkeeping (new keys
  `supervisor_generation`, `resetting`, `reset_hold_until`);
  `_stop_path_pending(state)` is the shared check.

### What changed

`MHS/sdk/src/mhs/server.py`:

- **HTTP hardening** (`_make_handler`).  Every route checks, in order: the
  `Host` header must name `localhost`, `127.0.0.1`, `[::1]`, the bound address
  or a `MHSServer(allowed_hosts=...)` entry (case-insensitive, port ignored;
  missing Host refused) -> else 403 `MHS.AUTH.FORBIDDEN`; an `Origin` header,
  when present, must be the endpoint's own loopback origin (same port) or a
  `MHSServer(allowed_origins=...)` entry (`null` refused) -> else 403; with
  `MHSServer(auth_tokens={token: principal})` every route but
  `/.well-known/mhs.json` needs `Authorization: Bearer <token>`
  (`hmac.compare_digest`) -> else 401 `MHS.AUTH.UNAUTHENTICATED` with
  `WWW-Authenticate: Bearer`, and the well-known descriptor advertises
  `auth: ["bearer"]`.  `POST /mhs/v1/rpc` needs `Content-Type:
  application/json` exactly (parameters allowed; missing, empty, form or
  text types -> 415 `MHS.PROTOCOL.INVALID_REQUEST`, TPT-011).  `GET
  /mhs/v1/rpc` -> 405.  Every early refusal closes the connection, so an
  unread body is never parsed as the next request.  Every connection has a
  socket timeout (`MHSServer(http_timeout_s=30.0)`).
- **Bind refusal.** `start_http`/`run_http` refuse a non-loopback host
  (`0.0.0.0`, `::`, `""`, any other address, any name but `localhost`) with
  `MHSError("MHS.AUTH.TRANSPORT_INSECURE")` unless `auth_tokens` is set, or
  `insecure_dev=True` (constructor or call argument; emits a `RuntimeWarning`).
  Principal binding from the token is not done yet (4b): the token only
  authenticates the HTTP request.
- **Schema lookups** (`_m_schema_get`, `GET /mhs/v1/schema/<ref>` and
  `?ref=`): a ref that is not a bound capability id goes only through
  `SchemaStore(autoload=False).resolve_public(ref)` on a fresh store per call
  (bare shipped file name or known `$id`; `/`, `\`, `..`, `~`, drives and
  URLs are refused with `INVALID_PARAMS` / HTTP 404).  A document a local
  caller loaded by path into the default store is never served.
- **SSE** (`GET /mhs/v1/events`): requires `?session_id=` of a live session
  (missing -> 400, unknown/expired -> 403) and drains only that session's
  subscriptions (`take_notifications_for_session`); an optional
  `subscription_id` must belong to it (else 404).  At most 4 concurrent
  streams per principal (`_MAX_SSE_STREAMS_PER_PRINCIPAL`, 429
  `MHS.LIMIT.CONNECTION_LIMIT`).  Frames carry `id: <subscription>:<seq>` and
  `event: mhs.event` (TPT-016) after an initial `retry: 3000`.  A stream ends
  when the client disconnects, the session ends or the handle shuts down.
  Subscription ids are `sub_` + 128 random bits (`secrets.token_hex(16)`);
  `mhs.unsubscribe` only works for the owning session (another session's id
  is reported like an unknown one, `MHS.SESSION.UNKNOWN`).  Permit ids are
  `permit_<ULID>_<64 random bits>`.
- **stdio** (`run_stdio`, `_StdioDispatcher`, `_StdioLane`): the reader thread
  handles `mhs.safety.estop` (and `mhs.command` on `cap.motion.estop.v1`, also
  inside a batch) itself, so the latch is set before the next line is read;
  `mhs.operations.cancel` runs at once on its own thread; every other request
  goes to a FIFO lane with one worker: the lane of the device it targets for
  `mhs.command`, `resource.read/write`, `snapshot`, `restore`,
  `safety.reset`, `safety.permit`, otherwise the endpoint lane.  At end of
  input the lanes are drained (each request is bounded by its deadline).  The
  reader now uses a blocking `readline()`: the old `select()` loop left
  pipelined lines in the reader's buffer unprocessed until more input came.
  A response that cannot be JSON-encoded becomes an `INTERNAL.ERROR` response
  instead of killing the transport; the rest of an oversized line is
  discarded.
- **Events exactly once, emitted outside `self._lock`** (`_notify`,
  `_flush_outbox`).  With a push transport (stdio) events are queued in seq
  order under the lock and written after it is released (non-blocking from
  operation workers; the stdio flusher is only a backstop); they are no longer
  also buffered (the old flusher re-sent every event, repro e4 `seqs: [1, 1]`).
  Without a push transport they are buffered per subscription as before
  (helper `_buffer_event`, unchanged gap logic).  `_notify("safety", ...)`
  (e-stop engaged/confirmed, reset) is delivered on the `control` stream with
  `type: "safety"` (the `safety` stream name was never subscribable).
- **Operation ids** are `op_` + a full 26-character ULID
  (`_new_operation_id`); registering an id that already exists raises (the
  command gets a `failed` receipt) instead of overwriting an operation.
  Operations carry a `done` event; `_run_command` and `operations.cancel`
  wait on it instead of polling every 2 ms (10,000 commands: ~3 s).
- **Session-expiry timer** (`_ensure_session_reaper`, `_session_reaper_loop`,
  `_reap_expired_sessions`, `_expire_session`): one daemon thread per server
  (weak reference; ends when no live session is left) wakes at the next
  expiry (at most every 1 s).  An expired session's running operations get
  `cancel_event` with reason `session expired` (stop / `achieved_by`
  operations are never cancelled), its permits and subscriptions are
  released, and every device that was running one of its effectful
  operations runs its `safe_state.achieved_by` actions in a daemon worker.
  The session record stays (`Session.released`) so its next use still gets
  `MHS.SESSION.EXPIRED`.
- **JSON-RPC hygiene** (`_handle_message`): an effectful method
  (`mhs.command`, `resource.write`, `restore`, `safety.reset`,
  `safety.permit`, `composition.run`) sent as a notification is dropped and
  logged (`logging.getLogger("mhs.server")` warning), never executed; an
  e-stop notification still latches (see deviations).  NaN / Infinity:
  the transports decode with `protocol.loads_strict` (PARSE_ERROR, HTTP 400)
  and in-process params containing non-finite floats get `PARSE_ERROR` too.
- **`mhs.registry.search`** is no longer an endpoint method (METHOD_NOT_FOUND;
  the registry is `mhs.registry`).
- **`mhs.conformance.report`** returns the last report stored with the new
  `MHSServer.record_conformance_report(report)` (digest must recompute,
  `subject.id` must be this endpoint or one of its devices) verbatim;

  0.9.0.dev0`.  The verdict enum has no `not_run`, hence `skip` + detail.
- **hello**: `conformance` lists only the devices' own claims (no default

  all): unresolvable path, unknown rule member (typo key, legacy `limit`),
  min/max on an object, per-element bound on a scalar or wrong length, unit
  mismatch, contradictory sources, an unknown `per` window (this replaces the
  separate SAFE-016 window check), a widening overlay, an overlay target that
  is not bound / not writable, an invalid envelope key.  Strict mode adds a
  `limits-invalid` finding to `MHSStrictError` (unless `resolve_device`
  already reported one).  Late strict devices are refused the same way
  (`MANIFEST_INVALID`, `strict_refused`); late compatibility devices are
  compiled on first use.
- **Runtime plans.**  `_limit_plan()` returns the cached plan and recompiles
  it when its fingerprint changed, so an envelope narrowed after start-up is
  enforced on the next command (the remediation tests rely on that) and one
  broken after start-up fails closed (`MHS.ADAPTER.MANIFEST_INVALID`,
  `details.reason: "limits_invalid"`).
- **Evaluation order (plan 3.6), in `_run_command`:** grant (2), binding (3),
  replay / reuse (4), latch (5), hybrid authority -- moved here from before the
  idempotency check -- and arming (6), then `_check_input`: structure with the
  bound keywords of limited fields stripped (7), `mhs.limits.check` over every
  array element and nested leaf, then `LIMITS_UNSET` (8), the full schema (9);
  then permit, then cumulative reservation (10), then interlocks (11), then
  `expected_revision` and the device lock (12).  Before: schema, limits +
  cumulative, interlocks, permit.
- **`MHS.SAFETY.ENVELOPE_VIOLATION`** details are the first violation's
  `Violation.to_details()` -- `path` (concrete, e.g. `joints[0]`), `kind`
  (`min`/`max`/`allowed`/`type`/`length`), `bound`, `value`, `unit`, `source`
  (the source label: `class`, `binding`, `envelope`, `envelope:<pattern>`,
  `overlay`), `element_name`, `limit_path`, `reason`, `provenance` -- plus
  `violations` (every violation, up to 16) and the legacy `field` (the limit
  path).  A value that cannot be compared with a numeric bound (a string, a
  bool, NaN) is a `type` violation, never a pass.
- **`MHS.SAFETY.LIMITS_UNSET`** (`details.paths`, `details.reason`): a call that
  sets a value (or relies on a schema default) at an `operator_required` path
  no overlay filled -- every mode (the driver gate G6 runs on the fake,
  simulated backend); and, strict mode only, a hardware or hybrid write/invoke
  at R1+ that sets a numeric leaf no limit covers.  Reads and stop classes are
  never refused for a missing bound.  New findings (`refuse: false`):
  `operator-required-unset` (warned as "enforced in every mode") and

- **Cumulative budgets** (`_reserve_cumulative`, replacing the second half of
  `_check_limits`): from `EffectiveLimits.cumulative` (intersected: the
  smallest budget wins), keyed `device|capability|path` as before; the amount
  is the sum of the magnitudes of the addressed values, so a negative value
  never refunds a budget.  Safe-state actions stay exempt.
- **`mhs.resource.write`**: the patched state document is now validated
  inside the command path, state before input, in steps 7 and 9, with the
  bound keywords of limited state fields stripped in step 7, so a nested 48 V
  write against a 5 V limit is `ENVELOPE_VIOLATION`, not `STATE_INVALID`.
- **Compatibility drift warning**: a call to a drifting catalogued binding
  whose input the class schema refuses gives one `MHSStrictWarning` per
  capability (served with the binding schema, as before).
- **`mhs.devices.get`** adds, per binding, `x-mhs-effective-limits`
  (`limits`, `cumulative`, `operator_required`, `unlimited`, `narrowed`) and
  the device `reference` rendered by `mhs.reference_file.render` (overlay
  recorded only when it names the device; `safety.estop.native` from the

- Removed: `_check_limits`, `SafetyEnvelope.limits_for` (the `update()`

## MERGE-B fix round (after the independent MERGE-B verification)

The MERGE-B verifier kept the 4a1 confirmation race as a major. This round

### What changed (`server.py` unless noted)

- **Major (4a1): e-stop confirmation not tied to the current attempt.**
  - **The problem.** E-stop E1 failed and its background retry succeeded.
    While the retry thread wrote the confirmation receipt, e-stop E2 started a
    new attempt whose native stop failed. Two things went wrong:
    - the old confirmation's `finally` set `confirmed: true`, so
      `mhs.safety.status` reported a confirmed stop after E2's
      `SAFE_STATE_UNREACHED` receipt;
    - the supervisor then returned, so E2 (`retrying: true`) was never
      retried.

    The verifier saw this in 8 of 10 trials of `s_confirm_race_nodelay.py`.
  - **The fix.**
    - `_confirm_estop` confirms only the current attempt. Under the lock it
      first checks the latch, the generation and `state["attempt"] is
      attempt`. If a newer attempt exists it records nothing, and those
      command ids stay unconfirmed until the newer attempt succeeds.
    - If a newer e-stop starts while the receipt is being written, the
      receipt settles the ids it names, but `confirmed` stays false and no
      `confirmed` event is sent.
    - `_engage_estop` and `_reassert_estop` set `confirmed` only for the
      current attempt of the same generation.
    - `_supervise_estop` re-checks under the lock after confirming. It serves
      a newer attempt if one exists, and otherwise deregisters itself
      (`state["supervisor"] = None`) atomically with its decision to end, so
      `_ensure_estop_supervisor` starts a new supervisor for a later failure.
      The inner retry loop also switches to a newer attempt as soon as one
      appears.
    - The confirmation receipt's state read is bounded
      (`read_timeout_s=_ESTOP_READ_BOUND_S`).
- **Minor (4a1): the reset hold delayed an e-stop pressed during the reset.**
  A reset entering `bridge.reset()` records `reset_seq = seq`. The retry is
  held only while `seq == reset_seq`, so an e-stop engaged during the reset
  (which refuses that reset with `estop_during_reset` anyway) is retried at
  once.
- **Minor (4a1): `_reassert_estop` hid a pending native e-stop.** Every
  attempt is tracked in `state["pending_attempts"]` until done, and
  `_stop_path_pending` checks all of them. A re-assert after
  `estop_during_reset` or after an e-stop during `bridge.restore()` still runs
  the stop path again, but no reset passes while an older native e-stop may
  still land.
- **Minor (4a2): `loads_strict` RecursionError** (`protocol.py`). A line of
  200,000 `[` (within 1 MiB) killed the stdio endpoint. `loads_strict` now
  maps `RecursionError` to `PARSE_ERROR`, and the stdio reader answers
  `PARSE_ERROR` for any decoder exception instead of exiting.
- **Minor (4a2): docstring** (`protocol.py`). `validate_deadline` names
  `MHS.PROTOCOL.DEADLINE_INVALID`.
- **Minor (4b): refused late devices in hello and the default session.** The
  new `_served_devices()` skips late devices that strict mode refuses. hello
  (`devices`, `features`), `/.well-known/mhs.json`, `_conformance_claims` and
  the default `device_ids` of `mhs.session.open` use it. The e-stop still
  reaches every device.
- **Minor (4b): compatibility lookalikes** (`_server/strict.py`).
  `untrusted_principal` in compatibility mode also drops top-level
  `authenticated`, `role` and `claimed_principal`, so compatibility receipts
  stay schema-valid.
- **Minor (4a2/4c): stale transcript.** `docs/e2e-transcript.txt` was
  regenerated (PASS). Normalised for timestamps, ids and digests, it differs
  only in the line number of one `MHSStrictWarning`.

### Behavioural / compatibility notes

- A device may bind one class to several resources (both modes); the same
  pair twice raises `MHSStrictError` at `Device(...)`.  Compatibility mode no
  longer warns `capability-duplicate` for one class on two resources.
- `mhs.command` with a `resource` the class is not bound to (it used to run

  `rejected NOT_BOUND`; without `resource` on a class bound several times it
  is `INVALID_PARAMS resource_required`.  Single-binding callers are unchanged.
- Revisions advance only on a state change: a completed command that changes
  nothing (or a read, or a failed call without effect) keeps the revision, so
  `expected_revision` chains no longer break on reads.  Stops always advance
  it.  Clients that counted one revision per command must read
  `state_revision_after`.
- `resource.write` needs a `cap.device.configure.v1` binding on the resource;

- Write receipts: `capability_id: cap.device.configure.v1`, output

- Replay devices: commands are `rejected MODE.READ_ONLY` before any bridge call

- Wire additions only: `capabilities[]` objects in `session.open`, one

### Decisions

- `resource_required` is a JSON-RPC `INVALID_PARAMS` error (the params do not
  name one binding, PROTO-028), not a receipt; `NOT_BOUND` is a receipt (an
  outcome of a well-formed command), also for a resource the device does not
  have (`details.resource_exists: false`).
- A session restricted to one binding still needs `resource` when the class
  has several bindings on the device (no grant-based defaulting).
- Cumulative budgets stay pooled per `(device, class, path)` across the
  resources of one class: each binding's own `per` rules apply, but draws on
  either pipette count against one pool (the conservative reading of a
  class-level budget).
- Stop classes and `achieved_by` actions always advance the revision (they are
  not delayed by a state read); e-stop, reset and restore are unchanged.
- No grant-free fallback: a session built without resource scopes
  (`granted_resources` None, only the e-stop's transient session) allows by
  class.

### What changed (`MHS/sdk/src/mhs/server.py`)

- **The revision rule fails closed (blocker).**  `_device_state_digest`
  returns hash None, which `_state_changed` treats as an unknown change and
  so advances the revision, in these cases: the device has no bridge; any
  resource read raises (including the base `Bridge.read` `unsupported`, and
  the WP-05 bridges for resources without a reads spec); a read has not
  answered in time; or the state is not canonical JSON.  Before this fix a
  failed read hashed the declared `Resource.state`, and before == after
  always held.  On such a device the revision therefore never moved, and a
  command with a stale `expected_revision` ran (p1: A moved the arm 0 -> 0,
  B with expected_revision 0 completed).  Now A goes 0 -> 1 and B is
  `rejected MHS.CONFLICT.REVISION` with `current_revision: 1`.  A read that
  fails both before and after a failed call also advances the revision.  The
  declared state is still put in the returned document for each resource
  that could not be read, but it is used only for the receipt's
  `state_hash_after` (the same fallback `_resource_state_hash` uses), never
  for the comparison.
- **Bounded state reads around a command.**  The pre-call and post-call
  device reads run in one daemon worker per digest, bounded by
  `_REVISION_READ_BOUND_S` (1.0 s).  The pre-call read is also bounded by
  half of what is left of the caller's budget (`ctx.extra["deadline_at"]`).
  A read that does not answer in time is an unknown change, so the revision
  advances, and the command proceeds without waiting for it.  A hung read
  no longer holds a command or uses up its deadline.  Test: a read blocked
  for 5 s and a 0.1 s bound give a completed receipt in well under 1.5 s.
- **Nested configure fields (`_check_configure_fields`).**  The
  `readOnly` / unknown-key rules now apply at every depth of the state
  schema:
  - In an object property that declares `properties`, an undeclared key is
    `MHS.RESOURCE.FIELD_UNKNOWN`, unless `additionalProperties` is `true` or
    a schema. In the schema case the value is walked against that schema.
  - A `readOnly` property, or anything inside a `readOnly` object, is
    `MHS.RESOURCE.NOT_WRITABLE`.
  - Array elements are checked against `items`.
  - A free-form object (no `properties`) still takes any keys.
  
  `details.fields` uses the limit path syntax, e.g. `ch1.measured_current`,
  `channels[1].reading`, `ch1.bogus`.  For p2, `{ch1: {measured_current: 9.9}}`
  is now `NOT_WRITABLE` and `{ch1: {voltage: 2, bogus: 1}}` is
  `FIELD_UNKNOWN`; the bridge is not called for either.  A non-object patch
  is left to the input schema (`INPUT_INVALID`), as before.
- **Late duplicate pairs and late binding changes.**
  - `Device._by_binding` is now a property. It re-indexes when
    `Device.capabilities` changed, compared by element identity, so a binding
    replaced, added or removed after construction is the one served.  Before,
    a replaced binding kept the stale object, with its wider schema and
    limits.  New helpers: `Device.duplicate_pairs()` and
    `Device.duplicate_findings()`.
  - `MHSServer(...)` refuses a pair appended twice before start-up with
    `MHSStrictError` `capability-duplicate` in every mode.  Strict mode
    already did this; compatibility mode used to serve the first binding.
  - A pair appended twice after start-up makes `_recompile_device_limits`
    store a device-level `capability-duplicate` error. Every command on the

### What changed (`MHS/sdk/src/mhs/server.py`)

- **The e-stop path follows the bindings served now (blocker).**  The first
  fix round made `Device._by_binding` re-index when `Device.capabilities`
  changes, but `_native_estop_path` still read the legacy view
  `Device._by_capability`, which was built once at construction.  With the
  `cap.motion.estop.v1` binding removed after start-up the path stayed
  `capability`, the native stop looped over no binding, and the receipt said
  `completed`, `estop: "engaged"`, `safe_state_achieved: true` on a hardware
  device without any stop reaching the bridge.  Now:
  - `_native_estop_path` decides on `device.bindings_of(cap.motion.estop.v1)`.
    A removed binding is no stop path: a hardware or hybrid device without
    another one gives `failed MHS.SAFETY.SAFE_STATE_UNREACHED`
    (`reason: no_stop_path`), a simulated one `estop: "software_only"`.  An
    e-stop binding added after start-up is called; before, it was ignored.
    `devices.get` publishes the reference file's `safety.estop.native` from
    the same helper, so it follows too.
  - The capability stop path fails closed: when it finds no binding to call
    it raises, so the attempt is `native_failed` (`SAFE_STATE_UNREACHED`,
    retried in the background), never `engaged`.
  - `Device._by_capability` is rebuilt with every re-index (first binding
    per class), and the start-up `safe_state.achieved_by` check uses the
    served bindings.  Nothing in the runtime decides with the legacy view
    any more.
- **An exclusive call never runs beside the server's own state read
  (minor).**  The first fix round bounded the reads around a command and
  abandoned a read that outlived its bound, so an exclusive command's
  `bridge.call` could start while its own `bridge.read` was still running
  (q2 / `q3_standalone`: `call overlapped a read: 1`).  A new `_StateRead`
  handle (`_start_state_read`, `_state_read_digest`; `_device_state_digest`
  is now a wrapper) lets the worker keep track of the reads it started:
  - exclusive command, read before the call outlives its bound: the call
    waits for it, as it would for the device lock.  The deadline still bounds
    only the response (plan 3.7: the caller gets `unknown`
    `MHS.OUTCOME.TIMEOUT` if this takes too long).  An e-stop or
    `operations.cancel` ends the wait, and the command is then cancelled
    without being dispatched.  The read's own answer is used as the hash
    before, so it is no longer an unknown change;
  - exclusive command, read after the call outlives its bound: the receipt
    is written at once (an unknown change, the revision advances), and the
    device lock is released only when the read returned.  Until then the
    next exclusive command is `rejected MHS.DEVICE.BUSY` (retryable).
  Non-exclusive commands still run beside reads, as they run beside each
  other (WP-05 followup below).
- **The read after the call answers inside the deadline (minor).**  It was
  bounded only by the global 1 s, so a fast call on a device whose state
  read takes 0.3-0.5 s, with a 400-700 ms deadline, came back
  `unknown MHS.OUTCOME.TIMEOUT` with the revision at 0 -> 0 (pre-4d:
  `completed 0 -> 1`).  It is now bounded by what is left of the response
  deadline minus a margin (`max(20 ms, a quarter of what is left)`).  An
  unanswered read is an unknown change, so the result stays fail-closed.
  Once the deadline has passed, the caller already has its answer, and the
  read gets the full 1 s bound for the final receipt.  `q3_standalone` now
  gives `completed 0 -> 1` in all three cases (0.62 s, 0.38 s and 0.00 s).
- **Start-up duplicate refusal covers strict devices (minor).**
  `_resolve_strict` reused the resolution a `Device(strict=True)` computed
  at construction, so a duplicate pair appended before
  `MHSServer(...)` started was not refused at start-up.  It was still
  refused at runtime with `MANIFEST_INVALID`.  The pairs are now counted
  again for every device: strict devices whose resolution already refuses
  them are counted once, compatibility devices as before.  The late-adoption
  path for devices added after a strict endpoint started does the same.
- **Configure fields under composition (minor).**
  `_check_configure_fields` reads each state-schema node together with its
  `allOf` / `anyOf` / `oneOf` / `then` / `else` branches and its local
  `$ref` (`#/...` inside the state schema):
  - `readOnly` in any branch makes the node read-only;
  - the keys any branch declares are declared, including through
    `patternProperties`;
  - an undeclared key is written only when every branch that declares keys
    admits more (`additionalProperties` true or a schema);
  - array elements follow `prefixItems`, then `items`.
  A `$ref` that does not resolve inside the state schema, such as an
  external URL, or a reference cycle, is `NOT_WRITABLE`, because what it
  allows cannot be known.  The same goes for an unusable
  `patternProperties` pattern.  q5's `{ch1: {allOf: [... measured:
  readOnly]}}` with patch `{ch1: {measured: 3}}` is now `rejected
  MHS.RESOURCE.NOT_WRITABLE` with no bridge call.  Previously, a matching
  `patternProperties` key was `FIELD_UNKNOWN`; now it follows its schema.

### What changed

`MHS/sdk/src/mhs/server.py`:

- **The deadline bounds only the response.**  `deadline_ms` counts from the
  request (the ingress time of `mhs.command`, PROTO-011).  It never cancels a
  command: the old `cancel_event.set()` at the deadline is gone.
  `max_duration_ms` bounds the execution.  It is taken from the binding's
  `constraints`, else from its catalogue class (`_execution_bounds`; an
  extension class has none).  It counts from dispatch, and it is now the
  bridge's budget: `ctx.extra["deadline_at"]` and `ctx.deadline_ms` carry it,
  as `bridge/base.py` asks of a server.  Only a command with no execution
  bound at all keeps the response deadline as its bridge budget.  The state
  reads around the call stay bounded by the response deadline
  (`_start_operation(response_at=...)`).
- **`long_running` bindings** (`constraints.long_running: true`, or the
  class flag) answer the current, non-terminal receipt once the deadline has
  passed.  That receipt is `status: running` with its `operation_id`, no
  outcome fields, and `x-vendor {long_running, deadline_ms,
  max_duration_ms}`.  It is not evidence.  The command keeps running and is
  never cancelled by the deadline.  A `long_running` binding with no bound of
  its own or of its class is bounded by 600 000 ms
  (`_LONG_RUNNING_DEFAULT_MAX_MS`), and strict mode refuses it (below).
- **Any other command** answers `unknown` + `MHS.OUTCOME.TIMEOUT`
  (`retryable: false`) and keeps running.  The error states the effective
  bound: `details.reason` is `deadline_exceeded` or `max_duration_exceeded`,
  and the details also carry `deadline_ms`, `max_duration_ms`,
  `cancellation_requested`, `long_running` and `operation_id`.  The receipt
  has a `cancellation` member only when cancellation was really requested.
  Its state read is bounded (`_DEADLINE_RECEIPT_READ_BOUND_S` = 0.1 s): a slow
  device no longer delays the answer.  With a 0.6 s read and a 400 ms
  deadline, the answer used to come after about 1.0 s and now comes after
  about 0.45 s.
- **The execution bound.**  When `max_duration_ms` ends the wait before the
  deadline does, a cancellable command is asked to stop (`cancellation.reason
  "max_duration_ms exceeded"`).  If it stops within the deadline (at most
  `_MAX_DURATION_GRACE_S` = 0.25 s), the caller gets the `cancelled` receipt.
  Otherwise it gets `unknown` with `max_duration_exceeded`.  After the caller
  has been answered, a timer (`mhs-exec-bound-<op>`) does the same at the
  bound: it asks a cancellable command to stop, then records `unknown` for a
  long-running one, whose caller holds only a `running` receipt.  The worker
  cancels the timer when it finishes.
- **Exactly one final receipt per command.**  The response path (and the
  timer) records `unknown` only after claiming it under
  `Operation.outcome_lock`.  The worker sets `finishing` under the same lock
  before it writes its final receipt.  If an `unknown` was claimed, the
  worker first waits until it is recorded, so `unknown` always comes before
  the final receipt in the evidence.  It then records the final receipt with
  `x-vendor.reconciles = {receipt_id, status: "unknown", mhs_code}`.  This
  final receipt is the reconciliation evidence record.  It replaces the
  stored (idempotency) receipt, so `operations.get` and a replay return it.
  A late rejection (`Busy`) instead frees the command id, as any rejected
  attempt does (OP-005).  The worker's own final state read is bounded by
  `_REVISION_READ_BOUND_S`, so the response path never waits long on a
  worker that is finishing.
- **Live state until then.**  After an `unknown` answer,
  `operations.get` / `operations.list` and a replay of the `command_id` report
  the operation's live `running` receipt until the final receipt exists
  (OP-003/OP-010).  That receipt names the recorded unknown receipt in
  `x-vendor.unknown_receipt_id` and has its own (provisional) `receipt_id`.
  The `operations.cancel` snapshot no longer copies outcome fields (`error`,
  `ended_at`, `state_revision_after`, ...) into its `running` receipt.
- **Refused if the deadline passed before dispatch (OP-012).**  A command
  whose deadline passed during the pre-checks (a slow interlock read, for
  example) is now `rejected` with `MHS.OUTCOME.TIMEOUT`
  (`details.reason: deadline_exceeded_before_dispatch`, `retryable: true`).
  A consumed permit is given back, and nothing is dispatched.
- **Driver signals (plan 3.7; `_native_outcome`).**  Only exceptions raised
  by the native call are classified, with `mhs.signals.outcome()`:
  - `DriverFailed` is `failed` with its code, message and `native_code`;
  - `Busy` is `rejected` `MHS.DEVICE.BUSY` (retryable, `retry_after_ms`;
    the revision does not move);
  - `OutcomeUnknown` is `unknown` `MHS.OUTCOME.UNKNOWN`;
  - `Cancelled`, `asyncio.CancelledError` and
    `concurrent.futures.CancelledError` are `cancelled`.  An
    `asyncio.CancelledError` used to kill the worker thread, leaving no
    receipt at all;
  - any other exception (`BaseException`) is `failed`
    `MHS.ADAPTER.SHIM_FAILED`, with the message `driver raised <Type>` and
    `details.exception_type`.  The native message is never forwarded.  It
    used to be `MHS.DEVICE.FAULTED` with `str(exc)`;
  - a plain `MHSError` that is not a signal keeps its code (a bridge's own
    refusal);
  - the legacy outputs `{"status": "cancelled"}` and, once cancellation was
    requested, `{"cancelled": true}` are still `cancelled`.

  A failure in the server's own post-call code is now `failed`
  `MHS.INTERNAL.ERROR` with the exception type only (it used to be
  `MHS.DEVICE.FAULTED` with the message).
- **Non-canonical input (verifier H2).**  `mhs.command` input,
  `mhs.resource.write` patch and `mhs.safety.permit` input are checked first.
  One with no canonical JSON form (an integer beyond 2**53-1) is the protocol
  error `MHS.CAPABILITY.INPUT_INVALID` (`details.reason:
  not_canonical_json`), with nothing dispatched.  It used to be
  `MHS.INTERNAL.ERROR`.  A `mhs.command` on `cap.motion.estop.v1` with such
  an input used to fail with `MHS.INTERNAL.ERROR` *before latching*.  It now
  latches: the digest falls back to a placeholder input
  (`_estop_action_digest`).
- `Capability.long_running` (binding flag), `Operation` fields
  (`long_running`, `outcome_lock`, `unknown_claimed`, `unknown_recorded`,
  `unknown_receipt`, `finishing`, `bound_timer`), the request-ingress
  contextvar and the per-server class-constraint cache.

`MHS/sdk/src/mhs/_server/strict.py`: `constraints-invalid` now also covers a
non-boolean `constraints.long_running` and a `long_running` binding without
an execution bound (neither the binding nor its class declares
`max_duration_ms`).  Path: `constraints.long_running`.  Compatibility mode

### Behavioural / compatibility notes

- A command slower than its deadline is no longer cancelled.  Before, a
  cancellable one was asked to stop at the deadline.  Now it runs to the end
  of its execution bound, and only then is it asked to stop.
- Bridges get the execution bound as their budget, which can be longer than
  the deadline (class `max_duration_ms`).  A hung native therefore holds an
  exclusive device lock until that bound, instead of the deadline: the
  device really is busy.
- The class `max_duration_ms` now applies when a binding declares none,
  both to the response wait (`min(deadline, bound)`, PROTO-011) and to the
  execution.
- `unknown` receipts at the deadline no longer carry a `cancellation` member
  unless cancellation was really requested.  `details.reason` is new.  The
  message names the effective bound.
- `operations.get` / `list` and replays of a command answered `unknown` show
  `running` while it still runs (they used to show the unknown receipt).
- Bridge exceptions: `MHS.DEVICE.FAULTED` + message became
  `MHS.ADAPTER.SHIM_FAILED` + exception type.  A `Busy` signal is `rejected`
  (it used to be `failed`).  `OutcomeUnknown` is `unknown` and cancellation
  exceptions are `cancelled` (they used to be `failed` or no receipt).
- New receipt member values: `x-vendor.reconciles` on a final receipt that
  follows `unknown`; `x-vendor.unknown_receipt_id`, `long_running`,
  `deadline_ms` and `max_duration_ms` on `running` receipts.  Wire methods,
  error codes and schemas are unchanged.  `receipt.schema.json` already
  allows `running` + `operation_id`, and `x-vendor` is open.
- A long-running operation is still owned by its session: closing the
  session, or letting it expire, cancels it (unchanged).

### What changed

New `MHS/sdk/src/mhs/_server/state.py` (stdlib only):

- **Layout.**
  - `<state_dir>/evidence.jsonl`: the evidence chain;
  - `latch.json`: the latch of every device the endpoint knows (format
    `openmhs.state.latch/1`);
  - `journal.jsonl`: the idempotency index and the write-ahead records
    (`openmhs.state.journal/1`);
  - `lock`: a POSIX `flock`, so one endpoint process uses a directory at a
    time.
- **Atomic writes.** `atomic_write_bytes` writes a temp file, fsyncs it,
  `os.replace`s it and fsyncs the directory.  `latch.json` is always
  written this way and always fsynced.  The journal is rewritten this way
  (compacted) at every start.  Between starts it is append-only, one line
  per entry.
- **Journal entries:**
  - `put` / `drop`: the idempotency index, `(device_id, command_id)` -> the
    receipt at evidence `seq`;
  - `begin` / `end`: bracket a command from its idempotency reservation to
    its final receipt (write-ahead);
  - `draw` / `release`: the cumulative budget reservations;
  - a header with the revisions reached.
- **Loading.** `derive_index` rebuilds the index from the verified
  evidence chain with exactly the server's retention rule: a receipt that
  is not `rejected` is the outcome, a later one replaces it, and a late
  rejection that reconciles the retained receipt frees the id.  Every
  `put` line is checked against the evidence record it names.  A rule that
  derives from the evidence cannot be fooled by journal lines written out
  of order by concurrent commands.
  - A `begin` with no outcome is a command in flight when the process
    stopped.  One whose receipt reached the evidence after the `begin`'s
    `evidence_seq` is settled by that receipt.
  - A `put` past the end of the evidence means the evidence lost its tail
    while the journal kept its own.  A power failure with `fsync=False`
    can do that, and so can a non-atomic copy of the directory.  That
    command becomes in flight too.
  - A torn final journal line is ignored with a `RuntimeWarning`.  Any
    other unreadable line, a `put` that contradicts its evidence record, a
    `put` past the end with no `begin`, or a journal or latch file of
    another endpoint refuses the start (`StateDirError`, a `ValueError`).
  - A missing journal is rebuilt from the evidence.

`MHS/sdk/src/mhs/server.py`:

- `MHSServer(state_dir=None, fsync=False)`, `MHSServer.close()` (idempotent:
  closes the evidence log and releases the directory), `StateDirError`
  exported.  Without `state_dir` nothing changes and nothing is written.
- **Start-up** (`_open_state_dir`, no bridge I/O):
  1. take the lock;
  2. `EvidenceLog(path=<state_dir>/evidence.jsonl, fsync=..., recover_torn_tail=True)`.
     A chain that fails verification, or whose genesis names another
     endpoint, refuses the start;
  3. read the latch file and rebuild the journal;
  4. record an `unknown` receipt for every command that was in flight:
     `MHS.OUTCOME.UNKNOWN`, `retryable: false`, `details.reason:
     endpoint_restarted`, plus `lost_receipt_id` when the journal kept a
     receipt the evidence lost, and `x-vendor.restart_reconciled`.  The
     receipt is built from the `begin` entry (capability, resource,
     session, principal, mode).  It is schema-valid and goes into the
     evidence and the index, so a retry replays it instead of running the
     command again;
  5. adopt the index (`_receipts`, `_receipts_by_id`), the revisions and
     the cumulative draws still inside their window;
  6. compact the journal, then write the latch file.

  Any failure releases the directory.
- **Latch (SAFE-065).**
  - `_persist_latch` replaces the whole `latch.json` atomically under
    `self._lock`, before any bridge I/O.  That happens on every e-stop
    (the latch is on disk before `bridge.estop()` runs) and on every
    completed reset.
  - A failed write never stops the latch.  It is logged and reported in
    the e-stop's `output.latch_persisted` (present only with `state_dir`)
    and in `safety.status` `estop.persisted`.  The next latch write
    rewrites the whole file.
  - On start, a latched entry keeps its device latched.  That includes a
    device that is not served now: a device added later is still latched.
    `safety.status` then shows `estop.restored: true` and `estop.confirmed:
    false`: nothing has confirmed the stop path since the restart, and the
    next e-stop runs it.
- **Unreadable latch file: fail latched.**  A `latch.json` that exists but
  cannot be read or parsed, or has the wrong shape, starts latched: every
  device served now and every device the evidence holds a receipt for.  A
  `RuntimeWarning` is emitted.
  - At the end of a successful start the file's bytes are copied to
    `latch.json.unreadable-<ULID>`, and `latch.json` is replaced atomically
    with every device latched.  Each device is then released through
    `mhs.safety.reset`.
  - A start refused for another reason leaves the unreadable file where it
    was, so the next start fails latched again.  `latch.json` is never
    renamed or removed.
- **Idempotency (OP-006).**
  - Every retention goes through `_retain_receipt` / `_forget_receipt`,
    which also write the `put` / `drop` lines under `self._lock`.
  - `_begin_inflight` writes `begin` (with `capability_id`, `resource`,
    session, principal, mode, risk and the evidence `seq`).
    `_finish_inflight` writes `end`.
  - A completed command id replays its receipt byte for byte after a
    restart (same `receipt_id`, same evidence link), with zero bridge
    calls.  A different input is refused with `COMMAND_ID_REUSE`.  A
    rejected attempt is still not the outcome.  The 4e reconciling final
    receipt (`x-vendor.reconciles`) is the one retained.
- **Revisions.**  On start each device continues at the highest revision
  any previous run reached, plus one.  The highest comes from the evidence
  receipts and the journal header.  A restart may have changed the device
  without the endpoint seeing it, so no pre-restart revision is ever
  current again: a stale `expected_revision` is refused with
  `CONFLICT.REVISION`.
- **Cumulative budgets (SAFE-016).**  Draws and releases are journalled,
  so a restart never refills a rolling budget.
- **hello.**  `limits.receipt_store` is `"state_dir"` with a state
  directory, `"memory"` without one.
- Docstrings: the module simplification note and the class docstring
  describe persistence.  `_server/__init__.py` lists the new module.

`MHS/sdk/src/mhs/evidence.py`:

- `EvidenceLog(recover_torn_tail=False)`.  When true, a final line that a
  crash cut short is moved to `<path>.torn-<ULID>` and the file is
  truncated to the last complete record.  That record was never returned
  to anyone: an append returns only after its line was written.  A
  complete last record that lost only its newline gets it back.
  `recovered_tail` reports what was done.
- Damage anywhere else still fails verification.  The default (`False`)
  is unchanged.  The server uses `True` and warns.  The command whose
  receipt was torn becomes `unknown` through its `begin` entry.

### Behavioural / compatibility notes

- Everything is opt-in.  Without `state_dir` the endpoint behaves exactly
  as before (memory only, nothing written).  The new hello value
  `receipt_store: "state_dir"` appears only with a directory.
- With `state_dir`, construction can raise `StateDirError`: the directory
  is in use, belongs to another endpoint, or holds an untrusted chain or
  journal.  Call `close()` before starting another server on the same
  directory.  A process exit releases the lock too.
- E-stop output gains `latch_persisted` and `safety.status` gains
  `estop.persisted` / `estop.restored`, only with `state_dir`.
- After a restart, revisions jump by one, sessions, permits and operations
  are gone (the safe direction), and a restored latch is unconfirmed.
- Without `fsync=True` a power failure (not a process crash) can lose the
  tail of the evidence or the journal.  The loader then fails safe:
  `unknown` receipts, or a refused start.  `fsync=True` fsyncs every
  evidence and journal append.  The latch file is always fsynced.
- Journal and latch writes happen under the global lock (the latch before
  any bridge I/O, as plan 3.6 asks).  A journal write failure is logged and
  never raised, because the evidence append that precedes it already fails
  the mutation.

## 4f (fix round) — verifier findings on the 4f step

The 4f verification failed on two major issues: a rejected duplicate of a
command in flight could make a crash re-run that command, and the restart
latch came only from `latch.json`.  It also reported four minor issues.
All six are fixed here, each with a ported repro (from
`scratch/verify-WP-04/4f/repro/`) that failed first
(`scratch/wp04-4f-fix/failfirst.log`: 11 failures, 3 errors in the 11 new
tests; the two that passed are guards that must pass both before and after).

### What changed

`MHS/sdk/src/mhs/server.py`:

- **The reservation belongs to the request that made it (major,
  `dup_settles.py`).**  The verifier traced this to the settle rule.  The
  first cause is in the server: a rejected receipt released the in-flight
  reservation of its `(device_id, command_id)`.  `_finish_command(rejected)`
  called `_finish_inflight`, which wrote the journal `end` line.  So a
  `COMMAND_ID_REUSE` refusal of a duplicate, sent while the original was
  blocked in the bridge, ended the original's write-ahead record, and a
  crash then re-ran it.  The same release also hurt without `state_dir`:
  with a non-exclusive binding, an identical retry after such a refusal ran
  the command a second time (`scratch/wp04-4f-fix/mem_dup.py`: 2 bridge
  calls).
  - `_finish_inflight(device_id, command_id, digest=None)` releases only a
    reservation for the same input digest.
  - `_finish_command` releases on final receipts (`completed`, `failed`,
    `cancelled`, `unknown`).  A `rejected` receipt releases only with the
    new `release_inflight=True`.  Only the command worker passes it, since
    its bridge's `Busy` ends its own reservation.  Every other refusal
    before or after `begin` is released by its owner: the `mhs.command`
    `finally` and the explicit calls in `mhs.restore`, which now also pass
    the digest.
- **A failed write-ahead `begin` refuses the command (minor,
  `begin_fail.py`).**  `_begin_inflight(..., write_ahead=...)` appends the
  `begin` line itself.  For an effectful command (`mhs.command` with
  `latch_applies`, and every `mhs.restore`) a failed append withdraws the
  reservation and returns `"journal_failed"`.  The caller then gives a
  `rejected` receipt before any bridge I/O: `MHS.INTERNAL.ERROR`,
  `details: {reason: journal_write_failed, executed: false}`.  Reads, stop
  classes and safe-state actions still run, with the error logged.
  `entry["journaled"]` is set only when the `begin` line was written.
- **Latch from the evidence (major, `latch_cases.py` 1, 2, 5).**
  - `_adopt_latches` ORs `latch.json` with
    `state.derive_latches(records)`.  A device is latched when its last
    e-stop receipt that engaged the latch comes after its last completed
    `cap.internal.safety_reset.v1` receipt.  Such a receipt is
    `cap.internal.safety_estop.v1` or `cap.motion.estop.v1`, with any
    status but `rejected`.  A confirmation receipt
    (`output.confirms_command_ids`) does not count: it can be written just
    after a reset.
  - The union is fail-safe: `latch.json` is written before the e-stop
    receipt and before the reset receipt.  A device latched only by the
    evidence gets a `RuntimeWarning` that names the e-stop receipt, and
    `latch.json` is repaired at the end of the start.
- **Absent `latch.json` (major).**  A directory whose evidence holds a
  receipt, but which has no `latch.json`, now fails latched like an
  unreadable file.  `LatchState.absent` reports the missing file, and the
  `RuntimeWarning` says "missing".  The endpoint writes the file at every
  start, before any receipt, so a missing file means lost state.  A
  directory with no receipts (fresh, or with only a torn genesis) still
  starts unlatched.
- **A restored latch re-runs its stop path (minor, SAFE-040).**  The
  verifier's first suggestion is implemented.  A replay of the latching
  e-stop's `command_id` on a latch restored at start-up (`restored`, not
  yet confirmed, no attempt running) now does the following:
  - starts the stop path (`_rerun_restored_stop_path_locked`);
  - waits for it within the e-stop budget and the deadline
    (`_await_stop_path`, now shared with `_reassert_estop`);
  - confirms the latch, or hands it to the background retry supervisor;
  - still returns the retained receipt unchanged.

  A replay of a latch that is already confirmed does not stop the device
  again.
- **`StateDirError` for the final start-up writes (minor, `latch_cases.py`
  3).**  An `OSError` from `store.compact` or `store.write_latches` is
  re-raised as `StateDirError`, naming the file.  An example is a
  `latch.json` that is a directory.  The directory is still released.
- Docstrings: the class docstring (persistence paragraph),
  `_open_state_dir`, `_adopt_latches`, `_begin_inflight`,
  `_finish_inflight`, `_finish_command` and `_engage_estop`.

`MHS/sdk/src/mhs/_server/state.py`:

- **Settle rule (major).**  The `load_journal` settle loop now settles a
  pending `begin` only with a receipt that meets all of these:
  - it has the same key and the same `input_digest`;
  - it comes after the begin's `evidence_seq`;
  - its status is not `rejected` (nor `accepted` / `running`).

  This is exactly a receipt `derive_index` retains.  A crash between the
  command's own refusal and its `end` line now gives an `unknown` receipt,
  the conservative direction.
- New `derive_latches`, `holds_receipts`, `ESTOP_CAPABILITIES`,
  `RESET_CAPABILITY` and `LatchState.absent`.  The module docstring
  describes the settle rule and the evidence-derived latch.

`MHS/sdk/tests/safety/test_persistence.py`: 28 -> 39 tests.

### Behavioural / compatibility notes

- A refused duplicate no longer frees the command id of the command it
  collided with.  A third request with that id now waits for the command
  in flight, or gets `DEVICE.BUSY` / `COMMAND_ID_REUSE`.  Before, it ran
  the command again.
- Under `state_dir`:
  - an effectful command can now be refused with `MHS.INTERNAL.ERROR`
    (`journal_write_failed`) when the journal is not writable.  Nothing
    ran, and the refusal is not the outcome, so the same `command_id` may
    be retried;
  - a hand-edited or deleted `latch.json` no longer releases a latch.
    Only `mhs.safety.reset`, with its evidence receipt, does;
  - a missing `latch.json` next to receipts fails latched.
- Fail-safe spurious latch: a reset can complete between an e-stop's
  stop-path answer and that e-stop's receipt write.  The evidence then has
  the e-stop after the reset, and a restart comes back latched.  One more
  reset releases it.
- A replayed e-stop on a restored, unconfirmed latch calls the native stop
  path.  A replay used to make no bridge call in that state.

### Followups

- **WP-09** (spec, SAFE-065 / SAFE-040 / OP-006 note of 4f): the
  restart latch is the union of `latch.json` and the evidence (last
  engaging e-stop receipt after the last completed reset).  A missing
  latch file next to receipts fails latched.  A replay of the latching
  e-stop re-runs the stop path of a restored, unconfirmed latch.  Only the
  reserving request ends a command id's reservation, and only the
  command's own non-rejected receipt (same input digest) settles its
  write-ahead record.  An effectful command whose write-ahead record
  cannot be written is refused (`MHS.INTERNAL.ERROR`,
  `journal_write_failed`).
- **WP-04 (post-pilot)**, carried:
  - a restored latch that no one e-stops or replays gets no stop-path
    attempt, since construction does no bridge I/O.  A lazy supervisor on
    the first request after start would close this;
  - on macOS `os.fsync` is not `F_FULLFSYNC`, so the latch file's fsync
    is not a hard barrier there.  `F_FULLFSYNC` costs tens of ms, so it
    needs measuring against the 50 ms latch bound first.
