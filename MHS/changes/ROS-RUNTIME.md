# ROS simulated deployments and action completion

The ROS helper now accepts an explicit simulated deployment configuration (`endpoint`, `fidelity`, `deployment_id`) for a simulated `RosDriver`. Configuration is validated before transport I/O. The helper never silently substitutes hardware for simulation, and every model-authored ROS hardware backend still requires a human `reviewed_by` signature regardless of its risk class. Per-backend fidelity is copied for each constructed driver.

ROS 1 actionlib topics and ROS 2 action messages have explicit bindings, fresh correlation identifiers, bounded goal state and latest feedback, native terminal-status checks, and an optional application success predicate. Feedback alone is not completion. Cancellation addresses the exact retained goal; a physical safe-state claim still requires its independently acknowledged native stop. A transmitted goal whose outcome remains uncertain continues to block mutation and safety recovery. Ordinary read diagnostics and the explicit safe-stop path remain available. Recovery does not erase that uncertainty.

Focused tests exercised the stock ROS helper, adapter, server, action status/cancel paths, gate and controlled transports. The first consolidated SDK run passed 2,268 tests with four skips. Later work added further changes: the second full run executed 2,361 tests with four failures (two generated applicability line indexes, the changelog index and standalone collect bytecode suppression), all subsequently addressed by 20 passing focused tests. A clean final full regression is still required. Controlled peers establish protocol/contract behavior, not interoperability with an installed ROS graph.

The initial implementation above used controlled peers. Subsequent user-authorized isolated Docker validation ran a pinned ROS 2 Jazzy turtlesim graph through the stock SDK, native actions and MCP stdio. Controlled real ROS Image messages passed pixel/hash/resource checks, and a later controlled BatteryState run established rosbridge's null serialization for NaN fields. The preserved container and fixtures were stopped after each completed run. See the private docker-ros-validation/RESULTS.md; the accepted safety-freshness change also passes a separate complete live regression in freshness-regression-v3, with all source hashes unchanged and the owned runtime stopped. These checks do not validate Panda/Gazebo/MoveIt, physical cameras or hardware. Auth/QoS configuration, fragmentation, reconnect policy and package-specific deployment ownership must not be inferred from these tests. Prior ROS-HELPER.md remains the historical five-package pilot record; its statement that action/simulation support is absent is superseded only for the bounded paths above.
