### What changed

New files under `MHS/registry/` (stdlib only):

- `triage.py`: the eleven ordered rules of the handoff kit, first match wins,
  then curated overrides. Output per repo: a `Decision` with `strategy` (the
  card's `decision`), `role`, `reason_code`, `rule` (1-11 or `override`),
  `quarantine`, `variant_of`, the integration `family`, `helper`,
  `helper_status`, `blocked_on`, `partner`, `flagship`, `wave`, the override
  `justification` and an `evidence` list. Also the family table (`FAMILIES`:
  pilot helpers PythonObjectDriver, SerialDriver, ScpiDriver, GymnasiumDriver,
  MujocoDriver are available; ros, http, pylabrobot, sila2, qcodes, ophyd,
  pymmcore-plus, lerobot, mavlink, tag-bridge and mcp-client are
  `helper:<name>` prerequisites), `exemplar_for(family, track)`, the rule-6
  table `BRIDGE_RUNTIME` (105 corpus repos), `load_overrides`/`check_override`,
  `summarize` and a CLI:
  `python3 MHS/registry/triage.py [--jobs N] [--cache DIR] [--out FILE.jsonl] [--json] [--only ID]`.
  The CLI exits 1 when an override names a repo that is not a registry record.
- `source_scan.py`: bounded, read-only scan of one clone. The file tree is
  capped at 20,000 sorted paths and is used for similarity. File counts by kind
  cover Python, other code, notebooks, executables/installers and archives.
  Python files (at most 1,500 per repo, 400 KB each, shallow first) are parsed
  with `ast`; files that do not parse (Python 2) contribute regex imports only.
  Vendored `third_party`/`vendor`/`external` trees are skipped. The scan
  records gym/gymnasium registrations (string ids, f-string ids and any id
  with an `entry_point`), environment classes, and ranked device entry
  classes `{symbol, file, line, score, bases, methods, members, api, exported,
  async, transport}`. A class inherits API from its in-repo base classes;
  scores rise for device verbs, descriptor members, address-like `__init__`
  parameters, transport imports, and `__all__`, package or README exports.
  Markers: `package.xml`, launch files, URDF, MJCF (`<mujoco` heads), Unity
  and Unreal projects, root build files, tests. README facts: heading,
  download calls to action pointing to the owner's github.io page, a file host
  or an installer, lure wording, curated-list and tutorial wording, MHS
  mentions, and class names the README imports or calls. Nothing is imported or
  executed. `SCAN_VERSION` invalidates cached facts.
- `corpus_lock.py` writes `corpus.lock.jsonl`. It runs
  `git --no-optional-locks -C <clone> rev-parse HEAD` and `remote get-url
  origin`, with `GIT_OPTIONAL_LOCKS=0` and no prompts. Each line is
  `{commit, local_path, package_id, repo_url}`, sorted by `package_id`. The
  remote is normalised to `https://` with no `.git` and no embedded
  credentials. A clone without HEAD gets `commit: null`. `--check` exits 1
  when the lock is stale.
- `corpus.lock.jsonl`: 2,967 clones, 2,962 pinned commits, 5 empty upstreams
  (`commit: null`), one non-GitHub remote (`croningroup/xdl` on GitLab). The
  lock agrees with `clone_audit_2026-10-12/baseline.jsonl` on every remote. It
  differs on one HEAD: `pku-yuangroup/openai4s` moved after the audit.
  `labs/` and `robots/` were reshuffled after the audit, so the audit is joined
  by `owner/repo` rather than by path.
- `catalog_view.py`: `risk_floor(caps)`, `class_risk(cap)` and `verb(cap)` from
  `mhs.catalog.Catalog.load(MHS/spec/capabilities.json)`. The repo's SDK
  source tree goes on `sys.path`.
- `overrides/{exemplars,partners,labs,robots}.json` plus `overrides/README.md`:
  103 curated decisions, each with a one-line justification. They are 4
  exemplars at wave 0, 25 repos for partner products, 41 lab flagships and 33
  robot/simulator flagships.
- `schema/overrides.schema.json` and `schema/taskcard.schema.json`. Both are
  closed and use `$id` = `SCHEMA_BASE` + file name, with `$ref` into
  `MHS/schema/defs.schema.json`. `schema/examples/taskcard.thermal-bath.json`
  is a valid example card.
- Tests: `tests/test_triage.py` (every rule, ordering, overrides, inputs,
  determinism), `tests/test_source_scan.py`, `tests/test_corpus_lock.py` and
  `tests/test_overrides_and_schemas.py`. The last one covers the override
  files, card schema constraints and catalogue-derived risk.

Edited files:

- `family_data.py`: the private `CAP_RISK` table and the `CAP_HINT_RULES`
  keyword regexes are deleted (`grep -c CAP_RISK` and `grep -c CAP_HINT_RULES`
  both return 0).
- `build_registry.py`: `risk_class_for()` is `catalog_view.risk_floor()`.
  `candidate_caps()` keeps the catalogue-filtered family template and no
  longer adds regex hits. Card hints come from code in 10b.
- `manifests.py`: device `risk_class` is `catalog_view.risk_floor()` over the
  device's capabilities.

### Triage rules as implemented

Inputs (read-only):

- the committed registry records (tier, families, stars, catalogue row number);
- `work/analysis/repo_profiles.jsonl` (analyst family, tier, quality flags, MHS
  claim, and the catalogue row with `relation_to_other_projects` and
  `limitations`);
- the catalogue CSV (fork and mirror notes of every row a record maps to);
- `corpus.lock.jsonl` (remote and HEAD; the clone audit is the fallback and the
  cross-check);
- the source scan.

1. `skip:empty`: registry tier X, or a clone with no files.
2. `skip:not-device` (role docs):
   - no source code and no model files (MJCF, URDF, package.xml);
   - an analyst `no_source_code`, `clone_content_gap` or docs-only flag that the
     scan confirms (at most one source file, no structural family, no entry
     class);
   - an awesome/curated list;
   - a repo name that names a course, tutorial, lecture, workshop, notes or book.
3. `skip:quarantine`: a README download call to action (to the owner's
   github.io page, a file host or an installer), or crack/keygen-style
   wording, in a repo with at most two source files; or executables with no
   source at all. `quarantine` is set for every repo whose rule-3 predicate
   holds, even when rule 1 or 2 decided first. Such repos get role not-device
   and `blocked_on` `QUARANTINE`.
4. `reference:prior-art`, for any of:
   - a README title naming MHS;
   - a repo name naming MHS plus at least one README mention;
   - an analyst MHS claim (`claimed` or `inspired_or_third_party`) plus at
     least five mentions.
5. `skip:duplicate_of`, with `variant_of` set to the canonical repo, for any of:
   - the same HEAD or the same git remote as another clone;
   - a catalogue fork/mirror/copy note without a divergence marker ("hard
     fork", "substantive", "adds" or "extends", a port, "independent" ..., in
     English or in the catalogue's Chinese wording) that names exactly one corpus repo by `owner/repo` or
     by the longest matching project name, corroborated by a file-tree Jaccard
     of at least 0.5;
   - a same-name repo with a file-tree Jaccard above 0.9.

   The canonical repo is the named upstream, otherwise ordered by not archived,
   most stars, `owner == repo`, then package_id. Chains resolve to their root
   and cycles keep exactly one repo.
6. `bridge-runtime:<family|engine>`: the curated `BRIDGE_RUNTIME` table. It
   holds VISA/SCPI, Modbus, OPC UA, EPICS, Tango and Alpaca transports;
   ROS/DDS/rosbridge infrastructure; the gymnasium, gym, MuJoCo and dm_control
   cores; the frameworks behind post-pilot helpers (QCoDeS, ophyd, PyLabRobot,
   pymmcore-plus/MMCore, LeRobot, the Opentrons robot-server, MADSci,
   flowchem); and 25 simulation engines and engine remote-API transports
   without a helper (Drake, Webots, CoppeliaSim, Isaac Sim/Lab, Habitat,
   SAPIEN, Genesis, Bullet, PhysX, CARLA, AirSim ...).
7. `reference:host` or `skip:tooling`:
   - host: an MCP server (named so, or analyst mcp-server) that wraps a
     covered backend (ROS, VISA, PyLabRobot, Opentrons, SiLA2, QCoDeS, ophyd,
     Micro-Manager, LeRobot, Isaac Sim, MuJoCo/gym, MAVLink, Modbus, OPC UA,
     EPICS, Tango, MADSci, flowchem, Gazebo); or, for a repo whose catalogue
     role is not a device SDK and that has no env registration, a catalogue
     category of orchestration, agent framework, experiment orchestration or
     workflow, or a repo name naming an orchestrator, scheduler, workflow,
     assistant, ground station or queue server;
   - tooling (same guard): catalogue category auxiliary tool with role
     peripheral tool, or a GUI/viewer/plotting/dashboard/widget/template-style
     repo name.
8. `skip:peripheral`, for either:
   - registry tier D;
   - "content tier D": a catalogue row of policy/algorithm, dataset, control
     framework, navigation, physics engine, model/scene asset or measurement
     model where the scan finds neither device evidence (catalogue
     device/instrument/SDK wording, a device-SDK role, a driver/SDK/hardware
     repo name, or an exported strong class that uses a transport) nor
     simulation evidence (gym registration, MJCF, environment classes, a
     simulation catalogue role, a sim/gym/twin/emulator repo name).

   Overrides are the curated list that rule 8 never skips.
9. `family:<family>` (family-config). The structural markers are checked in
   order:
   1. imports of pylabrobot, qcodes, ophyd/ophyd_async,
      pymmcore_plus/pymmcore/pycromanager, sila2, or madsci/flowchem;
   2. gym/gymnasium env registrations, unless the env needs an external
      simulator (isaacgym/isaaclab/omni, airsim, carla, mlagents, pyrep,
      habitat, the Webots controller, ROS, gym-ignition, raisim, omnigibson),
      which has no helper;
   3. `package.xml` when the analyst or registry family is ros1, ros2 or gazebo;
   4. MJCF models with a mujoco/dm_control/mujoco_py import, or a pure asset
      repo;
   5. lerobot with device evidence and no simulation evidence;
   6. then, when the repo is not a driver pack: pyvisa/visa/vxi11/usbtmc/pymeasure
      (scpi); Modbus, OPC UA, EPICS, Tango, Alpaca, ADS or S7 imports
      (tag-bridge); pymavlink/mavsdk/dronekit (mavlink); pyserial (serial),
      unless a strong Python device class exists; an MCP server (mcp-client),
      under the same condition.

   The inferred role must fit the family: gymnasium and mujoco take sim-env or
   twin-candidate; ros takes device, driver-pack, sim-env or twin; protocol and
   lab families take device-driver, driver-pack or twin-candidate.
10. `PY_SDK_WITH_ENTRY` (direct-driver, python-object): the best AST entry
    class has score ≥ 9 and at least 3 device API members, the repo has
    device evidence, it imports no external simulator, and its role is
    device-driver, driver-pack or twin-candidate.
11. `untriaged:<non_python|no_entry_class|weak_entry|no_scan|env_factory>`:
    a recon-only card.

Names and README words never choose a simulator family; only code structure
does. Families without a planned helper (Isaac, Unity, Unreal, Webots,
CoppeliaSim, Habitat, AirSim, plain PyBullet) fall through to rule 11.

### Deviations

- Rule 2 adds "no source code and no model files" by scan, and accepts an
  analyst flag only when the scan confirms it. The analyst `no_source_code`
  and `clone_content_gap` flags mark many real single-file drivers and C++ ROS
  packages, for example `interbotix_ros_manipulators`.
- Rule 8 uses a content tier. A catalogue row that describes software, with no
  device or simulation evidence, counts as tier D, so policy, dataset and
  algorithm repos do not reach the per-repo queue.
- Serial and MCP repos that already have a strong Python device class are
  direct drivers rather than SerialDriver command maps. SCPI instruments are
  always ScpiDriver family-configs, like the sr860 exemplar. Driver packs
  never take a protocol family.
- Rule 6 reports helper-less engines as `bridge-runtime:engine`. Rule 6 alone
  would make the gymnasium core bridge-runtime; an override keeps it as the
  CartPole family-config exemplar that WP-11 needs.

### What changed

New files under `MHS/registry/` (stdlib only):

- `licenses.py`: SPDX ids and classes. `from_catalog` reads the catalogue field (an id, `A OR B`, or prose whose
  first id wins; a proprietary, non-commercial or custom term before the first id names the main code;
  "no licence declared" gives none), `detect_text`/`detect_files` fingerprint the root licence files (an
  `SPDX-License-Identifier` line first; `LICENSE-APACHE` plus `LICENSE-MIT` is `Apache-2.0 OR MIT`),
  `from_declared` reads packaging metadata, `license_class` maps ids to permissive, weak-copyleft, copyleft,
  network-copyleft, source-available (SSPL, PolyForm, BUSL, Elastic, CC NonCommercial/NoDerivatives, NVIDIA
  Source Code), proprietary or unknown (`OR` takes the least restrictive term, `AND` the most restrictive).
  `resolve` uses the catalogue, then the licence file, then the packaging metadata.
- `taskcards.py`: one card per record, validated by `schema/taskcard.schema.json`, with `$schema` =
  `_ids.SCHEMA_BASE + "taskcard.schema.json"`. Field rules:
  - `entry_symbols`: AST only, typed `{symbol, file, line, confidence: "ast"}`. Gymnasium and MuJoCo cards use
    gym registrations whose entry point is a `module:Class` (file and line of the class when it is defined in
    the repo); a simulator without one has no entry symbol (`needs_recon: entry_symbol`). Device cards list up to
    five ranked classes, re-ranked for the card: README-constructed (+3) and re-exported (+2) classes up,
    transport or protocol layers (`...Interface`, `...Port`, `...Cmd`) and server/GUI/CLI wrappers (-4) down.
  - `install`: `pip install .` for a root setup.py or a buildable pyproject.toml, else `pip install -r
    requirements.txt`, plus `colcon build` for a root package.xml; `python` from `requires-python` /
    `python_requires`; `gpu` from GPU-only imports or a positive (not negated) catalogue requirement; `platform`
    windows for Windows-only imports, linux for ROS.
  - `mock_strategy`: upstream-sim when the repo ships a device simulator, mock or fake outside tests and GUI
    task folders (or a pyvisa-sim device file), and for every simulator card; transcript for SCPI and serial
    command maps without one; fake otherwise. `upstream_tests` is the first tests directory.
  - `hints`: reads, writes and actions of the top three entry classes (device API methods and class-level
    descriptors; lifecycle and raw I/O excluded) and the stable catalogue classes their names suggest: setters
    without a better class map to `cap.device.configure.v1`, `set_temperature`/setpoints in a thermal context to
    `cap.thermal.setpoint.v1`, getters to the measure class that fits or `cap.sensing.read.v1`, joint/servo/move
    to `cap.motion.joint_position.v1`, robot poses to `cap.motion.cartesian_pose.v1`, `cap.motion.stop.v1` only
    beside a motion class; an e-stop and tip handling map to no class. Simulator cards get

The issue reproduced. `final_modes()` gave a twin candidate dual mode only when it was a direct driver, so
some repos whose code drives real instruments were recorded as `modes: ["simulated"]` with
`hardware_free: true`, no hardware device in the device plan, and `expected_mode: "simulated"` on the card.
Affected: `little-did-i-know/scpi-instrument-control` (SCPI over pyvisa), the four `tiagocoutinho` controller
libraries (tag-bridge), `lewbert/talos-2d-transfer`, `deepmodeling/uni-lab-os`,
`amandavical/comunication-instrument`, `pangea567/gnsdo-scpi-simulator` and `tetheria/aero-hand-open` (ROS).
Recon cards for `roversx/universal-robot-mcp` (a UR controller over urx), `itheima1/mcp_robot`, `rhoban/bam`
and `markfzp/humanplus` had the same problem.

- `build_registry.hardware_evidence(facts)` returns the ranked device class that uses a hardware transport,
  as `triage.hardware_transport` does. It leaves out simulation environment classes (`...Env`,
  `...Environment`, `...Gym`, `Simulator...`, or a subclass of one). So an Aspen process-simulator gym that
  talks COM is not hardware.
- `final_modes`:
  - A twin candidate is hardware first and simulated second when it is a direct driver that drives
    hardware (as before), or when its code drives hardware and its family is not a simulator family
    (gymnasium, mujoco).
  - An `untriaged` recon card for code that drives hardware lists hardware first.
  - Sim-env roles and gymnasium/MuJoCo twins stay simulated: their driver drives the simulator.
- Records carry the evidence in `x-vendor.triage.hardware_transport` (298 records).
- `validate.py` adds `check_hardware_evidence`: with that evidence, a device driver, driver pack,
  non-simulator twin or recon card must list hardware first. It runs with `--no-corpus` and passes on every
  record.
- Result: 14 records moved from simulated only to `["hardware", "simulated"]`. Their device plans now start
  with a hardware device (`estop_required` at R1 and above), and their cards say `expected_mode: "hardware"`.
  Dual-mode records: 208 (was 194).
