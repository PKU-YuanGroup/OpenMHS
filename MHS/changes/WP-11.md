# WP-11 — Exemplar drivers and the DeepSeek handoff kit

## 11a — Lab exemplars (julabo, srsinst.sr860)

Step 11a builds two of the four exemplar packages at their real per-repo paths. Both pass
`python3 -m mhs.driver check <dir> --backend fake`. The other two exemplars (xArm, Gymnasium) and the handoff kit
(`MHS/handoff/**`, `MHS/drivers/README.md`, `CONTRIBUTING.md`) are later steps. An earlier attempt at these packages was
lost in a temp-dir cleanup, so they were rebuilt here from the current tree.

Findings the packages exercise on real repos: FIT-09 (an async Python API
driven by a direct Driver), FIT-02 (parameter writes through `cap.device.configure.v1`), FIT-03 (limits enforced by the
runtime, an allowed set), FIT-04 (a SCPI instrument as a command map, no launch command), FIT-08 (units).

Followups from earlier steps that this step applied: SAFE-045 (julabo is R2 hardware: its stop is also a
`safe_state=True` action, since no hardware e-stop line is cited); `LIMITS_UNSET` (the only numeric write input is
`operator_required`, and no catalogue numeric input is left unlimited); `concurrency` for python-object commands (not
applicable: julabo is a direct Driver, and the sr860 has no command); `fixtures/conformance.json` (not needed: no
pattern string or allowed string set, and the numeric allowed set of the sr860 is probed by the gate itself); SCPI
mnemonics (only `FREQ`, `SLVL`, `OFLT`, `OUTP`, which occur in the clone, plus the exempt `*IDN?`); `x-cap.<upstream
owner>.<name>.v1` ids (`x-cap.tiagocoutinho.*`); a `Field(description=...)` on every input; `MHS/drivers/EXEMPLARS.txt`;
the check-report/overlay issue (deviations 1 and 2).

**Honest provenance.** Both packages are model-authored: `driver.lock.json` `authored_by` is
`{kind: model, model_id: claude-sonnet-5-5, run_id: wp11a-julabo | wp11a-sr860, date: 2026-10-27}` and `reviewed_by` is
`null`. Nobody reviewed them and no hardware was attached. A pass is evidence `contract_checked` on the fake backend and
never an MHS-Device level. The julabo package is a hardware driver at R2, so the loader refuses its hardware backend
(`review_required`, checked) until a human signs `reviewed_by`. The sr860 driver is R1: nothing here connected to an
instrument, and its wire syntax was not tried on one (below).

### Deviations (changes outside the step's scope, each needed by the acceptance)

1. **Gate digest without the clock (the check-report/overlay issue).** Every gate run rewrites `check-report.json` with a
   new `generated_at` and durations, so its `report_digest` changes on each run, and `validate.py` failed with
   `RESULT.json gate digest != check-report.json report_digest` after any re-run. Fix, least invasive of the options:
   - `mhs.driver.check.stable_digest(report)`: the JCS digest of the report without `report_digest`, `generated_at` and
     the durations. Two runs that found the same thing give the same value (also under Python 3.10.21 and 3.14.7); it
     changes when a gate status, a finding, the backend, the upstream pin or the SDK version changes. The CLI prints it on
     a pass: `gate digest (RESULT.json gate.digest): sha256:...` (before the `PASS` line; `--json` is unchanged).
   - `RESULT.json` records that printed digest as `gate.digest`.
   - `MHS/registry/validate.py` (`gate_digest_problem`) accepts a `gate.digest` equal to the present report's stable
     digest or to its own `report_digest` (a hand-recorded or hardware report). A package without a `check-report.json`
     has nothing to compare and is not an error. A stale digest says "re-run the gate and record the digest it prints".
   - Tests: `tests/driver/test_check.py::StableDigestTests` (5), `registry/tests/test_overlays_index_validate.py::GateDigestTests` (5).
   The schema text for `gate.digest` ("report_digest of the check-report.json") is now incomplete; it is outside this
   step (follow-up).
2. **Registry records no longer depend on the generated report.** `overlays.py` and `build_registry.py` named
   `check-report.json` in `x-vendor.overlay.files` and `evidence.provenance_refs` whenever the file existed, so
   `build_registry.py --check` changed with every gate run. A record now names the report only as the evidence of an
   operator-run hardware check (`Overlay.committed_files()`); `validate.py` still reads it. Verified: `--check` gives 0
   differing files with and without the reports. Tests: two in `test_overlays_index_validate.py::OverlayTests`.
3. **G8 serves `site-limits.example.json`.** The conformance run (`_Context.server_factory`) built servers with no
   overlay. A driver whose writable parameters are all `operator_required` (julabo has one) could not write anything:
   the suite fell back to the class example `{setpoint: 37.0}`; OP-001, TCAP-001, TCAP-003, OP-003..005 and TSAFE-001
   failed with `LIMITS_UNSET` and SAFE-014 was skipped. That is the common case for lab instruments whose code states no range, so
   DeepSeek would have been blocked (`SDK_BUG`) on many repos. G8 now serves the package's example overlay (a vetted
   file: G6 already refuses an overlay that widens). A failing G8 on a driver with `operator_required` limits and no
   example overlay says so ("add site-limits.example.json"). Tests: `OperatorRequiredConformanceTests` (4).
4. **G6 no longer polls a settled `unknown` receipt.** A failure injected into a transport (`FAILURE_HIDDEN`) ends the
   operation as `unknown` / `MHS.OUTCOME.UNKNOWN`, but `Session._final` polled it for its whole 15 s bound, six times per
   check: G6 of the sr860 package took 90 s and the whole gate 3 min (G9 runs the gate again, against a 180 s limit; a
   SCPI or serial driver with more parameters would have hit `GATE_TIMEOUT`). `MHS.OUTCOME.UNKNOWN` is now final;
   `MHS.OUTCOME.TIMEOUT` and `running` are still polled. G6 of the sr860 package: 90 s -> 0.08 s. Tests:
   `SettledReceiptTests` (3).
5. **`MHS/sdk/tests/core/test_registry.py::test_integration_fields`** asserted that julabo and sr860 are dispatchable. A
   passing package is maintained, not dispatched again, so the test now expects the wave-0 queue to hold exactly the
   exemplars whose evidence is not yet `contract_checked` (it stays right when the xArm and Gymnasium packages land).
6. **The julabo example overlay fills a limit instead of narrowing one.** The step asks for an overlay that narrows the
   setpoint, but nothing narrows an `operator_required` bound: `site-limits.example.json` supplies 15..60 Cel (the
   schema says an overlay also fills operator_required limits). The sr860 overlay does narrow: frequency 1..100000 Hz,
   amplitude at most 0.1 V, and a subset of the allowed time constants. Both are examples, not statements about a unit.

### Behavioural changes

- `mhs.driver check` prints one more line on a pass (`gate digest (RESULT.json gate.digest): ...`); the `PASS:` line and
  the exit codes are unchanged. `mhs.driver.check.stable_digest` is new public API (`__all__`).
- G8 applies `site-limits.example.json` to its endpoints. A package with an example overlay now has its conformance
  inputs checked against the narrowed limits (a `fixtures/conformance.json` entry must fit them). Packages without an
  overlay behave as before. The G8 row of `MHS/sdk/INTERFACE.md` still reads correctly and was not regenerated.
- G6 is faster for SCPI and serial drivers (no 15 s waits). No verdict changes: `unknown` still counts as an honest
  failure outcome.
- Records of drivers with a passing package: `evidence.provenance_refs` is `RESULT.json` only, `x-vendor.overlay.files`
  lists committed files only. The regenerated julabo and sr860 cards have `package_status: pass`, so they are not
  dispatched again; `task.json` of both packages is a copy of the regenerated card (gate G1 `CARD_EDITED`).
